# خطة هجرة البيانات وتفعيل RLS للأسرة والتنويم (Beds & Wards Migration & RLS Activation Plan)
## نظام نما الطبي (NamaMedical) - بيئة Staging

توثق هذه الخطة الخطوات والترتيب المقترح لتعبئة البيانات وتفعيل سياسات Row-Level Security (RLS) للأسرة والأجنحة والتنويم في المراحل القادمة بشكل آمن ومنعزل.

---

### 1. تقييم الحالة الهيكلية الحالية لقاعدة البيانات
بناءً على نتائج التدقيق البرمجي وقراءة قاعدة البيانات في بيئة Staging:
- **تغطية الأعمدة**: الأعمدة الأساسية `tenant_id` و `branch_id` (أو `facility_id`) **موجودة ومثبتة بالفعل** في كافة جداول الأسرة والأجنحة والتنويم وحركات النقل الداخلي بفضل هجرات سابقة.
- **حالة تعبئة البيانات (Backfill)**: تم إجراء التعبئة المسبقة بنجاح، وجميع السجلات الحالية مسندة للـ Tenant 1 والـ Branch 1، ولا توجد أي سجلات تحتوي على قيم NULL.
- **الحالة الراهنة لـ RLS**: نظام RLS مفعل فقط على جدول `emergency_beds` وغير مفعل على بقية الجداول الأربعة (`wards`, `beds`, `admissions`, `bed_transfers`).

وبناءً عليه، **لا تتطلب هذه المرحلة أي تغيير هيكلي (No Schema Change) ولا هجرات تعبئة واسعة (No Backfill Needed)**. يتركز العمل المستقبلي بالكامل على **تفعيل RLS وإنشاء السياسات الأمنية فقط**.

---

### 2. الترتيب المنهجي لتفعيل RLS والتحقق (RLS Enablement Steps)

يوصى باتباع الخطوات التشغيلية الثمانية التالية بالتسلسل لضمان أمان التطبيق والتراجع الفوري:

1. **النسخ الاحتياطي الكامل (Preflight Backup)**: أخذ نسخة احتياطية كاملة لقاعدة بيانات Staging وحفظها بصيغة ملف `.bak` أو `.sql` قبل تطبيق أي سياسات جديدة.
2. **كتابة ملفات SQL للـ Migration**:
   - ملف التأسيس (`beds_ownership_rls_up.sql`): لتفعيل RLS وإنشاء السياسات على الجداول المعنية.
   - ملف التراجع (`beds_ownership_rls_down.sql`): لتعطيل RLS وحذف السياسات المضافة في حال حدوث خلل.
   - ملف التحقق (`beds_ownership_rls_validate.sql`): للتأكد الإنشائي من فحص القيود وسلامة السياسات.
3. **التشغيل التجريبي الآمن (Dry-Run)**: فحص السكربتات في بيئة محلية وتأكيد سلامة البناء نحوياً قبل التطبيق على خادم Staging.
4. **تفعيل الـ RLS الإنشائي (Up Migration)**: تشغيل سكربت التأسيس على خادم Staging.
5. **التحقق من صحة القيود والسياسات**: تشغيل سكربت التحقق وتأكيد أن RLS Enabled = true لكافة الجداول.
6. **تشغيل اختبارات عزل المستأجرين (Automated Smoke Tests)**:
   - تشغيل اختبارات `cross_tenant_inpatient_beds_test.js` تحت دور المستخدم المقيد `test_rls_user` وتأكيد نجاح الـ 53 فحصاً برمجياً.
   - تشغيل بقية اختبارات الدخان المعتمدة للنظام لضمان عدم حدوث أي انكسار للعمليات الحالية.
7. **التحقق البشري واليدوي (Manual QA Verification)**: الدخول للواجهة ببيانات مستأجرين مختلفين والتحقق من عزل الأجنحة والأسرة وحسابات الإشغال بدقة.
8. **التوثيق النهائي وإغلاق البوابة**: كتابة التقارير وتحديث ذاكرة المشروع الذكية.

---

### 3. خطة التراجع السريع والجاهزية للحوادث (Rollback Readiness)
في حال رصد أي مشكلة تشغيلية (مثل توقف مسارات API أو ظهور أخطاء حظر غير مبررة)، يتم تشغيل سكربت التراجع فوراً لتعطيل RLS واستعادة الاتصال الطبيعي دون التأثير على البيانات المخزنة:
```sql
ALTER TABLE wards DISABLE ROW LEVEL SECURITY;
ALTER TABLE beds DISABLE ROW LEVEL SECURITY;
ALTER TABLE admissions DISABLE ROW LEVEL SECURITY;
ALTER TABLE bed_transfers DISABLE ROW LEVEL SECURITY;
```
