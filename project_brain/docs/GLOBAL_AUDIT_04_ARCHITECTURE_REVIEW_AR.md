# التدقيق العالمي 04 — مراجعة المعمارية (Architecture Review)

> التاريخ: 2026-06-20 | التصنيف: P0 (خطر مباشر) / P1 (عالٍ) / P2 (تحسين مهم) / P3 (لاحق).

---

## 1. نظرة عامة معمارية

- **النمط**: Monolith أحادي (Node.js/Express) — كل المنطق في `server.js` (7,044 سطراً) وكل الواجهة في `app.js` (10,884 سطراً).
- **الفصل**: Backend (API JSON) + Frontend (SPA يستهلك `/api/*`) — فصل منطقي جيد عبر REST.
- **الوصول للبيانات**: استعلامات `pg` مباشرة (parameterized)؛ لا ORM. سياق المستأجر عبر GUC (`set_config('app.tenant_id', ...)`) في `tenant_context_pg_session.js`.
- **الجلسات**: express-session + connect-redis مع منع التراجع لـ MemoryStore في الإنتاج (`process.exit(1)` عند فشل Redis).
- **النشر**: PM2 + Nginx (reverse proxy) + Let's Encrypt HTTPS.

## 2. تصنيف المشاكل المعمارية

### P0 — خطر مباشر
| # | المشكلة | الدليل | الأثر |
| - | ------- | ------ | ----- |
| P0-1 | **تباين RLS بين المصدر والإنتاج**: سياسات FORCE RLS على 13 جدولاً مُطبّقة يدوياً على خادم الإنتاج وليست في `db_postgres.js`/migrations متتبعة | المصدر يحوي RLS لـ 3 جداول overrides فقط | فقدان الحوكمة: أي إعادة بناء/استعادة DB من المصدر تُسقط RLS صامتاً → تسريب بين المستأجرين |

> **توضيح**: الذاكرة توثّق أن FORCE RLS على 13 جدولاً تم تنفيذه عبر DDL مباشر على الإنتاج (المراحل 103/106) ونجح. الخطر ليس في غياب RLS الآن، بل في **عدم وجود مصدر حقيقة واحد متتبع (single source of truth)** لسياسات RLS داخل version control.

### P1 — خطر عالٍ
| # | المشكلة | الأثر |
| - | ------- | ----- |
| P1-1 | **Monolith ضخم بملف واحد** (`server.js` 7K سطر) | صعوبة الصيانة، مخاطر التعارض، صعوبة الاختبار الوحدوي |
| P1-2 | **لا طبقة خدمات (Service Layer)** — منطق العمل ممزوج بالمسارات | تكرار، صعوبة إعادة الاستخدام، اختبار صعب |
| P1-3 | **لا معالجة أخطاء مركزية موحّدة** (error-handling middleware) واضحة | استجابات خطأ غير متسقة، خطر تسريب stack traces |
| P1-4 | **`CORS origin: true` + `credentials: true`** | مخاطر CSRF عبر النطاقات (انظر Gate 6) |
| P1-5 | **لا مهام خلفية/طابور (job queue)** | لا يمكن نقل المهام الثقيلة (تقارير/إخطارات) خارج دورة الطلب |

### P2 — تحسين مهم
| # | المشكلة | الأثر |
| - | ------- | ----- |
| P2-1 | لا ORM/طبقة migrations متتبعة موحّدة | المخطط يُدار عبر `CREATE TABLE IF NOT EXISTS` + ALTER يدوي |
| P2-2 | تسجيل (logging) غير مهيكل (لا JSON logs/correlation id) | صعوبة التتبع والمراقبة |
| P2-3 | لا تخزين مؤقت (caching) للقراءات الثقيلة عدا الجلسات | حمل DB أعلى عند التوسع |
| P2-4 | رفع الملفات يُخزّن في `public/uploads` (قابل للوصول العام) | يجب نقله خارج public + توقيع روابط |
| P2-5 | لا فصل بيئات واضح للإعدادات (config management) | اعتماد على `.env` + قيم افتراضية مضمّنة |

### P3 — تحسين لاحق
| # | المشكلة |

## 3. القابلية للتوسع (Scalability)

| البُعد | الحالة | الملاحظة |
| ------ | ------ | -------- |
| Horizontal scaling | ممكن جزئياً | الجلسات في Redis تتيح عدة instances؛ لكن MemoryStore للجلسات النشطة (Map) في `server.js` يكسر تعدد العمليات |
| Statelessness | جزئي | `activeSessions` Map داخل الذاكرة → غير مشترك بين instances |
| DB pooling | نعم | `pg.Pool` (max 20) |
| Background work | لا | لا طابور مهام |
| CDN/الأصول الثابتة | لا | تُخدم من Nginx مباشرة |

> **ملاحظة توسع حرجة**: وجود `activeSessions` كـ `Map` في الذاكرة (لفرض جلسة واحدة) يعني أن تشغيل أكثر من عملية/خادم سيُفقد تماسك هذا المنطق. يجب نقله إلى Redis قبل التوسع الأفقي.

## 4. التوصيات المعمارية (مرتبة)

1. **(P0)** نقل سياسات RLS إلى ملف migration متتبع في Git + سكربت تحقق idempotent يُعاد تطبيقه عند أي استعادة/إعادة نشر. مصدر حقيقة واحد.
2. **(P1)** تقسيم `server.js` تدريجياً إلى routers + service layer حسب الموديول (دون إعادة كتابة شاملة).
3. **(P1)** إضافة error-handling middleware مركزي يمنع تسريب التفاصيل ويوحّد الاستجابات.
4. **(P1)** تقييد `CORS origin` لنطاقات معروفة.
5. **(P1)** نقل `activeSessions` من ذاكرة العملية إلى Redis لتمكين التوسع الأفقي.
6. **(P2)** logging مهيكل (JSON + correlation id) + نقل الرفع خارج `public`.
7. **(P3)** OpenAPI spec + API versioning + Docker.

---

## 5. القرار

المعمارية **سليمة وعملية ومناسبة لمستشفى/عيادة واحدة في الإنتاج الحالي**، لكنها تحمل ديون معمارية (Monolith ضخم، حالة في الذاكرة، حوكمة RLS خارج المصدر) تحدّ من **التوسع الأفقي والصيانة طويلة الأمد كـ SaaS عالمي**. لا توجد مشكلة P0 تمنع التشغيل الحالي، لكن P0-1 (حوكمة RLS) **يجب** معالجته لضمان عدم تسريب صامت مستقبلي.
