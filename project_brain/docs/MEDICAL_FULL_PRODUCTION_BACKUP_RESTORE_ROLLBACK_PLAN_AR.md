# خطة النسخ الاحتياطي والاستعادة والتعافي السريع للإنتاج (Backup, Restore, and Rollback Production Plan)
## نظام نما الطبي (NamaMedical) - مرحلة التخطيط للترقية والعبور للإنتاج

توثق هذه الخطة التدابير الحمائية وإجراءات الطوارئ للنسخ الاحتياطي واستعادة البيانات والتعافي الفوري (Rollback) عند حدوث أي حوادث أمنية أو تقنية أثناء عبور النظام لبيئة الإنتاج الكامل.

---

### 1. إجراءات النسخ الاحتياطي والتحقق (Backup & Verification Standards)

1. **النسخ الاحتياطي قبل ساعة الصفر (Pre-Cutover Backup)**:
   - يتم أخذ نسخة احتياطية كاملة وثنائية من قاعدة البيانات باستخدام أداة `pg_dump` مع تمكين التنسيق المخصص والضغط:
     ```bash
     pg_dump -h localhost -p 5432 -U postgres -d nama_medical_web -F c -b -v -f /var/backups/db/nama_medical_prod_pre_cutover.bak
     ```
2. **الاستبعاد التام من مستودع Git**:
   - إجبارية استبعاد مجلد النسخ الاحتياطية `/var/backups/` تماماً من تتبع Git وإدراجه في ملف التكوين `.gitignore` لمنع أي تسريب لقاعدة البيانات.
3. **التحقق الهيكلي من جودة النسخة (Verification)**:
   - التحقق من حجم ملف النسخة الاحتياطية وتأكيد عدم كونه فارغاً.
   - إجراء تمرين استعادة جاف (Restore Dry-Run) على خادم اختبار معزول والتأكد من مطابقة عدد الجداول الإجمالي لـ `148 جدولاً` وتماثل البنية الهيكلية لضمان سلامة البيانات قبل الترقية.

---

### 2. مسببات التراجع السريع عند النشر (Rollback Triggers)

يتم تفعيل قرار التراجع الفوري عن النشر والعودة للحالة المستقرة السابقة عند حدوث أي من المؤشرات التالية:
1. **فشل بدء الخدمة**: توقف خادم الويب تحت PM2 أو تكرار الانهيار الذاتي (Crash Loops).
2. **عطل قاعدة البيانات**: فشل تشغيل الهجرات الهيكلية أو حدوث تعارض يمنع اكتمال المعاملات.
3. **فشل التحقق الصحي**: عدم استجابة المسار `/api/health` أو إرجاع رمز استجابة مغاير لـ 200 OK.
4. **فشل اختبارات الدخان**: فشل تسجيل الدخول أو وجود خلل في التنقل وعرض الأقسام الطبية للوحة التحكم.
5. **انتهاك الأمان وعزل المستأجرين**: حدوث تسريب للبيانات بين المستأجرين أو فشل اختبارات العزل `cross_tenant_leak_test.js`.
6. **زمن تأخير مرتفع**: ارتفاع زمن استجابة طلبات المرضى واللوحة لأكثر من `2000 مللي ثانية`.

---

### 3. خطوات التراجع التقني الفوري (Rollback Execution Steps)

عند تفعيل أحد مسببات التراجع، يتم تنفيذ الخطوات التالية بالتسلسل:
1. **إيقاف تطبيق الويب الفاشل**:
   ```bash
   npx pm2 stop "nama-web-prod"
   ```
2. **استعادة السورس كود المستقر**:
   ```bash
   git checkout <LAST_STABLE_COMMIT_HASH>
   npm ci --only=production
   npm run build:css
   ```
3. **تطهير وإعادة استعادة قاعدة البيانات**:
   ```bash
   # إفراغ وإعادة بناء قاعدة البيانات (للتخطيط فقط)
   dropdb -h localhost -p 5432 -U postgres nama_medical_web
   createdb -h localhost -p 5432 -U postgres nama_medical_web
   
   # استعادة قاعدة البيانات من النسخة الاحتياطية الآمنة
   pg_restore -h localhost -p 5432 -U postgres -d nama_medical_web -v /var/backups/db/nama_medical_prod_pre_cutover.bak
   ```
4. **إعادة تشغيل خادم الويب المستقر**:
   ```bash
   npx pm2 start server.js --name "nama-web-prod"
   ```
5. **التحقق من العودة الآمنة**:
   - تشغيل اختبارات الصحة وقراءة السجلات وتأكيد استعادة الخدمة الفعالة.

---

### 4. معايير زمن التعافي ونقاط استعادة الخدمة (RTO / RPO targets)

1. **الحد الأقصى لزمن تعافي الخدمة (Recovery Time Objective - RTO)**:
   - يجب ألا يتجاوز الزمن الإجمالي لإيقاف النشر الفاشل واستعادة النسخة الاحتياطية وتشغيل الخدمة المستقرة السابقة عن **15 دقيقة**.
2. **الحد الأقصى لفقدان البيانات (Recovery Point Objective - RPO)**:
   - نظراً لأخذ النسخ الاحتياطي مباشرة قبل البدء بالترقية، يُستهدف خفض نسبة فقدان البيانات إلى **5 دقائق** كحد أقصى (وهي فترة سكون النظام لتنفيذ العبور).
