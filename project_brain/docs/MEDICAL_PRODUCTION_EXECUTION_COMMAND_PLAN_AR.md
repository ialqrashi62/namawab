# خطة الأوامر التنفيذية المقترحة للطرح الإنتاجي (Proposed Production Execution Command Plan)
## نظام نما الطبي (NamaMedical) - مرحلة التخطيط والتحقق

> [!IMPORTANT]
> **تنبيه هام**: هذه الأوامر والتعليمات هي خطة مقترحة ومعلقة بانتظار الموافقة التنفيذية الصريحة الثانية (`Proposed Commands Pending Final Approval`). يمنع منعاً باتاً البدء بتنفيذ أي منها قبل الحصول على موافقة العميل النهائية والخطية.

---

### 1. ضوابط وسياسة متجر الجلسات Redis للإنتاج
* **إلزامية اتصال Redis**: يعتبر اتصال خادم الويب بـ Redis متطلبًا إجباريًا بالكامل في بيئة الإنتاج الفعلي.
* **حظر التراجع لـ MemoryStore**: يمنع منعاً باتاً تشغيل النظام إنتاجياً باستخدام `MemoryStore` كوضع تشغيل عادي أو fallback مقبول في الإنتاج. التراجع للميموري ستور مقبول فقط في بيئات التطوير والـ Staging/Rehearsal أو كحالة تطوير غير إنتاجية.
* **سياسة إيقاف النشر عند الطوارئ**:
  - إذا فشل Redis قبل النشر: يتم إلغاء النشر فوراً وتثبيت القرار كـ `NO_GO_STOP`.
  - إذا فشل Redis أثناء أو بعد النشر: يتم تفعيل سياسة إيقاف خط الإنتاج فوراً (STOP_THE_LINE) ثم تشغيل التراجع التلقائي (ROLLBACK) للالتزام المستقر السابق، أو تفعيل خطة الطوارئ (Incident Plan).
  - لا يتم اعتبار النظام جاهزاً للإنتاج (`Production-ready`) إذا كان متجر الجلسات يعمل على `MemoryStore`.
  - لا يوجد fallback صامت في بيئة الإنتاج الفعلي.

**الحقول المعيارية لسياسة الإنتاج**:
```yaml
REDIS_REQUIRED_FOR_PRODUCTION: YES
MEMORYSTORE_ALLOWED_FOR_PRODUCTION: NO
REDIS_FAILURE_BEFORE_DEPLOY: NO_GO_STOP
REDIS_FAILURE_AFTER_DEPLOY: STOP_THE_LINE_ROLLBACK
```

### 2. بوابات وفحوصات التحقق ما قبل التنفيذ (Pre-execution Verification Gates)
يجب تشغيل بوابات الفحص التالية والتأكد من نجاحها قبل بدء التنفيذ. **توقف فوراً (STOP) إذا فشلت أي بوابة**:

1. **التحقق من هاش نسخة الإطلاق (Verify Release Candidate Hash)**:
   التأكد من مطابقة هاش الالتزام الرئيسي المرشح للإنتاج مع الالتزام الفعال.
2. **التحقق من هاش المجلد الفرعي (Verify Submodule Hash)**:
   التحقق من هاش submodule `namaweb` وتطابقه مع الالتزام المعتمد.
3. **التحقق من وصول خدمة Redis (Verify Redis Reachability)**:
   التأكد من أن منفذ خادم Redis متاح للاتصال من خادم الويب دون طباعة قيم الأسرار في السجلات:
   ```bash
   nc -z -v <redis_host> 6379
   ```
4. **التحقق من متغيرات البيئة (Verify Env Vars Existence)**:
   التحقق من وجود المتغيرات البيئية اللازمة (`REDIS_HOST` و `REDIS_PASSWORD` و `NODE_ENV`) دون طباعة قيمها.
5. **التحقق من مسار وصلاحيات النسخ الاحتياطي (Verify Backup Path)**:
   التأكد من وجود مجلد النسخ الاحتياطي وصلاحيات الكتابة عليه، وضمان كونه خارج تتبع Git.
6. **تنفيذ والتحقق من ملف النسخ الاحتياطي (Run Backup & Verify File)**:
   تشغيل أمر النسخ الاحتياطي والتأكد من نشوء ملف الـ bak وامتلاكه لحجم غير صفري.
7. **التحقق من الالتزام المستقر الأخير (Verify Previous Stable Commit)**:
   حفظ الهاش الحالي الفعال للتمكن من التراجع الفوري إليه.
8. **التحقق من اسم عملية PM2 (Verify PM2 Process Name)**:
   مطابقة اسم العملية في PM2 لتكوين المشروع.
9. **التحقق من فحص الصحة قبل النشر (Verify Health Endpoint Before Deploy)**:
   التأكد من استجابة خادم Staging الحالي بصحة ممتازة قبل البدء.
10. **التحقق من وجود ملفات SQL برمجياً (Verify SQL Scripts Existence)**:
    التأكد من وجود ملفات SQL للتحديث والتراجع في مساراتها المطلوبة من مسار العمل الفعال قبل التنفيذ.

### 3. الأوامر التنفيذية المقترحة (Proposed Execution Commands)

في حال الحصول على الموافقة الصريحة الثانية، سيتم إجراء التالي بدقة ومن جذر المشروع لمنع أي أخطاء في المسارات:

#### الخطوة الأولى: النسخ الاحتياطي لقاعدة البيانات (Database Backup)
```bash
# تنفيذ النسخ الاحتياطي من جذر المشروع وحفظه خارج مستودع Git
pg_dump -h localhost -p 5432 -U postgres -d nama_medical_web -F c -b -v -f /var/backups/db/nama_medical_prod_before_rls_up.bak
```
* **شرط إيقاف (Stop Condition)**: إذا فشل أمر النسخ الاحتياطي أو لم ينشأ الملف بنجاح: **توقف فوراً (STOP)**، ولا تقم بأي عملية نشر.

#### الخطوة الثانية: تحديث الكود وتثبيت التبعيات (Application Deploy)
```bash
# 1. تحديث الكود وتحديث المجلد الفرعي من جذر المشروع
git fetch origin
git checkout e44b7be
git submodule update --init --recursive

# 2. الانتقال إلى مجلد تطبيق الويب لتثبيت التبعيات وبناء التنسيق
cd namaweb
npm install --production
npm run build:css
cd ..
```
* **شرط إيقاف (Stop Condition)**: في حال فشل تثبيت التبعيات أو البناء البرمجي: **توقف فوراً (STOP)**، ولا تعتمد النشر وقم بالتراجع.

#### الخطوة الثالثة: ترقية قاعدة البيانات وتفعيل FORCE RLS (Database Upgrade)
```bash
# تنفيذ ملفات SQL من جذر المشروع مباشرة لضمان صحة المسارات
psql -h localhost -p 5432 -U postgres -d nama_medical_web -f docs/sql/production_readiness_force_rls_up.sql
psql -h localhost -p 5432 -U postgres -d nama_medical_web -f docs/sql/production_readiness_force_rls_validate.sql
```
* **شرط إيقاف (Stop Condition)**: إذا فشل استعلام التحقق الهيكلي أو ظهرت حالة `false` لأي جدول: **توقف فوراً (STOP)**، وقم بتشغيل خطة التراجع السريع (Rollback) فوراً.

#### الخطوة الرابعة: تفعيل متغيرات البيئة وإعادة تشغيل التطبيق (Process Manager)
```bash
# إعادة التشغيل وتحديث المتغيرات البيئية من جذر المشروع
pm2 restart nama-web --update-env
pm2 logs nama-web --lines 50
```
* **شرط إيقاف (Stop Condition)**:
  * إذا لم يتصل التطبيق بـ Redis بنجاح أو ظهر أي تحذير تراجع للميموري ستور (`MemoryStore fallback`): **توقف فوراً (STOP)**، وقم بالتراجع الفوري للالتزام المستقر السابق.

#### الخطوة الخامسة: فحص الصحة المبدئي (Smoke Test)
```bash
# التحقق من صحة النظام عبر نهاية فحص الصحة
curl -I http://localhost:3000/api/health
```
* **شرط إيقاف (Stop Condition)**: إذا لم تستجب الصحة برمز `200 OK`: **توقف فوراً (STOP)**، وقم بالتراجع الفوري (Rollback).

### 4. الخلاصة وحالة العبور (Gate Conclusion)
* **حالة خطة الأوامر**: **PASS** (تم صياغة البوابات المسبقة، وشروط الإيقاف الصارمة بنجاح بمسارات نسبية).
* **التوصية**: الانتقال لتصحيح التقرير التالي.

**القرار**: تم إعداد خطة الأوامر بنجاح وبانتظار موافقة التشغيل المباشر (**Command Plan: PASS**).
