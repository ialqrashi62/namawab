# تقرير اعتماد نظام تصميم Google Stitch (Google Stitch Design System Adoption Report)
## نظام نما الطبي - تأمين وحوكمة قواعد البيانات الطبية

---

### 1. سبب اعتماد نظام تصميم Google Stitch (Rationale)

بهدف الحفاظ على اتساق الهوية البصرية، وتقديم تجربة مستخدم سريرية احترافية تتوافق مع معايير Google وتصاميم SaaS الحديثة، تم رسمياً اعتماد مشروع Google Stitch كمصدر وحيد ونهائي لتصميم واجهات الاستخدام لنظام نما الطبي. يمنع الاعتماد على التخمين البصري أو التطوير العشوائي للواجهات، مما يضمن اتساق الألوان، الخطوط، التباعد، والمظهر العام للبطاقات واللوحات (Neon Glow Glassmorphism).

* **رابط التصميم الرسمي المعتمد**:
  https://stitch.withgoogle.com/projects/17612445146025313712

---

### 2. نطاق الاستخدام والتطبيق (Scope)

#### أ. متى يُستخدم إلزامياً؟
- عند إضافة أي قسم أو صفحة أو شاشة لوحة تحكم (Dashboard) جديدة.
- عند إعداد واجهات موديولات الطبيب والتمريض والطوارئ والصيدلية والتأمين.
- عند إجراء تعديلات هيكلية في القائمة الجانبية (Sidebar) أو الترويسة (Topbar) أو النماذج (Forms) والجداول (Tables).
- عند تحويل أي فكرة أو متطلب تصميمي لـ UI تفاعلي في الكود.

#### ب. متى لا يُستخدم؟
- عند معالجة ثغرات البرمجة الخلفية (Backend Bugs).
- عند تفعيل أو مراجعة سياسات أمان السجلات (RLS/Security only).
- عند أخذ أو استعادة النسخ الاحتياطية وإجراء محاكاة الطوارئ.
- عند كتابة وتعديل سكربتات هجرة البيانات وتعديل الجداول.

---

### 3. تدفق عمل إضافة شاشة جديدة (New Screen Workflow)

1. **المراجعة والبحث**: فتح رابط مشروع Stitch وتحديد الشاشة المرجعية الأقرب للمتطلب الجديد.
2. **مطابقة الأنماط (Design Mapping)**: استخراج الرموز البصرية (spacing, typography, color tokens) والبطاقات والنماذج وتسجيلها كـ Design Mapping في خطة العمل.
3. **التطبيق التدريجي**: كتابة كود الواجهة في الملفات المعنية (`namaweb/public/index.html` أو `public/js/app.js`) باستخدام أنماط Vanilla CSS الموحدة في `public/css/styles.css`.
4. **توثيق الفروقات (Design Drift)**: تسجيل أي اختلافات اضطرارية ناتجة عن قيود تقنية أو متطلبات حماية الخصوصية.

---

### 4. حوكمة ملفات التصميم المستوردة (Code ZIP Conversion Policy)

في حال تنزيل ملف كود مضغوط (Code ZIP) من مشروع Stitch:
- **يُمنع منعاً باتاً فك الضغط ونسخ الملفات مباشرة فوق الكود الحالي للنظام** لتفادي كسر روابط الجلسات أو الـ APIs أو سياسات RLS النشطة.
- يجب دراسة الملفات المستخرجة بشكل معزول واستخلاص الكلاسات والمكونات البرمجية وتطبيقها يدوياً وتدريجياً.
- يمنع دفع ملفات ZIP المضغوطة الكبيرة أو الأصول غير المصرح بها لمستودع Git الخاص بالمشروع.

---

### 5. معايير تأكيد الجودة البصرية والبرمجية (UI QA Gates)

بعد إتمام بناء أو تعديل أي واجهة معتمدة على Stitch، يُلزم تشغيل الفحوصات التالية:
1. **بناء CSS وتأكيد النحو**:
   - تشغيل `npm run build:css` لتجميع الأنماط.
   - تشغيل `node --check` للملفات البرمجية للتحقق من سلامة الأسطر البرمجية.
2. **اختبارات E2E Smoke**: تشغيل `node namaweb/e2e_local_smoke_test.js` للتأكد من عدم كسر أي تدفق تشغيلي.
3. **فحص الالتزام بالترميز**: التأكد من ترميز الملفات العربية بـ UTF-8 السليم وتلاشي الماشيباكي.
4. **التحقق من التحذير**: بقاء شريط التحذير (`HTTPS-secured staging environment - Not production ready`) ظاهراً وواضحاً للعيان لمنع خلط البيئات.

---

### 6. المخاطر والخطوات التالية (Risks & Next Phase)

* **المخاطر**: تعارض بعض حزم CSS المستوردة مع التنسيق المخصص الحالي للمشروع. تم وضع ضوابط اختبار Visual QA للحد من هذا التعارض وتوفير إمكانية التعديل المرن.
* **المرحلة التالية الموصى بها**: تفعيل مهارة Stitch عند البدء في بناء أي موديول UI جديد كدورة حياة التمريض أو مبيعات الصيدلية التفاعلية.
