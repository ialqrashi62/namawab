### 2. سياسة تفعيل متجر الجلسات Redis في الإنتاج
لتجنب تعريض أمن وتوسيع الجلسات للخطر في بيئة الإنتاج:
* **إلزامية Redis**: يعتبر ربط وتفعيل متجر الجلسات الموزع Redis إلزامياً بالكامل في بيئة الإنتاج الفعلي.
* **حظر MemoryStore**: يمنع منعاً باتاً تشغيل النظام إنتاجياً باستخدام `MemoryStore` كوضع تشغيل عادي أو fallback مقبول في الإنتاج. التراجع للميموري ستور مقبول فقط في بيئات التطوير والـ Staging/Rehearsal أو كحالة تطوير غير إنتاجية.
* **سياسة إيقاف النشر عند الطوارئ**:
  - إذا فشل Redis قبل النشر: يتم إلغاء النشر فوراً وتثبيت القرار كـ `NO_GO_STOP`.
  - إذا فشل Redis أثناء أو بعد النشر: يتم تفعيل قرار إيقاف خط النشر فوراً (STOP_THE_LINE) ثم تشغيل التراجع التلقائي (ROLLBACK) للالتزام المستقر السابق، أو تفعيل خطة الطوارئ (Incident Plan).
  - لا يتم اعتبار النظام جاهزاً للإنتاج (`Production-ready`) إذا كان متجر الجلسات يعمل على `MemoryStore`.
  - لا يوجد fallback صامت في بيئة الإنتاج الفعلي.

**الحقول المعيارية لسياسة الإنتاج**:
```yaml
REDIS_REQUIRED_FOR_PRODUCTION: YES
MEMORYSTORE_ALLOWED_FOR_PRODUCTION: NO
REDIS_FAILURE_BEFORE_DEPLOY: NO_GO_STOP
REDIS_FAILURE_AFTER_DEPLOY: STOP_THE_LINE_ROLLBACK
```

### 3. قائمة الأوامر الموصى بتنفيذها على خادم الإنتاج (Execution Commands)

بمجرد صدور الموافقة التنفيذية الصريحة الثانية، سيتم تشغيل السلسلة التالية من الأوامر بالتسلسل الدقيق:

#### الفحوصات الاستباقية (Pre-execution Verification Gates)
يجب التأكد من نجاح الفحوصات التالية بالكامل قبل البدء. **توقف فوراً (STOP) إذا فشلت أي بوابة**:
* التحقق من هاش نسخة الإطلاق الرئيسية المطابقة للالتزام الفعال.
* التحقق من هاش المجلد الفرعي `namaweb` وتطابقه مع الالتزام المعتمد.
* التحقق من وصول خدمة Redis ومنفذ 6379 دون طباعة قيم الأسرار.
* التحقق من وجود الأسماء التعريفية للمتغيرات البيئية اللازمة دون طباعة قيمها.
* التحقق من مسار وصلاحيات النسخ الاحتياطي لقاعدة البيانات وضمان كونه خارج تتبع Git.
* تشغيل أمر النسخ الاحتياطي والتحقق من نشوء ملف الـ bak وحجمه غير الصفري.
* التحقق من اسم عملية PM2 والتزامات Git السابقة للاستعداد للتراجع.
* التحقق من استجابة خادم الصحة (Health Endpoint) بنجاح قبل البدء.
* التحقق من وجود ملفات SQL برمجياً من مسار العمل الفعال قبل التنفيذ.

#### الأوامر التنفيذية المقترحة
1. **النسخ الاحتياطي لقاعدة البيانات (Database Backup)**:
   ```bash
   pg_dump -h localhost -p 5432 -U postgres -d nama_medical_web -F c -b -v -f /var/backups/db/nama_medical_prod_before_rls_up.bak
   ```
   *(إذا فشل النسخ الاحتياطي أو لم ينشأ الملف بنجاح: **توقف فوراً (STOP)** ولا تنشر).*
2. **تحديث الكود وتثبيت التبعيات (Code Rollout)**:
   ```bash
   # جلب التعديلات وتحديث المستودع الفرعي من جذر المشروع
   git fetch origin
   git checkout e44b7be
   git submodule update --init --recursive

   # تثبيت وبناء تطبيق الويب
   cd namaweb
   npm install --production
   npm run build:css
   cd ..
   ```
   *(إذا فشل التثبيت أو البناء البرمجي: **توقف فوراً (STOP)**).*
3. **ترقية قاعدة البيانات وتفعيل FORCE RLS**:
   ```bash
   # تشغيل استعلامات SQL من جذر المشروع لضمان صحة المسارات
   psql -h localhost -p 5432 -U postgres -d nama_medical_web -f docs/sql/production_readiness_force_rls_up.sql
   psql -h localhost -p 5432 -U postgres -d nama_medical_web -f docs/sql/production_readiness_force_rls_validate.sql
   ```
   *(إذا فشل استعلام التحقق الهيكلي أو ظهرت حالة false: **توقف فوراً (STOP)** وتشغيل التراجع Rollback).*
4. **إعادة تشغيل خادم الويب والتحقق من السجلات**:
   ```bash
   pm2 restart nama-web --update-env
   pm2 logs nama-web --lines 50
   ```
   *(إذا ظهر أي تحذير تراجع الجلسة للميموري ستور: **توقف فوراً (STOP)** وتشغيل التراجع).*
5. **فحص الصحة محلياً**:
   ```bash
   curl -I http://localhost:3000/api/health
   ```
   *(إذا لم تستجب الصحة برمز 200 OK: **توقف فوراً (STOP)** وتشغيل التراجع).*

### 4. خطة التراجع السريع عند الطوارئ (Rollback Steps)
1. **إلغاء قسرية الـ RLS عن قاعدة البيانات**:
   ```bash
   psql -h localhost -p 5432 -U postgres -d nama_medical_web -f docs/sql/production_readiness_force_rls_down.sql
   ```
   *(أو استرداد قاعدة البيانات بالكامل من النسخة الاحتياطية).*
2. **تراجع الكود وإعادة التشغيل**:
   ```bash
   git checkout <previous_stable_commit_hash>
   npm install --production
   pm2 restart nama-web
   ```
