## 2. الهيكل المعماري والبرمجي للمستودع (Repository & System Architecture)

يتكون المشروع من مستودع Git رئيسي يحتوي على مستودع فرعي (Submodule) باسم `namaweb`:

```
NamaMedical/ (المستودع الرئيسي الأب)
│   .git/
│   .ai-brain/ (ذاكرة المساعد الذكي وحزمة المهارات)
│   │   AI_PROJECT_MEMORY.md (ذاكرة مراحل التطوير)
│   │   skills/ (التعليمات المخصصة وحزم الحوكمة الطبية)
│   namaweb/ (مستودع كود التطبيق الأساسي - Node.js Express)
│   │   .git/
│   │   server.js (نقطة الدخول والتحكم والـ APIs)
│   │   database.js (منشئ قاعدة البيانات الأساسي)
│   │   db_postgres.js (محرك اتصالات PostgreSQL وربط سياق المستأجرين)
│   │   public/ (ملفات الواجهة الثابتة وأكواد العميل)
│   │   migrations/ (نصوص التعديلات الهيكلية الآمنة)
│   │   ...
│   docs/ (ملفات التقارير، دراسات الأمان وخارطة الطريق التفصيلية)
│   │   PHASE_A1_EMR_LOCK_SIGNATURE/
│   │   PHASE_A2_MFA/
│   │   PHASE_A3_PHI_ENCRYPTION_VAULT/
│   │   ...
```

### التقنيات الأساسية المستخدمة (Tech Stack)
1. **الخادم (Backend)**: خادم Express.js يعتمد على Node.js للـ Routing ومنطق الأعمال والتحقق من الجلسات.
2. **قاعدة البيانات (Database)**: PostgreSQL متكاملة مع آلية Row Level Security (RLS) لضمان حماية PHI.
3. **الذاكرة المخبئية والجلسات (Caching & Session)**: Redis (ممثلة بحاوية `nama-redis` وتدار عبر Docker Desktop).
4. **مدير العمليات**: PM2 لمراقبة التشغيل وإعادة الإحياء المستقر للتطبيق.
5. **الواجهة الأمامية (Frontend)**: واجهات HTML5 ديناميكية مدعومة بلغة CSS قياسية (Vanilla CSS) محسنة محلياً، تدعم اللغة العربية والإنجليزية وتخطيط RTL.

## 3. حوكمة عزل المستأجرين وحماية قاعدة البيانات (Database RLS & Tenant Isolation)

تم تطبيق عزل تام للبيانات الطبية والحساسة للمستأجرين والمرافق الصحية على مستوى قاعدة البيانات لمنع تسريب البيانات بين المستشفيات والمستفيدين:

* **آلية الحقن الذكي للسياق (AsyncLocalStorage)**:
  - عند استقبال خادم الويب أي طلب مصادق، يقوم Middleware بجلب `tenantId` من جلسة المستخدم الموثوقة وحفظها في سياق تشغيل معزول عبر `AsyncLocalStorage` في `db_postgres.js`.
  - تم تغليف استدعاءات `pool.query` لتمرير قيمة `app.tenant_id` ديناميكياً إلى اتصال قاعدة البيانات الحالي قبل تنفيذ الاستعلام، وتصفيره فور انتهاء المعاملة وإرجاع الاتصال للـ Pool.
* **تصفية الصفوف تلقائياً (Fail-Closed RLS)**:
  - جميع الجداول الـ 150 الحساسة مفروض عليها `FORCE ROW LEVEL SECURITY`.
  - السياسة الافتراضية تعتمد على: `USING (tenant_id = (current_setting('app.tenant_id', true))::integer)`.
  - في حال محاولة إجراء أي استعلام بدون سياق مستأجر نشط، تعيد قاعدة البيانات **صفر صفوف** تلقائياً.
  - إدراج أي سجل جديد بدون تمرير معرّف المستأجر يتم ختمه تلقائياً بالاعتماد على قيم الـ DEFAULT في جداول قاعدة البيانات: `ALTER TABLE ... ALTER COLUMN tenant_id SET DEFAULT (NULLIF(current_setting('app.tenant_id', true), ''))::integer`.
  - محاولات التزوير أو الكتابة المتقاطعة للمستأجرين تُجابه بخطأ نظامي `42501 (Violation of RLS)`.

## 4. المنجزات الأمنية وحماية الخصوصية (Post-Acceptance Security Wave)

تم إغلاق وتطبيق سلسلة من حواجز الأمان الإضافية لتقسية بيئة الإنتاج:

1. **إغلاق وحراسة السجلات الطبية (EMR Lock & Signature - Phase A1)**:
   - منع التعديل على ملفات وملاحظات المرضى بعد توقيعها برمجياً وقفل حقل `emr_status`.
   - توليد وحفظ بصمة سلامة السجل الرقمي باستخدام SHA-256.
   - إعداد شاشات ونماذج توقيع الأطباء وطلب إجراء تعديلات مبررة (Amendments) مسجلة بالكامل.
2. **المصادقة الثنائية (TOTP MFA - Phase A2)**:
   - تطبيق المصادقة الثنائية الاختيارية عبر رموز الـ Authenticator المتوافقة مع RFC-6238.
   - تصليب ضد هجمات القوة الغاشمة وتكرار الجلسات وتثبيتها.
3. **خزنة وحراسة ملفات المرضى (PHI File Guard - Phase A3A)**:
   - إنشاء مسار آمن `GET /api/phi-files/:id` لقراءة المرفقات الحساسة المخزنة في مجلد معزول خارج مسار خادم الويب العام لمنع الـ Directory Traversal والوصول العشوائي.
   - تقييد امتدادات الملفات المقبولة (Content-Type Pinning) وتوثيق الوصول أمنياً.
4. **تأمين النسخ الاحتياطية وتصليب سجل التدقيق (Backup & Audit Hardening)**:
   - إعداد برنامج نسخ احتياطي يومي تلقائي غير مراقب لقاعدة البيانات بالاعتماد على أداة `pg_dump` وحفظ اعتمادات الاتصال في ملف `.pgpass` الآمن دون تضمين كلمة المرور في كود السكريبت.
   - تعميق سجل تدقيق حركات الأمان ليشمل حركات الدخول الفاشلة والخروج والـ MFA.
5. **أمن المتصفح وحماية نهايات الإدارة (HTTP Perimeter & XSS Hardening)**:
   - ترميز المخرجات وتطهيرها ضد هجمات XSS على مستوى الخلايا والجداول والواجهات الإدارية (Layer 1) ومستوى المكونات التخصيصية المنبثقة (Layer 2).
   - حظر تصعيد الصلاحيات في إدارة المستخدمين `system_users` والموظفين.
   - تفعيل إعدادات شهادة SSL النطاق الأساسي وتوجيه نطاق `www` كنسياً عبر Nginx لمنع أخطاء الشهادات.
   - إعداد سياسة أمن المحتوى (Content Security Policy) بوضع التقرير والحد المانع، وتوجيه تقارير الانتهاك لنقطة استقبال آمنة ومحددة بمعدل طلبات معقول.

## 5. بيئة تكامل البيانات الطبية وصناديق الاختبار (Clinical Sandboxes)

لضمان اختبار عمليات الربط الطبي والمستودعات الطبية الشاملة دون التأثير على بيئة الإنتاج، تم إدراج وإعداد بيئات اختبار محلية (Staging Sandboxes) متكاملة في المشروع:

* **خادم صور الأشعة (Orthanc PACS Sandbox)**: محاكاة واستقبال وإرسال أفلام الأشعة عبر معيار DICOM الطبي.
* **محرك رسائل التكامل (Mirth Connect Sandbox)**: إدارة وتوجيه قنوات استقبال وإرسال رسائل HL7 الطبية ونقلها بين الأقسام.
* **محاكي المعاملات الطبية الذكي (Dummy FHIR Sandbox)**: محاكاة استقبال البيانات والتحقق من توافقها مع معيار HL7 FHIR وتخزين السجلات الطبية.

## 6. نظام تصميم Stitch RTL وتطبيق الواجهات الفاخرة

تمت إعادة تصميم وتطوير واجهات نظام نما الطبي بالكامل بالاعتماد على نظام تصميم **Stitch** المتميز للغات ثنائية الاتجاه (RTL العربية كأولوية)، مع التخلص الكامل من روابط الـ CDNs الخارجية لتلبية معايير أمان البيانات:

* **جرد وتصميم المكونات**:
  - جرد وتصنيف 45 شاشة وواجهة مستخدم رئيسية وفرعية و 80+ مكون واجهة مستخدم.
  - إعداد 14 موجه تصميم تفصيلي جاهز لمنصة Google Stitch لتغطية دورة أعمال المستشفى.
* **حزم الواجهات المطبقة والمثبتة (Completed Batches)**:
  - **Batch B (السريرية)**: إعادة تصميم المختبر (LIS)، الأشعة (RIS)، والصيدلية (Pharmacy) بنمط بصري متماسك ومظلم بتأثيرات Glassmorphism خفيفة.
  - **Batch C (سلسلة الإمداد)**: تطوير واجهة المخازن الطبية، الموردين، وعمليات الاستلام الذكي Bento Grid.
  - **Batch D (الإدارية والمالية)**: إتمام شجرة الحسابات، سندات الصرف، لوحة كفاءة الأجور WPS، ونموذج الامتثال للجودة المئوية التفاعلية.
  - **Batch E (الحوكمة والتحليلات)**: إتمام لوحة مستوى التهديد الأمني السيبراني SVG، تقويم الصيانة الوقائية (PM)، وأشرطة تقدم أهداف التحول لرؤية 2030، وإعادة تجميل وتعديل صفحة تسجيل الدخول `login.html` لتسمح بالتبديل الفوري والسلس للغتين العربية والإنجليزية ديناميكياً مع الحفظ محلياً.

## 7. سيناريوهات دورة العمل المتكاملة وحوكمة الأمان (End-to-End Business Scenarios & Security Governance)

لضمان سلامة الدورة الطبية والمالية وتشغيلها دون عيوب، تم تحديد وتأكيد سيناريوهات العمل التالية كأنماط حوكمة أساسية في النظام:

### 1) سيناريو تسجيل وإعداد المستأجرين (SaaS Tenant & Facility Onboarding)
* **الزناد (Trigger)**: قيام المشرف العام بإنشاء مستأجر جديد ومرفق صحي في النظام.
* **التدفق التشغيلي (Operational Flow)**:
  - التحقق من نوع المنشأة المضافة ومطابقتها للاستحقاقات المحددة (مثال: منشأة صيدلية فقط `pharmacy_only` تمنع برمجياً من الوصول لشاشات أو مسارات EMR أو المختبر).
  - تهيئة الجداول وحساب الصلاحيات بالكامل.
* **حوكمة الأمان والعزل (Security Governance)**:
  - يُحظر الوصول العشوائي عبر الروابط المباشرة بواسطة حراس الواجهة الموحدة المستندة إلى نوع المنشأة وسجل الاستحقاق (`facility_type`).
  - أي محاولة استخدام غير مصرح به تعيد رمز الخطأ `403 Facility type not entitled`.

### 2) سيناريو الاستقبال ودورة الزيارة الطبية (Patient Admission & Visit Lifecycle)
* **الزناد (Trigger)**: وصول المريض إلى الاستقبال لتسجيل بياناته وحجز موعد.
* **التدفق التشغيلي (Operational Flow)**:
  - إنشاء ملف طبي جديد للمريض وتوليد رقم الملف الطبي (MRN) الفريد.
  - جدولة موعد المريض وتسجيل الدخول الفعلي (Check-in) وتوليد رقم الزيارة (V-ID) للقسم المختص.
* **حوكمة الأمان والعزل (Security Governance)**:
  - يتم وسم بيانات المريض والزيارة تلقائياً بـ `tenant_id` المستمد من جلسة الموظف النشطة.
  - يُمنع تزوير المعرفات (IDOR)؛ فإذا حاول مستخدم من المستأجر A فتح ملف مريض للمستأجر B، ترفض قاعدة البيانات RLS جلب البيانات مباشرة وتعيد صفحة فارغة أو خطأ `404/403`.

### 3) سيناريو محطة الطبيب وتوقيع الملف الطبي (Doctor Station & EMR Lock Signature)
* **الزناد (Trigger)**: استدعاء الطبيب للمريض من طابور الانتظار وبدء الفحص السريري.
* **التدفق التشغيلي (Operational Flow)**:
  - فحص التاريخ المرضي، وكتابة ملاحظات الفحص والتشخيص (SOAP).
  - إرسال طلبات الأدوية أو الفحوصات وتأكيد إغلاق الزيارة وتوقيع السجل الطبي.
* **حوكمة الأمان والعزل (Security Governance)**:
  - بمجرد النقر على زر "توقيع السجل" (EMR Sign)، يقوم النظام بحساب بصمة تكامل البيانات SHA-256 للمحتوى الإكلينيكي وقفل حقل الحالة `emr_status = 'signed'`.
  - يمنع الخادم تماماً أي تعديل أو مسح في السجلات الموقعة لحماية مصداقية البيانات، ولا يسمح إلا بإضافة ملحقات تفسيرية مبررة (Amendments) كأحداث إضافية مسجلة وموثقة في سجل التدقيق.

### 4) سيناريو صرف الأدوية وحركة المخزون (Pharmacy Dispensing & Inventory FEFO)
* **الزناد (Trigger)**: إرسال الوصفة المعتمدة والموقعة من الطبيب تلقائياً إلى صيدلية المرفق.
* **التدفق التشغيلي (Operational Flow)**:
  - يراجع الصيدلي الوصفة في طابور الصرف ويقوم بالتحقق من التعارضات الدوائية.
  - تأكيد الصرف الفعلي وطباعة ملصق الباركود للدواء وصرف الحصة للمريض.
* **حوكمة الأمان والعزل (Security Governance)**:
  - تُمنع عمليات خصم المخزون قبل الصرف الفعلي.
  - يتم الخصم ديناميكياً بناء على معيار FEFO (ما تنتهي صلاحيته أولاً يُصرف أولاً) بالاعتماد على أرقام دفعات الأدوية (Batch Numbers) المدعومة بـ RLS لضمان سلامة مخازن المرفق وتجنب تلف الأدوية.

### 5) سيناريو الفحوصات المخبرية والطب الإشعاعي (LIS & RIS Diagnostic Loop)
* **الزناد (Trigger)**: إرسال الطبيب لطلب فحص مخبري أو فحص أشعة.
* **التدفق التشغيلي (Operational Flow)**:
  - جلب الطلب في المختبر/الأشعة -> سحب العينة وتوليد باركود العينة الفريد -> إدخال نتائج الفحص أو رفع تقرير الأشعة -> اعتماد النتيجة.
* **حوكمة الأمان والعزل (Security Governance)**:
  - تمنع واجهة المستخدم ظهور أي نتيجة أو تقرير للطبيب المعالج كمسودة قبل اعتمادها رسمياً وتوقيعها من أخصائي المختبر أو الأشعة المسؤول لمنع التشخيص الخاطئ.
  - يتم عزل مسارات النتائج وتخزين المرفقات الطبية بشكل منفصل ومحمي بـ RLS.

### 6) سيناريو الفوترة والامتثال لهيئة الزكاة والمطابقة المحاسبية (Billing, ZATCA, & Accounting Posting)
* **الزناد (Trigger)**: إصدار الفاتورة النهائية للمريض فور صرف الخدمات أو إنهاء الزيارة.
* **التدفق التشغيلي (Operational Flow)**:
  - احتساب تكاليف الزيارة وتوزيعها بين حصة المريض النقدية وحصة التأمين الطبي.
  - سداد الفاتورة وتوليد الفاتورة الإلكترونية المشفرة الحاملة لرمز الاستجابة السريعة (ZATCA QR).
* **حوكمة الأمان والعزل (Security Governance)**:
  - **الحدود المالية الذرية (Fail-Closed Transaction)**: عند تفعيل محرك المحاسبة، يتم ترحيل الفاتورة وتأثيرها المالي (Dr ذمم المرضى/التأمين، Cr الإيرادات، Cr ضريبة القيمة المضافة) في معاملة برمجية موحدة عابرة لقاعدة البيانات، فإذا فشل ترحيل أي حساب محاسبي، يتم إلغاء المعاملة بالكامل وتتوقف الفاتورة لمنع وجود فواتير بدون قيود محاسبية مقابلة (يتم مالي).
  - يُمنع الترحيل المكرر للفاتورة عبر فحص فريد وغير مكرر لرقم الفاتورة (Idempotency).

### 7) سيناريو منع التسريب والولوج غير المصرح به (Cross-Tenant Prevention Scenario)
* **الزناد (Trigger)**: محاولة مهاجم أو مستخدم مصادق من المستأجر A الوصول لبيانات أو تعديل سجلات المستأجر B عبر تغيير معرّف الطلب يدوياً (IDOR).
* **التدفق الأمني (Security Flow)**:
  - يقوم خادم الويب بفلترة الطلب أوتوماتيكياً ويمرره لقاعدة البيانات.
  - تفشل قاعدة البيانات فوراً في تلبية الطلب نتيجة لعدم مطابقة سياق `app.tenant_id` الفعلي وتُرجع صفوفاً فارغة (Fail-Closed) أو ترمي استثناء `42501 (Violation of RLS)`.
  - يسجل الخادم المحاولة الفاشلة تلقائياً كحدث مشبوه في سجل الأمان لتمكين التحليل اللاحق.

## 8. فجوات الحوكمة والبوابات المعلقة (Pending Approvals & Roadmap)

تبقى بعض البنود محجوبة أو معلّقة بانتظار توجيهات واعتمادات مالك النظام:

1. **نشر Vault Production على خادم معزول (Isolated VM)**:
   - الحالة: **محجوب (Blocked)**.
   - السبب: لضمان عزل مفاتيح التشفير، يمنع نشر الحاوية على نفس الخادم المشترك للتطبيق لتفادي تعطل الجلسات وإخفاق محرك Docker. يتطلب توفير خادم VM منفصل معزول مع تفعيل صلاحيات الـ SSH.
2. **تشفير at-rest للملفات والحقول الحساسة (Phase A3)**:
   - الحالة: **محجوب (Blocked)**.
   - السبب: لا تتوفر بيئة إدارة مفاتيح KMS سحابية أو سكريبت خارجي آمن لفك التشفير وقت التشغيل. النظام مجهز فور اعتماد مصدر المفاتيح.
3. **تفعيل ترحيل القيود المحاسبية الفعلية (Accounting Posting)**:
