# مستند تصميم آلية سياق المستأجر وإعدادات جلسة PostgreSQL (Tenant Context PostgreSQL Session Settings Design)
## Phase: Tenant Context Middleware for PostgreSQL Session Settings Design

---

## 1. الملخص التنفيذي
يوثق هذا المستند التصميم الهيكلي والبرمجي لآلية ضبط سياق المستأجر (`tenant_id`, `facility_id`, `branch_id`) داخل خادم قاعدة بيانات PostgreSQL لكل طلب (Request) أو عملية (Transaction)، تمهيداً لتفعيل سياسات أمان مستوى الصف (Row-Level Security - RLS) لاحقاً بشكل آمن وتدريجي دون تعطيل البيئة الإنتاجية أو تعريضها لمخاطر تسرب البيانات.

---

## 2. سبب الحاجة لهذه المرحلة
مع توجه النظام لتطبيق عزل المستأجرين على مستوى قاعدة البيانات باستخدام PostgreSQL RLS، تحتاج قاعدة البيانات إلى معرفة هوية وسياق المستأجر الذي يقوم بالاستعلام بشكل ديناميكي لكل عملية. الطريقة القياسية والآمنة هي استخدام متغيرات الجلسة (Session GUCs) مثل `app.tenant_id`.
يجب تصميم هذه الآلية بعناية فائقة لتفادي أكبر خطر في بيئات Express/PostgreSQL وهو **تسرب سياق الاتصال (Connection Pooling Context Leak)** بين الطلبات المختلفة.

---

## 3. تحليل طبقة الاتصال الحالية

بعد فحص الملفات البرمجية (`server.js`, `db_postgres.js`):
* **تجميع الاتصالات (Connection Pooling):** يستخدم النظام مكتبة `pg` ومحرك `pg.Pool` لإدارة الاتصالات وإعادة استخدامها لتوفير موارد الخادم.
* **الاستعلام المباشر (Direct Queries):** تعتمد معظم مسارات API في `server.js` على استدعاء `pool.query(...)` مباشرة. هذا الاختصار يقوم بحجز اتصال مؤقت من المجمع، وتنفيذ الاستعلام، ثم تحريره فوراً وإعادته للمجمع.
* **العمليات المتكاملة (Transactions):** يتم استخدام `pool.connect()` للحصول على اتصال مخصص (Client) فقط في السكربتات الخاصة بالتجهيز والتهيئة (Seeding) لحصر العمليات بين `BEGIN` و `COMMIT`/`ROLLBACK`.
* **النتيجة:** الاستخدام المباشر لـ `pool.query` يمنع ضبط متغيرات الجلسة بشكل مستمر لأن كل استعلام قد يعمل على اتصال مادي مختلف تماماً عن الاستعلام الذي قبله.

---

## 4. تحليل خطر تسرب تجميع الاتصالات (Connection Pooling Leak)

عند تشغيل خادم ويب، يتم تجميع الاتصالات المادية بقاعدة البيانات وإعادة استخدامها لخدمة طلبات مستخدمين مختلفين بشكل متتالي:
* **خطر SET المستمر:** إذا قام طلب يخص **المستأجر 1** بتنفيذ `SET app.tenant_id = 1;` على اتصال مادي، ثم انتهى الطلب وأُرجع الاتصال إلى المجمع (Pool) دون تنظيفه؛ فإن الطلب التالي (الذي قد يخص **المستأجر 2**) إذا حصل على نفس الاتصال المادي فإنه سيرث القيمة `app.tenant_id = 1`. إذا لم يقم المطور بضبط القيمة يدوياً، فإن قاعدة البيانات ستسمح للمستأجر 2 بقراءة أو تعديل بيانات المستأجر 1 بالكامل، وهو ما يمثل **خرقاً أمنياً خطيراً وتسللاً للبيانات**.
* **الفرق الفني بين SET و SET LOCAL:**
  * `SET parameter = value;` ➔ يغير الإعداد على مستوى الجلسة بالكامل، ويستمر التأثير حتى يتم إغلاق الاتصال أو تغيير القيمة يدوياً أو عمل `RESET`.
  * `SET LOCAL parameter = value;` ➔ يغير الإعداد **فقط طوال فترة العملية الحالية (Transaction)**، وبمجرد انتهاء العملية بـ `COMMIT` أو `ROLLBACK` يتم التراجع عن الإعداد تلقائياً وتطهير الاتصال المادي دون أي تدخل برمجى إضافي.
* **متى يقع الخطأ؟** إذا فشل كود التطبيق في عمل `RESET` للاتصال المادي بسبب حدوث خطأ استثنائي (Exception) لم يتم معالجته بشكل صارم في كتلة `finally`.
* **تأثير الأداء:** إن استخدام العمليات (Transactions) لكل عملية قراءة يزيد من استهلاك الموارد وعدد الرحلات بين التطبيق وقاعدة البيانات، لذا يجب قصر هذه الآلية على الاستعلامات الحساسة والجداول التي سيُطبق عليها RLS.

## 5. مراجعة وتصميم البدائل الأربعة

### البديل A: تطبيق SET LOCAL داخل Transaction Wrapper
* **الآلية:** يتم سحب Client مخصص من الـ Pool، والبدء بـ `BEGIN` ثم تشغيل `SET LOCAL app.tenant_id = N` ثم تشغيل الاستعلامات، وأخيراً `COMMIT` أو `ROLLBACK`.
* **المميزات:** أعلى درجات الأمان. يضمن عدم تسرب المعطيات إطلاقاً لأن التطهير يتم ذاتياً من محرك PostgreSQL عند انتهاء العملية.
* **العيوب:** يتطلب تعديل الأكواد البرمجية الحساسة للف الاستعلامات داخل Wrapper مخصص.

### البديل B: تطبيق SET مع RESET في كتلة Finally
* **الآلية:** تشغيل `SET app.tenant_id = N` على الاتصال المخصص، وتنفيذ العمليات، ثم تشغيل `RESET app.tenant_id` أو `DISCARD ALL` في كتلة `finally`.
* **المميزات:** لا يتطلب تشغيل transactions لكافة عمليات القراءة البسيطة.
* **العيوب:** خطورة عالية جداً في حال تعطل الخادم أو حدوث أخطاء غير متوقعة تمنع الوصول لكتلة `finally` أو تفشل في تنظيف الجلسة.

### البديل C: الاكتفاء بالفلترة البرمجية (Explicit Tenant Filters)
* **الآلية:** تمرير سياق المستأجر برمجياً في الاستعلام مثل `WHERE tenant_id = $1`.
* **المميزات:** بسيط، آمن من ناحية الـ Pool Leak، ومستقر للأداء.
* **العيوب:** لا يضمن حماية شاملة على مستوى قاعدة البيانات (لا يفعل RLS الحقيقي)، ويعتمد على انتباه المطور لعدم نسيان الفلتر في أي استعلام جديد.

### البديل D: المدخل الهجين (Hybrid Approach - الموصى به)
* **الآلية:** الجمع بين الفلترة البرمجية الحالية كخط دفاع أول للعمليات العامة، مع إدخال `withTenantTransaction` (البديل A) تدريجياً للعمليات والجداول الأكثر حساسية (المرضى، الفواتير، المواعيد).
* **المميزات:** يجمع بين أمان RLS الصارم وأداء النظام العالي، ويتيح تفعيلاً تدريجياً لسياسات الأمان دون التسبب في توقف النظام.

## 6. التصميم البرمجي المقترح (Pseudo-Code)

مستند التصميم التفصيلي متوفر باللغة الإنجليزية في: [tenant_context_pg_session_middleware_design.md](file:///c:/Users/ice/Desktop/NamaMedical/docs/design/tenant_context_pg_session_middleware_design.md)

### الكود الهيكلي للـ Helper:
```javascript
// namaweb/db_postgres.js

async function withTenantTransaction(req, handler) {
    const { tenantId, facilityId } = getRequestTenantContext(req);
    const isProduction = process.env.NODE_ENV === 'production';

    // التحقق الأمني في الإنتاج
    if (!tenantId && isProduction) {
        throw new Error('SECURITY_ERROR: Missing tenant context in production');
    }

    const context = {
        tenantId: tenantId || 1, // Dev fallback
        facilityId: facilityId || null
    };

    const client = await pool.connect();
    try {
        await client.query('BEGIN');
        
        // ضبط المتغيرات المحلية بالعملية الحالية فقط
        await client.query("SET LOCAL app.tenant_id = $1", [context.tenantId]);
        if (context.facilityId) {
            await client.query("SET LOCAL app.facility_id = $1", [context.facilityId]);
        } else {
            await client.query("SET LOCAL app.facility_id = NULL");
        }

        // تشغيل المعالج وتمرير العميل المخصص والبيانات
        const result = await handler(client, context);

        await client.query('COMMIT');
        return result;
    } catch (error) {
        await client.query('ROLLBACK');
        throw error;
    } finally {
        client.release(); // إعادة الاتصال نظيفاً تماماً إلى الـ Pool
    }
}
```

## 7. تحديد نطاق النموذج التجريبي القادم (Next Prototype Scope)
لضمان سلامة التصميم قبل تعميمه، سيتم تفعيل مرحلة تجريبية محلية مغلقة باسم `Tenant Context Middleware Local Prototype`:
* **عدم المساس بالإنتاج:** لن يتم تفعيل RLS أو عمل أي هجرات (migrations) على قاعدة البيانات الإنتاجية.
* **نطاق الاختبار:** إنشاء مسار تجريبي محدد (مثال: `/api/test/tenant-scope`) يخدم فحص الاتصال المعزول.
* **إثباتات الفحص المرجوة:**
  1. التحقق من أن إعدادات `SET LOCAL` تحجب وتسمح بالبيانات للمستأجر الفعلي داخل الـ transaction.
  2. إثبات عدم تسرب `tenant_id` بين الطلبات المتزامنة والمستقبلية على الاتصالات المادية المعاد استخدامها.
  3. إثبات أن عدم تمرير المستأجر في بيئة الإنتاج يفشل بأمان ويمنع الوصول للبيانات.

## 8. المخاطر المتبقية
1. **أداء مجمع الاتصالات:** زيادة طفيفة في زمن الاستجابة بسبب الحاجة لثلاث عمليات إضافية لكل طلب (`BEGIN`, `SET LOCAL`, `COMMIT`). سنقوم بتقييم هذا الأثر في البيئة التجريبية قبل التعميم.
2. **العمليات الخارجية والخلفية (Background Jobs):** السكربتات التي تعمل خارج سياق طلبات Express (مثل Startup seeds أو cron jobs) يجب استثناؤها أو تزويدها بصلاحيات مشرف النظام (bypass RLS) بشكل آمن.
