# BLOCKER — عدم توافق FORCE RLS مع آلية الاتصال (RLS/GUC Incompatibility)

> المرحلة: `P0_TENANT_ISOLATION_WAVE2B` | التاريخ: 2026-06-20 | الخطورة: **P0 (إنتاجي كامن)**
> الحالة: `BLOCKED_CRITICAL` — أُوقِف تنفيذ Wave 2B DDL. **لم يحدث أي تغيير على الإنتاج.**

---

## 1. وصف الحاجز

على خادم الإنتاج، الجداول الـ13 المحمية بـ `FORCE ROW LEVEL SECURITY` تستخدم سياسة:
```
USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::integer)
```
لكن التطبيق (`server.js`) يتصل عبر `pg.Pool` ويستخدم `pool.query(...)` مباشرة، و**لا يضبط `app.tenant_id` إطلاقاً** (لا `set_config`، لا `SET LOCAL`، ولا استخدام لـ `withTenantTransaction` من `tenant_context_pg_session.js`).

النتيجة: `current_setting('app.tenant_id', true)` يرجع NULL → `tenant_id = NULL` → **لا صفوف**. ودور التطبيق `nama_medical_app` غير superuser وNOBYPASSRLS، فلا يتجاوز السياسة.

---

## 2. الدليل (قراءة فقط من الإنتاج)

| القياس | القيمة |
| ------ | ------ |
| `patients` كـ superuser (يتجاوز RLS) | 3 صفوف |
| `patients` كما يراها التطبيق `nama_medical_app` | **0 صفوف** |
| `invoices` كما يراها التطبيق | **0 صفوف** |
| `patients` كما يراها التطبيق **بعد** `set_config('app.tenant_id','1')` | **3 صفوف** (يعود الظهور) |

> الخلاصة: FORCE RLS تحجب بيانات حقيقية عن التطبيق على الإنتاج. الإصلاح المثبت اتجاهه: ضبط `app.tenant_id` لكل طلب.

---

## 3. الأثر

- **حالي**: الجداول الـ13 (المرضى، الفواتير، المواعيد، المختبر/الأشعة... إلخ) ترجع **صفراً من الصفوف** للتطبيق على الإنتاج. لم يظهر الضرر بعد لأن الإنتاج حديث العبور (بيانات seed فقط: 3 مرضى/3 فواتير) ولا يوجد استخدام سريري فعلي.
- **لماذا لم تكشفه المراحل 105-107**: فحوص المراقبة أصابت `/api/health` فقط (لا يقرأ جداول مستأجرين)، فمرّت بنجاح بينما قراءة البيانات الفعلية مكسورة.
- **على Wave 2B**: إضافة FORCE RLS إلى blood_bank/approvals/package_sessions يوسّع نفس الكسر.

---

## 4. سبب إيقاف Wave 2B

- تشغيل الـ DDL المعتمد سيطبّق إعداداً يجعل التطبيق لا يرى بيانات هذه الجداول (نفس حالة الـ13).
- الإصلاح الحقيقي (ربط `app.tenant_id`) **مفقود** وهو شرط مسبق لأي RLS فعّالة.
- التزاماً بقواعد المهارة: "لا تكسر production"، "إيقاف التنفيذ فوراً عند أي فشل"، وعدم اعتبار إعداد مكسور نجاحاً.

## 5. الحل الموصى به (قبل أي RLS إضافية)

### الأولوية القصوى (P0): إصلاح ربط سياق المستأجر على مستوى DB
الخيار الموصى به **A — ربط `app.tenant_id` لكل طلب**:
1. إضافة طبقة وصول DB تضبط سياق المستأجر قبل كل استعلام محمي:
   - إمّا استخدام `withTenantTransaction` (الموجودة في `tenant_context_pg_session.js`) في المسارات الحساسة، تنفّذ `SET LOCAL app.tenant_id = $tenant` داخل معاملة، أو
   - middleware يأخذ اتصالاً من الـ pool لكل طلب ويضبط `app.tenant_id` ثم يحرّره (مع إعادة الضبط لتفادي تسرّب السياق بين الطلبات في الـ pool).
2. بعد الربط: التحقق أن الجداول الـ13 ترجع بيانات المستأجر الصحيحة (`patients` يعود ليُظهر 3) وأن العزل يعمل (مستأجر آخر لا يرى).
3. ثم — وفقط ثم — توسيع FORCE RLS إلى blood_bank/approvals/package_sessions (Wave 2B) عبر الـ SQL الجاهز.

### بدائل (أقل تفضيلاً)
- **B**: جعل السياسات متسامحة عند غياب الـ GUC (`USING (current_setting('app.tenant_id', true) IS NULL OR '' = current_setting(...) OR tenant_id = ...)`) — يعيد ظهور البيانات لكنه يجعل RLS بلا أثر عند عدم ضبط الـ GUC (يبقى العزل على مستوى التطبيق فقط). حل مؤقت لا يحقق عزلاً على مستوى DB.
- **C**: منح `nama_medical_app` صلاحية BYPASSRLS — **مرفوض** (يلغي RLS كلياً).

> العزل على مستوى التطبيق (`WHERE tenant_id=$N`) سليم ومُختبَر عبر Waves؛ لكن طبقة RLS الحالية تحجب بدل أن تُكمّل. يجب إصلاح الربط أولاً.
