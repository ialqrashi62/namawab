# تقرير تنفيذ المرحلة التمهيدية لعزل المستأجرين (Tenant Isolation Foundation Implementation Report)

يوفر هذا التقرير تفاصيل فنية متكاملة حول تنفيذ حجر الأساس لعزل المستأجرين والمنشآت في نظام **نما الطبي** على مستويي قاعدة البيانات وخادم التطبيق بشكل تدريجي وآمن.

---

## 1. الملخص التنفيذي (Executive Summary)

* **اسم المرحلة**: تنفيذ أساس عزل المستأجرين (Tenant Isolation Foundation Implementation)
* **تاريخ الإنجاز**: 2026-06-15
* **الحالة**: مكتملة بنجاح (`MEDICAL_TENANT_ISOLATION_FOUNDATION_IMPLEMENTATION_COMPLETED`)
* **قاعدة البيانات**: تم تعديل المخطط الهيكلي محلياً وإضافة الأعمدة والـ Seed الافتراضي بنجاح دون المساس بالإنتاج.
* **الأمان والعزل**: تم تطبيق تصفية البيانات وفق المستأجر على مسارين تجريبيين بشكل آمن ودون التسبب بكسر المسارات القائمة.

---

## 2. نطاق المرحلة ولماذا لم يتم تنفيذ العزل الكامل دفعة واحدة

* **نطاق المرحلة**:
  1. إنشاء جداول الأساس الحاكمة للمستأجر والمنشأة والفروع.
  2. إدراج Seed افتراضي لضمان تشغيل النظام في بيئة التطوير دون توقف.
  3. تحديث مسار تسجيل الدخول والجلسة لاستيعاب معطيات المستأجر والفرع.
  4. إنشاء دوال برمجيات الوساطة والفلترة التمهيدية.
  5. عزل مساري المرضى والفواتير تجريبياً.
* **لماذا لم يُنفذ العزل الكامل دفعة واحدة**:
  * يحتوي النظام على **135 جدولاً** وأكثر من **150 مسار API**. التعديل الشامل والدفعة الواحدة في بيئة حرجة كالنظام الطبي يرفع من احتمالية الأخطاء وكوارث تداخل البيانات أو كسر العمليات الطبية القائمة. لذلك اعتمدنا أسلوب **التطوير والترحيل التدريجي (Safe Progressive Migration)** لضمان الاستقرار الكلي والتثبت التدريجي.

## 4. البنية والتعديلات الهيكلية لقاعدة البيانات (DB Changes)

### الجداول المضافة:
تم إدراج جداول التحكم بالعزل التالية:
1. `tenants` (المستأجرين)
2. `facilities` (المنشآت الطبية)
3. `branches` (الفروع الجغرافية)
4. `departments` (الأقسام الطبية والتشغيلية)
5. `user_tenants` (خرائط الموظفين والمستأجرين)
6. `user_facilities` (خرائط فروع الموظفين النشطة)
7. `tenant_settings` (إعدادات المستأجر المنعزلة)

### Seed الافتراضي المعتمد (Idempotent Seed):
تم إدراج السجلات الافتراضية التالية لضمان توافق النظام عند الترقية:
* **Tenant ID = 1**: `Nama Medical Default Tenant` (subdomain: `default`)
* **Facility ID = 1**: `Default Medical Facility` (tax_number: `300000000000003`)
* **Branch ID = 1**: `Main Branch` (address: `Riyadh, Saudi Arabia`)
* **المسؤول (Admin)**: تم ربطه تلقائياً بـ `tenant_id = 1` و `facility_id = 1` و `branch_id = 1` في جدولي العلاقات `user_tenants` و `user_facilities`.
* **مزامنة عدادات المتسلسلات**: تم تنفيذ `setval` بعد الإدخال لضمان عدم حدوث تعارض للمعرفات في الإدخالات التلقائية المستقبلية.

### مهاجرة الأعمدة والـ Backfill:
* تم إضافة الحقلين `tenant_id` و `facility_id` كأعمدة **مفتوحة وقابلة للملء (Nullable)** في الجداول المستهدفة لتجنب كسر العمليات الجارية.
* تم تشغيل سكربت تحديث (Backfill Update) لتعيين القيمة `1` لجميع السجلات القديمة الفراغية في جدولي `patients` و `invoices` لضمان ربطها بالهيكل الجديد.
* تم عمل معالجة استباقية لجدول الفروع `branches` القائم مسبقاً في قاعدة بيانات النظام بإضافة الحقل `facility_id` له وتحديثه.

## 5. برمجيات الوساطة والأنماط المضافة (Middleware & Helper Functions)

تم إنشاء وتجهيز المكونات البرمجية التالية في `server.js`:

1. **`getRequestTenantContext(req)`**:
   * تقوم باستخراج سياق المستأجر والمنشأة من جلسة المستخدم مع دعم الـ Fallback التلقائي للقيمة `1` في بيئات التطوير غير الإنتاجية لتبسيط العمل الفني والاختبار المحلي.
2. **`requireTenantContext(req, res, next)`**:
   * تفرض وجود سياق مستأجر كشرط لإتمام الطلب، وترجع رمز الخطأ `400 Bad Request` في حال عدم ضبطه.
3. **`requireFacilityContext(req, res, next)`**:
   * تفرض وجود سياق مستأجر ومنشأة نشطة للطلب.
4. **`withTenantFilter(queryText, params, tenantId)`**:
   * نمط حقن معلمات الفلترة البرمجية بـ PostgreSQL لإدخال شرط المستأجر ديناميكياً.

## 6. المسارات المعدلة والمسارات المؤجلة

### المسارات المعدلة تجريبياً (Filtered APIs):
* **`GET /api/patients`**: تم تعديل مسار جلب المرضى والبحث ليقوم بالفلترة التلقائية والمطابقة بناءً على `tenant_id = user_tenant_id` لضمان تصفية نتائج المرضى الخاصة بكل مستشفى أو عيادة على حدة.
* **`GET /api/invoices`**: تم تعديل مسار جلب قائمة الفواتير ليفلتر الفواتير بناءً على المستأجر المرتبط بالموظف الحالي.

### المسارات المؤجلة للمراحل القادمة (Deferred APIs):
* بقية المسارات الـ 130+ للعلامات الحيوية، والوصفات الطبية، وطلبات المختبر والأشعة، والتنويم وغيرها، تم إبقاؤها بدون تصفية وبدون تعديل لضمان عدم تعطل العمليات السريرية واستكمال الهجرة تدريجياً.

## 8. المخاطر المتبقية (Remaining Risks)

1. **عدم تغطية باقي المسارات (Partial API Scoping)**:
   * لا تزال واجهات البرمجة الأخرى (كالسجلات الطبية والمواعيد) مفتوحة وغير مفلترة بـ `tenant_id` مما يبقي مخاطر تسريب البيانات قائمة للواجهات غير المغطاة.
2. **عدم فرض RLS (No RLS Yet)**:
   * لم يتم تفعيل سياسات PostgreSQL RLS لضمان عدم كسر استقرار الكود.
3. **الحاجة إلى اختبارات تداخل البيانات (Cross-Tenant Leakage Tests)**:
   * الحاجة لإنشاء واختبار هويات متعددة للتحقق من عدم تسرب البيانات السريرية في مسارات APIs.
