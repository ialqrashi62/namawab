# تدقيق الأداء (Performance Audit)

> التاريخ: 2026-06-20 | فحص ثابت للكود + ملاحظات تشغيلية (لا load testing مُنفَّذ).

## 1. ملاحظات معمارية مؤثّرة على الأداء
| البند | الأثر | التوصية |
| ----- | ----- | ------- |
| **wrapper لـ pool.query يحجز اتصالاً لكل استعلام عند وجود tenant context** | اتصال/تحرير لكل query (P0 binding) — تكلفة عند الحمل العالي | قياس تحت حمل؛ التفكير بـ per-request connection (اتصال واحد للطلب) بدل per-query |
| `server.js` monolith ~7200 سطر، 370 مسار | تحميل/صيانة | تقسيم تدريجي (لا يؤثر runtime مباشرة) |
| `activeSessions` Map في الذاكرة | يكسر التوسّع الأفقي + تسرّب ذاكرة محتمل | نقل لـ Redis |
| لا pagination ظاهر على الجداول الكبيرة | تحميل صفوف كثيرة | pagination + lazy load + حد صفوف |
| لا caching للقراءات الثقيلة (عدا الجلسات + cache نوع المنشأة 60s) | حمل DB | cache للقراءات المرجعية/اللوحات |
| لا job queue للمهام الثقيلة (تقارير/إخطارات) | حظر دورة الطلب | طابور خلفي |

## 2. قاعدة البيانات
- فهارس `tenant_id` المركّبة موجودة على الجداول الأساسية (جيد). جداول Class A تحتاج فهارس عند إضافة tenant_id.
- لا N+1 واضح في المسارات المفحوصة (استعلامات مباشرة parameterized)، لكن لوحات التجميع (dashboard/reports) تحتاج مراجعة تكلفة الاستعلام.

## 3. التشغيل
- PM2 مستقر (الإنتاج ~20-105MB سابقاً). Redis للجلسات. لا مراقبة/تنبيه آلي (مذكور في GLOBAL_AUDIT_07).

## 4. بنود تحتاج قياس فعلي (لم يُنفَّذ — يتطلب أدوات/بيئة)
- زمن استجابة المسارات الثقيلة (بحث المرضى، تقويم المواعيد، لوحات التحليلات).
- أثر wrapper الاتصال-لكل-query تحت تزامن عالٍ.
- حجم bundle الواجهة (app.js ضخم، بلا bundling/tree-shaking).
- نمو السجلات/القرص.
