# خطة طرح وتفعيل متجر الجلسات الموزع Redis للإنتاج (Production Redis & Session Rollout Plan)
## نظام نما الطبي (NamaMedical) - مرحلة التخطيط والتحقق

توثق هذه الخطة المعايير الأمنية والتشغيلية المعتمدة لنشر وربط خادم الويب Node.js بمتجر جلسات Redis الموزع والآمن في بيئة الإنتاج الفعلي.

---

### 1. بنية وتهيئة خادم Redis للإنتاج (Redis Architecture)

* **خادم Redis إلزامي ومحمي في الإنتاج**: 
  * يعتبر استخدام Redis كمتجر جلسات موزع شرطاً إلزامياً وأساسياً لتشغيل النظام في بيئة الإنتاج. يمنع تشغيل النظام إنتاجياً بدونه.
  * يجب حظر الاتصال بالمنفذ `6379` للعموم، وحصر الاتصال عبر عناوين الشبكة الداخلية المؤمنة (Private IP) أو إعداد جدار حماية يقيد الوصول لخادم التطبيق فقط.
  * إلزام تفعيل المصادقة بكلمة مرور معقدة عبر التكوين `requirepass` في ملف `redis.conf`.
* **متغيرات البيئة المطلوبة (Required Environment Variables)**:
  * يتم تغذية الكود بالمتغيرات التالية عند البدء وتجنب كتابتها صراحة في الكود (وبدون قيم صلبة):
    * `REDIS_HOST`: عنوان الخادم (مثال: `redis-prod.nama.internal`).
    * `REDIS_PORT`: منفذ الاتصال (الافتراضي `6379`).
    * `REDIS_PASSWORD`: كلمة مرور الاتصال بـ Redis.

---

### 2. إعدادات الجلسات وكوكيز الأمان (Session & Cookie Configuration)

* **أمان كوكيز الجلسة في ملف `server.js`**:
  * `httpOnly: true`: مفعلة لمنع سرقة معرف الجلسة برمجياً.
  * `sameSite: 'lax'`: لحماية المستخدمين من هجمات CSRF.
  * `secure: true`: **إلزامية** للإنتاج لضمان عدم إرسال الكوكيز إلا عبر قنوات مشفرة ببروتوكول HTTPS.
* **الوسيط العكسي (Reverse Proxy)**:
  * تفعيل `app.set('trust proxy', 1)` في Express ليتمكن الخادم من الثقة بالترويسات الواردة من Nginx ومعالجة سمة `secure` للكوكيز بشكل صحيح.

---

### 3. سياسة التراجع والإنذار عند الأعطال (Strict Redis & Fallback Policy)

* **حظر التراجع الصامت إلى MemoryStore في الإنتاج**:
  * التراجع التلقائي لـ `MemoryStore` **مقبول فقط** في بيئة التطوير والـ Staging/Rehearsal لتسهيل العمل دون حاويات، أو كمسار طوارئ أخير معزول غير إنتاجي.
  * يمنع منعاً باتاً اعتبار النظام جاهزاً للإنتاج (`Production-ready`) في حال استمرار عمله على `MemoryStore`.
  * لا يوجد تراجع صامت في بيئة الإنتاج. أي فشل في الاتصال بـ Redis يجب أن يظهر كخطأ حرج ويوقف تشغيل النظام فوراً لطلب التدخل المباشر.
* **سياسة اتخاذ القرار عند فشل الاتصال (Decision Matrix)**:
  * **قبل النشر**: في حال فشل اختبار الاتصال بـ Redis قبل البدء بالتنفيذ، يتم إلغاء النشر فوراً وتثبيت القرار كـ `CURRENT_GO_DECISION: NO_GO_FOR_NOW`.
  * **أثناء/بعد النشر**: في حال تعثر خادم الويب في الاتصال بـ Redis أثناء التشغيل في الإنتاج، يتم تفعيل سياسة إيقاف خط الإنتاج فوراً (Stop-The-Line) ثم تشغيل التراجع التلقائي (Rollback) للالتزام المستقر السابق، أو تفعيل خطة الطوارئ المعتمدة فوراً.

---

### 4. خطة التراجع والاختبار (Rollback & Testing Plan)

* **خطة التراجع (Rollback Path)**:
  1. إيقاف خادم الويب مؤقتاً عبر PM2.
  2. تعطيل متغيرات البيئة الخاصة بـ Redis في تكوين خادم PM2.
  3. إعادة تشغيل الخادم للعودة للالتزام المستقر السابق.
* **الاختبار بعد النشر**:
  * تشغيل فحص محاكاة تسجيل الدخول والتحقق من أن معرف الجلسة يتم إدراجه في Redis بنجاح عبر أداة `redis-cli KEYS "nama_session:*"`.

---

### 5. الخلاصة وحالة العبور (Gate Conclusion)

* **حالة بوابة التخطيط لـ Redis**: **PASS** (تم صياغة السياسة الصارمة لإلزامية Redis وحظر Fallback في الإنتاج بنجاح).
* **التوصية**: الانتقال لتصحيح بقية تقارير بوابة الموافقة.

**القرار**: تم التحقق والاعتماد بنجاح (**Gate 4: PASS**).
