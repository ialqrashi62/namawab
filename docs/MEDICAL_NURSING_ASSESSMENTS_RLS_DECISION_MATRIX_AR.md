# تقرير مصفوفة قرارات تفعيل RLS - موديول التقييمات التمريضية (RLS Decision Matrix)
## نظام نما الطبي (NamaMedical) - بيئة Staging

يوثق هذا التقرير قرارات وتصنيفات تفعيل Row-Level Security (RLS) لجدول التقييمات التمريضية وتحديد الحالة الأمنية المطلوبة للالتزام بمعايير العزل وحماية بيانات المرضى.

---

### 1. جدول تصنيف القرارات الأمنية لجدول التقييمات (RLS Decision Table)

| اسم الجدول | الحالة الحالية للأعمدة | وجود سجلات NULL | القرار الأمني المعتمد (RLS Decision) | المبرر الفني وتوصية المرحلة القادمة |
| :--- | :---: | :---: | :---: | :--- |
| `nursing_assessments` | ناقصة (تفتقر لـ `tenant_id` و `facility_id`) | لا يوجد (0 سجلات) | **ENABLE_AFTER_SCHEMA_CHANGE** | لا يمكن تفعيل RLS بقاعدة البيانات حالياً دون إضافة الأعمدة الحيوية. يتم الاعتماد حالياً على حماية الـ API، وسيوجه تفعيل RLS فور إتمام الهجرة الهيكلية (Gate 5). |

---

### 2. مراجعة بدائل وخيارات العزل الفنية (Isolation Alternatives Assessment)

1. **الخيار الأول: تفعيل RLS بالاعتماد على JOIN (مرفوض)**:
   - *الفكرة*: كتابة سياسة RLS تستعلم من جدول `patients` باستخدام `EXISTS`.
   - *العيوب*:
     - **الأداء**: بطء شديد في استرجاع السجلات عند نمو قاعدة البيانات.
     - **عمليات الإدخال (INSERT)**: ستفشل أو تصبح معقدة جداً لأن شرط `WITH CHECK` سيتطلب تتبع مفاتيح متقاطعة لا يمكن تحديدها بكفاءة قبل اكتمال الصف.
2. **الخيار الثاني: الحماية بالـ API فقط (مقبول مؤقتاً كمسكن)**:
   - *الفكرة*: فلترة الطلبات برمجياً في `server.js`.
   - *العيوب*: لا يحمي قاعدة البيانات في حال الوصول المباشر أو وجود ثغرات في الكود.
3. **الخيار الثالث: هجرة الهيكل وإضافة الأعمدة (الخيار المعتمد والموصى به)**:
   - *الفكرة*: إضافة `tenant_id` وتعبئة البيانات ثم تفعيل RLS المباشر.
   - *المزايا*: عزل أمني كامل بقاعدة البيانات، سهولة كتابة السياسات وسرعة الفهرسة والأداء.

---

### 3. خلاصة النتيجة (Conclusion)

* تم تصنيف القرار لجدول التقييمات التمريضية كـ **ENABLE_AFTER_SCHEMA_CHANGE**.
