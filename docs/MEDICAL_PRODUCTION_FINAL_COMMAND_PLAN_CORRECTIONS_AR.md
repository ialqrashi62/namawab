# تقرير تصحيحات خطة الأوامر والسياسات النهائية للنشر (Final Command Plan & Policy Corrections Report)
## نظام نما الطبي (NamaMedical) - مرحلة التطهير والتحقق النهائية

يوثق هذا التقرير كافة التصحيحات والمراجعات الأمنية والتشغيلية المعتمدة لحل الملاحظات المانعة لبوابة الموافقة النهائية للإنتاج، وبالأخص تصحيح سياسة متجر الجلسات Redis، وتصحيح مسارات أوامر SQL، وترتيب الانتقال في الدلائل.

---

### 1. تصحيح سياسة Redis و MemoryStore للإنتاج (Redis & Session Store Policy)

تمت صياغة سياسة صارمة وغير قابلة للتأويل لإلزامية خادم Redis وحظر الميموري ستور في بيئة الإنتاج:
* **خادم Redis إلزامي تماماً**: يعتبر استخدام Redis متطلباً إجبارياً للتشغيل في بيئة الإنتاج الفعلي.
* **حظر MemoryStore**: يمنع منعاً باتاً تشغيل النظام إنتاجياً باستخدام `MemoryStore` كوضع تشغيل عادي أو fallback مقبول في الإنتاج. التراجع للميموري ستور مقبول فقط في بيئات التطوير والـ Staging/Rehearsal أو كحالة تطوير غير إنتاجية.
* **السياسة عند الأعطال (Incident Policy)**:
  - **إذا فشل Redis قبل النشر**: يتم إيقاف النشر فوراً وتثبيت القرار كـ `NO_GO_STOP`.
  - **إذا فشل Redis أثناء أو بعد النشر**: يتم تفعيل سياسة إيقاف خط النشر فوراً (`STOP_THE_LINE`) ثم تشغيل التراجع التلقائي (`ROLLBACK`) للالتزام المستقر السابق، أو تفعيل خطة الطوارئ (Incident Plan).
  - لا يتم اعتبار النظام جاهزاً للإنتاج (`Production-ready`) إذا كان متجر الجلسات يعمل على `MemoryStore`.
  - لا يوجد fallback صامت في بيئة الإنتاج الفعلي.

**حقول تكوين سياسة الإنتاج**:
```yaml
REDIS_REQUIRED_FOR_PRODUCTION: YES
MEMORYSTORE_ALLOWED_FOR_PRODUCTION: NO
REDIS_FAILURE_BEFORE_DEPLOY: NO_GO_STOP
REDIS_FAILURE_AFTER_DEPLOY: STOP_THE_LINE_ROLLBACK
```

### 2. تصحيح خطة أوامر التنفيذ والمسارات (Execution Commands & Paths Corrections)

تمت إعادة هيكلة وترتيب الأوامر التنفيذية لتفادي أخطاء المسارات، بحيث يتم تنفيذ جميع ملفات SQL البرمجية من جذر المشروع، مع الانتقال والعودة الصحيحة في أدلة الويب:

```bash
# 1. من جذر المشروع: جلب وتطبيق الالتزام المرشح النهائي للإنتاج وتحديث المجلد الفرعي
git fetch origin
git checkout e44b7be
git submodule update --init --recursive

# 2. الانتقال إلى مجلد تطبيق الويب لتثبيت التبعيات وبناء التنسيق
cd namaweb
npm install --production
npm run build:css
cd ..

# 3. تنفيذ استعلامات SQL من جذر المشروع مباشرة لضمان صحة المسارات وعدم انكسارها
psql -h localhost -p 5432 -U postgres -d nama_medical_web -f docs/sql/production_readiness_force_rls_up.sql
psql -h localhost -p 5432 -U postgres -d nama_medical_web -f docs/sql/production_readiness_force_rls_validate.sql

# 4. إعادة تشغيل التطبيق وتحديث المتغيرات البيئية من جذر المشروع
pm2 restart nama-web --update-env

# 5. فحص الصحة محلياً للتأكد من استجابة الخادم
curl -I http://localhost:3000/api/health
```

### 3. بوابات وفحوصات التحقق ما قبل التنفيذ (Pre-execution Verification Gates)

تم إقرار بوابات تحقق إلزامية صلبة قبل البدء بأي نشر للإنتاج، وفي حال فشل أي بوابة يتم **الإيقاف فوراً (STOP)**:
1. **التحقق من هاش نسخة الإطلاق**: مطابقة الالتزام الرئيسي المرشح للإنتاج مع الالتزام الفعال.
2. **التحقق من هاش المجلد الفرعي**: مطابقة هاش `namaweb` وتطابقه مع الالتزام المعتمد.
3. **التحقق من وصول خدمة Redis**: التأكد من أن منفذ خادم Redis متاح للاتصال دون طباعة قيم الأسرار.
4. **التحقق من أسماء متغيرات البيئة**: التحقق من وجود المتغيرات اللازمة دون طباعة قيمها.
5. **التحقق من مسار وصلاحيات النسخ الاحتياطي**: التأكد من وجود المجلد المخصص وأنه خارج تتبع Git.
6. **تنفيذ والتحقق من ملف النسخ الاحتياطي**: تشغيل أمر النسخ الاحتياطي والتأكد من نشوء ملف bak غير صفري الحجم.
7. **التحقق من الالتزام المستقر الأخير**: حفظ الهاش الحالي للتمكن من التراجع إليه.
8. **التحقق من اسم عملية PM2**: مطابقة اسم العملية PM2 لتكوين المشروع.
9. **التحقق من فحص الصحة قبل النشر**: التأكد من استجابة خادم الصحة بنجاح قبل البدء.
10. **التحقق من وجود ملفات SQL برمجياً**: التأكد من وجود ملفات SQL للتحديث والتراجع في مساراتها المطلوبة قبل التنفيذ.
