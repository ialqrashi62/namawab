# خطة إصلاح قاعدة البيانات وعزل المستأجرين (Database & Tenant Isolation Fix Plan)

توثق هذه الخطة الخطوات البرمجية والهيكلية النظريّة لإصلاح ثغرات أمان الجلسات والمصادقة، وتهيئة بنية قاعدة البيانات ونهايات واجهات البرمجة (APIs) للتحول الآمن إلى SaaS متعدد المستأجرين (Multi-tenant) دون تعطيل العمليات الطبية الجارية.

---

## المرحلة 1: إغلاق مخاطر تسجيل الدخول والجلسات (Auth & Session Hardening)
الهدف هو إغلاق الثغرات الأمنية الفورية المكتشفة في `server.js` المتعلقة بالجلسات وتسجيل الدخول:

1. **إصلاح سجل التدقيق (Audit Trail Fix)**:
   * تعديل استعلام الإدخال في الدالة `logAudit` ليتطابق مع أعمدة الجدول الفعلي `audit_trail`:
     * استبدال العمود `user_name` بـ `username`.
     * استبدال العمود `details` بـ `new_values` أو إضافة عمود `details TEXT` إلى الجدول عبر هجرة منفصلة.
2. **حظر كلمات المرور النصية الصريحة (Plaintext Fallback)**:
   * إلغاء مقارنة كلمات المرور بالصيغة الصريحة تماماً في مسار `/api/auth/login`.
   * فرض التحقق الحصري عبر `bcrypt.compare` لضمان عدم إمكانية استخدام أي كلمات مرور غير مشفرة.
3. **تأمين كوكيز الجلسات (Session Cookies Security)**:
   * تعديل إعدادات middleware الجلسة في `server.js` إلى:
     ```javascript
     cookie: {
         maxAge: 8 * 60 * 60 * 1000,
         httpOnly: true, // منع الوصول عبر Javascript لمنع هجمات XSS
         secure: process.env.NODE_ENV === 'production', // فرض HTTPS في الإنتاج
         sameSite: 'strict' // حماية ضد هجمات CSRF
     }
     ```
4. **تخزين الجلسات (Persistent Session Store)**:
   * استبدال مخزن الذاكرة الافتراضي بمخزن مستقر (مثل `connect-pg-simple` لحفظ الجلسات في جدول مخصص داخل PostgreSQL) لضمان استقرار الجلسات ودعم التوسع.

## المرحلة 2: إضافة نموذج Tenant/Facility نظرياً (Tenant & Facility Schema Design)
تصميم الجداول الحاكمة لهيكل SaaS متعدد المستأجرين في ملف هجرة (Migration Script) دون تنفيذ:

1. **إنشاء جدول المستأجرين `tenants`**:
   * لتسجيل الشركات الطبية المشتركة ونطاقاتها الفرعية ومستوى اشتراكها.
2. **إنشاء جدول المنشآت الطبية `facilities`**:
   * لتمثيل المستشفيات والمراكز الطبية والعيادات التابعة للمستأجر.
3. **إنشاء جدول العالاقات `user_tenant_roles`**:
   * لربط موظفي النظام بالمنشآت والفروع وتحديد صلاحياتهم الخاصة بكل فرع.
4. **إجراء التعديلات الهيكلية**:
   * إضافة قيود المفاتيح الخارجية والعلاقات المباشرة مع جدول `tenants` و `facilities`.

---

## المرحلة 3: تصميم tenant_id / facility_id للجداول الحساسة (Isolation Fields Inject)
تصميم الهيكل لإدراج حقول العزل وتعديل الجداول القائمة:

1. **تحديث الجداول الطبية والمالية والتشغيلية**:
   * إضافة عمود `tenant_id INTEGER` كحقل إلزامي لربط السجلات بصاحب الحساب السحابي.
   * إضافة عمود `facility_id INTEGER` كحقل إلزامي لربط السجلات بالفرع الذي تمت فيه العملية الطبية.
2. **تجهيز الفهارس المشتركة (Composite Indexes)**:
   * تصميم فهارس لتحسين سرعة الاستعلامات ومنع الفحص الكامل للجداول (Table Scans) مثل:
     * `CREATE INDEX idx_patients_tenant_id ON patients (tenant_id, id);`
     * `CREATE INDEX idx_invoices_tenant_id ON invoices (tenant_id, id);`
     * `CREATE INDEX idx_medical_records_tenant_id ON medical_records (tenant_id, id);`

---

## المرحلة 4: حماية واجهات البرمجة (APIs) بالفلاتر (API Query Isolation Filtering)
إعادة صياغة استعلامات SQL في `server.js` لمنع الاستعلام العام غير المقيد:

1. **تضمين الـ Middleware لعزل الطلبات**:
   * استخراج `tenant_id` من النطاق الفرعي (Subdomain) أو الجلسة المؤمنة وإرفاقه بكائن الطلب `req.tenantId`.
2. **تعديل استعلامات القراءة (SELECT)**:
   * تحديث كافة استعلامات `SELECT` لتشمل شرط المستأجر بصورة إجبارية:
     * مثال: `SELECT * FROM patients WHERE tenant_id = $1` بدلاً من `SELECT * FROM patients`.
3. **تعديل عمليات الإدخال والتعديل (INSERT / UPDATE)**:
   * حقن `tenant_id` تلقائياً في الطلبات الجديدة لضمان عدم إمكانية تزييف الهوية.
4. **تقييد واجهات الحذف وتطبيق الحذف المرن (Soft Delete)**:
   * تعديل مسار `DELETE /api/patients/:id` لاستخدام `UPDATE patients SET is_deleted = 1, deleted_at = CURRENT_TIMESTAMP WHERE id = $1 AND tenant_id = $2`.

## المرحلة 5: اختبارات منع تسريب البيانات (Data Leakage Prevention Tests)
بناء مجموعة اختبارات آلية للتحقق من سلامة العزل قبل النشر:

1. **اختبارات وحدة (Unit Tests) لواجهات البرمجة**:
   * إنشاء طلبات وهمية باستخدام مكتبات مثل `supertest` لمحاكاة وصول مستخدم من المستأجر "أ" لمعرف مريض ينتمي للمستأجر "ب" والتحقق من رجوع رمز الخطأ `403 Forbidden`.
2. **اختبارات أداء للتحقق من سرعة التصفية**:
   * تشغيل اختبارات ضغط للتحقق من كفاءة الفهارس المشتركة وعدم تأخر زمن الاستجابة مع نمو حجم البيانات العام في الجداول المشتركة.

---

## المرحلة 6: خطة migration آمنة (Safe Data Migration Execution)
خطوات ترحيل البيانات الحالية تدريجياً لضمان عدم التوقف:

1. **إنشاء المستأجر والفرع الافتراضي**:
   * ترحيل البيانات الحالية تحت معرف مستأجر افتراضي `tenant_id = 1` ومنشأة افتراضية `facility_id = 1`.
2. **تشغيل سكربت التحديث المجدول**:
   * تطبيق التغييرات على الجداول بالترتيب: إضافة الحقول الجديدة كـ `NULLABLE` أولاً، ثم ملء البيانات بالقيم الافتراضية، ثم تحويلها إلى `NOT NULL`.
3. **التحقق من البيانات الفاعلة**:
   * مراجعة تكامل الجداول الطبية والمالية بعد انتهاء الترحيل.

---

## المرحلة 7: خطة rollback لضمان الاستمرارية (Rollback Strategy)
نص للتراجع المباشر في حال فشل أي مرحلة من الهجرة:

1. **استعادة الحالة البرمجية**:
   * سحب إصدار الكود الجديد والرجوع للنسخة المستقرة السابقة عبر Git.
2. **عكس عمليات الترحيل في قاعدة البيانات**:
   * تشغيل سكربت عكسي يقوم بالتالي:
     ```sql
     -- مثال نظري لعكس التعديلات
     ALTER TABLE patients DROP COLUMN IF EXISTS tenant_id;
     ALTER TABLE medical_records DROP COLUMN IF EXISTS tenant_id;
     -- استعادة الجداول المالية والتشغيلية كما كانت
     ```
3. **استرجاع النسخ الاحتياطية**:
   * إذا تعذر العكس السلس، يتم استعادة ملف النسخة الاحتياطية الفيزيائية المأخوذة فوراً قبل البدء.
