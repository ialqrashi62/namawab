# تقرير تقوية وحماية واجهة البرمجة - الدفعة الثالثة (Batch 3 API Hardening Report)
## نظام نما الطبي (NamaMedical) - بيئة Staging

يوثق هذا التقرير التدابير والبرمجيات الأمنية التي تم تطبيقها لتقوية واجهات برمجة التطبيقات (API Routes) المرتبطة بالتنويم وإشغال الأسرة ضد ثغرات IDOR وحالات السباق (Race Conditions).

---

### 1. تقوية مسار خروج المريض (Discharge Endpoint Hardening)
* **المسار**: `PUT /api/admissions/:id/discharge`
* **الحماية من IDOR**:
  * فرض الـ middleware المعتمد `requireTenantScope` لاستخراج معرف المستأجر `tenantId` من الجلسة الآمنة حصرياً.
  * التحقق من ملكية طلب التنويم عبر الاستعلام:
    `SELECT id, bed_id, patient_id FROM admissions WHERE id = $1 AND tenant_id = $2 FOR UPDATE`
  * إذا كان التنويم يخص مستأجراً آخر، يتم إرجاع `404 Not Found` دون تسريب أي بيانات عن السجل.
* **حماية المعاملات والسباق (Transactions & Race Condition Prevention)**:
  * إدراج كافة العمليات (تعديل حالة التنويم لـ `Discharged` -> تحرير السرير لـ `Available` -> تعديل حالة المريض لـ `Discharged`) داخل معاملة قاعدة بيانات واحدة تبدأ بـ `BEGIN` وتنتهي بـ `COMMIT` أو تتراجع بـ `ROLLBACK`.
  * استخدام القفل الحصري `FOR UPDATE` على السجل المطلوب من جدول التنويم لمنع حدوث خروج مكرر أو سباق في تحرير الأسرة.

---

### 2. تقوية مسار إحصاء الأسرة (Beds Census Endpoint Hardening)
* **المسار**: `GET /api/beds/census`
* **الحماية والفلترة**:
  * عزل جلب الأجنحة بـ `tenant_id` المعالج من الجلسة.
  * عزل جلب الأسرة والتنويم النشط المرتبط بها عبر دمج الجداول `JOIN` وتمرير معرف المستأجر كمعامل استعلام آمن:
    `WHERE b.tenant_id = $1`
  * منع حساب مؤشرات الإشغال والقدرة الاستيعابية بشكل عام، وربطها بنطاق المستأجر الحالي لتجنب تسريب أي إحصاءات.
