# تقرير المرحلة 2D — H-5: حراسات القيد المحاسبي (GL Guard Code-Only)

**المشروع:** NamaMedical / الطبيب
**الفرع:** `audit/phase-1-critical-remediation`
**التاريخ:** 2026-06-27
**النوع:** تنفيذ حراسات كود فقط — لا تفعيل محاسبة — لا journal entries — لا DB — لا DDL — لا deploy

---

## 1. الهدف

تنفيذ حراسات (guards) على مستوى الكود تمنع أي ترحيل محاسبي (GL posting) غير منضبط، وتثبت عبر اختبارات مؤتمتة أن الربط المستقبلي بين الفوترة/الدفع/الاسترداد ودفتر اليومية لن يحدث إلا بشروط صارمة — بينما تبقى المحاسبة معطّلة (OFF).

---

## 2. ما تم تنفيذه

### 2.1 حراسات سياسة الترحيل (`finance_engine.js`)

أُضيفت ثلاث دوال نقية (pure, DB-free) إلى محرك المالية:

| الدالة | الغرض |
|--------|-------|
| `validateSourceDocument(doc)` | التحقق من وجود وصلاحية المستند المصدري (`source_type`, `source_id`, `event_type`) |
| `idempotencyKey(source_type, source_id, event_type)` | اشتقاق مفتاح تكرار حتمي لمنع القيود المزدوجة |
| `checkPostingPreconditions(accountingEnabled, tenantId, sourceDoc, lines)` | حارس رئيسي يتحقق من **جميع** الشروط قبل أي قيد |

### 2.2 الشروط التي يفرضها الحارس الرئيسي

1. **علم المحاسبة مفعّل** — `ACCOUNTING_POSTING_ENABLED=1` (حالياً OFF).
2. **نطاق المستأجر موجود** — `tenant_id` من السياق الخادمي، لا من العميل.
3. **مستند مصدري صالح** — `source_type` من القائمة المعتمدة، `source_id` رقم صحيح موجب (إلا للقيود اليدوية)، `event_type` صالح.
4. **قيد متوازن** — مجموع المدين = مجموع الدائن (عبر `validateBalancedEntry`).
5. **مفتاح تكرار قابل للاشتقاق** — لمنع القيد المزدوج لنفس الحدث المالي.

أي فشل في أي شرط يمنع الترحيل بالكامل (fail-closed).

## 3. ما لم يتم

- ❌ لم يتم ربط invoice/payment/refund تلقائياً بدفتر اليومية.
- ❌ لم يتم تفعيل `ACCOUNTING_POSTING_ENABLED`.
- ❌ لم يتم إنشاء أي قيد يومية (journal entries = 0).
- ❌ لم يتم تغيير DB schema أو DDL أو migrations.
- ❌ لم يتم الاتصال بـ ZATCA أو NPHIES.
- ❌ لم يتم النشر أو إعادة تشغيل PM2.
- ❌ لم يتم Push.
- ❌ H-9/H-10 (RLS) و DR خارج النطاق.

---

## 4. لماذا بقيت المحاسبة OFF

- بوابة `e10PostingEnabled()` تعتمد على `process.env.ACCOUNTING_POSTING_ENABLED`.
- الحالة الافتراضية والحالية: **OFF**.
- تفعيل المحاسبة يتطلب:
  1. إعداد دليل الحسابات (Chart of Accounts) من المالك.
  2. قرار سياسة الترحيل (تلقائي أو يدوي).
  3. موافقة صريحة من المالك.
- الحراسات المضافة تضمن أنه حتى لو فُعّل العلم مستقبلاً، لن يمر أي ترحيل بلا شروط كاملة.

---

## 5. لماذا بقيت journal entries = 0

- لم يُضف أي hook يُنشئ قيوداً تلقائية.
- الحراسات هي **policy validators** فقط — لا تكتب في DB.
- الربط الفعلي يتطلب مرحلة تنفيذ لاحقة بموافقة المالك.

---

## 6. سياسة العكس (Reversal Policy)

- القيد المرحّل (POSTED) **غير قابل للتعديل** — immutable by design.
- التعديل يتم فقط عبر قيد عكسي (reversal entry) يقلب المدين/الدائن.
- `buildReversalLines()` تُنتج قيداً عكسياً متوازناً ومعلّماً بـ `notes='Reversal'`.

## 8. المتطلبات المتبقية لإغلاق H-5 بالكامل

1. **قرار المالك:** هل يُفعّل الترحيل المحاسبي؟
2. **إعداد دليل الحسابات:** أرقام الحسابات وهيكلها.
3. **سياسة الترحيل:** تلقائي (عند إصدار الفاتورة) أو يدوي (DRAFT ثم POST).
4. **اختبارات تكامل:** مع DB فعلي بعد التفعيل.
5. **تسوية:** بناء تقارير تسوية الفواتير مقابل القيود.
