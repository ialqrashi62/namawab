## 5. مقارنة الخيارات

### Option A — Purge + force-push على الـrepo العام الحالي
- **الفوائد:** إبقاء نفس URL/issues/stars؛ إزالة الأسرار من التاريخ المعاد كتابته.
- **المخاطر:** عالية — يتطلب إعادة كتابة **~20 فرعاً** و force-push لها جميعاً؛ **forks/clones/PR-refs/caches تحتفظ بالـcommits القديمة** (GitHub يُبقي commits غير المُشار إليها قابلة للوصول بالـSHA، والforks تحتفظ بها)؛ يكسر تاريخ كل المتعاونين (re-clone إجباري)؛ يتطلب `filter-repo`/BFG (rewrite) + نسخة احتياطية كاملة؛ قد يلزم **GitHub Support** لتطهير caches/forks. لا يضمن إزالة كاملة بسبب الـforks.
- **الحكم:** ثانوي فقط — إن أصرّ المالك على إعادة استخدام الـrepo العام.

### Option B — Remote خاص نظيف جديد (موصى به)
- **الفوائد:** بداية نظيفة، بلا نقل تاريخ ملوّث، تحكّم كامل بالـvisibility (خاص منذ الإنشاء).
- **الطريقة:** المالك يُنشئ repo **خاص** جديد (مثل `NamaMedical-namaweb-clean`)؛ يُجهَّز snapshot محلي نظيف من **الشجرة الحالية فقط**؛ يُرفَع فرع نظيف إلى الـremote الخاص **بعد بوابة push منفصلة**.
- **orphan مقابل filtered:** الأنظف = **orphan branch** (جذر جديد = الشجرة الحالية النظيفة، بلا تاريخ) → نظيف تماماً لكن يفقد سجلّ الـcommits؛ أو **filtered history** (يحفظ التاريخ ناقصاً الأسرار) لكنه **rewrite** = بوابة منفصلة (خارج هذا التمهيد). بما أن القيم محروقة، فقدان التاريخ في orphan مقبول (سجلّ التدقيق محفوظ في تقارير الجذر).
- **التقارير والـgitlink:** repo الجذر (الحوكمة) منفصل ويبقى. لو أخذ namaweb تاريخاً نظيفاً جديداً (orphan/filtered) ستتغيّر كل الـSHAs → **يلزم تحديث gitlink الجذر** إلى commit namaweb النظيف الجديد (خطوة تنسيق موثَّقة).
- **الـrepo العام القديم:** يُؤرشَف/يُحوَّل خاصاً بعد التحقق.
- **الحكم:** **التوصية الأساسية.**

### Option C — أرشفة/حذف الـrepo العام
- **الفوائد:** إزالة الظهور العلني كلياً؛ أبسط احتواء.
- **المخاطر:** يفقد issues/visibility/history؛ الـforks قد تبقى بعد الحذف؛ يلزم **تصدير الأدلة** (سجلّ التدقيق) قبل الحذف؛ لا يوفّر بذاته remote عاملاً (يُدمَج مع B).
- **الحكم:** **مكمِّل لـB** (أرشفة العام بعد إقامة الخاص النظيف)؛ الحذف يتطلب تصدير أدلة أولاً.

### Option D — إبقاء العام كما هو
- **HIGH RISK / NOT RECOMMENDED:** قيم ميتة تبقى مرئية علناً + تاريخ ملوّث يُعاد استخدامه + قلق امتثال/سمعة لنظام طبي. غير مقبول بلا سبب مالك واضح.

## 6. التوصية النهائية

**Option B (أساسي) + Option C (مكمِّل)، و Option A ثانوي فقط، و Option D مرفوض.**
- أقِم **remote خاص نظيف** من الشجرة الحالية، ثم **أرشِف/حوِّل العام خاصاً**.
- استخدم force-push/purge (A) فقط إذا أصرّ المالك على إعادة استخدام الـrepo العام نفسه — كقرار منفصل لاحق.

## 7. الخطة الموصى بها (owner-run، بوابات منفصلة، غير مُنفَّذة هنا)

1. **فوراً:** المالك يجعل `namawab` العام **private أو archived** من GitHub UI (يوقف الظهور العلني للقيم الميتة).
2. المالك يُنشئ repo **خاص** جديد واضح الاسم (`NamaMedical-namaweb-clean`).
3. تجهيز snapshot محلي نظيف من الشجرة الحالية فقط (**orphan branch**؛ أو filtered history عبر بوابة rewrite منفصلة).
4. رفع الفرع النظيف إلى الـremote الخاص **فقط بعد بوابة push منفصلة** (تحقق + موافقة).
5. **عدم** push للـcommits الحالية إلى الـremote العام القديم.
6. بعد التحقق: **أرشفة/حذف** العام (مع تصدير أدلة)، أو — إن لزم إعادة استخدامه — force-push للتاريخ المُطهَّر فقط (قرار منفصل).
7. **تحديث gitlink الجذر** إلى commit namaweb النظيف + توثيق كامل.
