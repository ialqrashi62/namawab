# جرد الأسطح البرمجية الحالية المتعلقة بالمدفوعات والفوترة (Jumanasoft Billing Surface Inventory)

* **المشروع:** منصة نما الطبية (NamaMedical ERP)
* **المرحلة:** تصميم أساس محول الفواتير (PHASE_BILLING_ADAPTER_DESIGN_ONLY_CANDIDATE)
* **البوابة:** البوابة 1.1 — جرد الكود المتاح (Gate 1.1 — Existing Code Inventory)
* **الحالة:** تم الجرد والتوثيق بنجاح (SUCCESS) ✅

---

## 1. حصر الكود والملفات المتعلقة بالمدفوعات حالياً

تم فحص الكود الحالي للمشروع ورصد الأسطح البرمجية التالية المرتبطة بالمدفوعات:

1. **محول مدفوعات المرضى الحالي (`payment_adapter.js`):**
   * *الملف:* `namaweb/payment_adapter.js`
   * *الوظيفة:* مخصص لمعالجة مدفوعات فواتير المرضى والخدمات الطبية لعيادات التعدادية باستخدام بوابة دفع Moyasar (مدى، فيزا، ماستركارد، Apple Pay).
   * *صمام الأمان:* يدعم التحويل التلقائي لـ Sandbox/Mock عند تشغيل وضع staging أو غياب المفاتيح.
2. **فحص المفاتيح والرموز التشفيرية (API Keys Scan):**
   * لا يوجد أي مفاتيح تشفير أو رموز سرية صريحة أو صلابة (Hardcoded) تخص Stripe أو Moyasar أو HyperPay داخل الكود. يتم قراءتها بأمان عبر متغيرات البيئة (`process.env.MOYASAR_SECRET_KEY`).
3. **جداول الاشتراكات وباقات الـ SaaS:**
   * لا توجد جداول حقيقية مفعلة في قاعدة البيانات لمعالجة اشتراكات باقات المستأجرين (Starter, Growth, Enterprise). خطط الـ SaaS والربط تتم برمجياً وعبر الخطط المبدئية فقط.
4. **بوابات الدفع والـ Webhooks التلقائية للـ SaaS:**
   * لا تتوفر أي مسارات (Routes) أو نقاط نهاية (Endpoints) حية لاستقبال إشعارات الدفع أو معالجة اشتراكات التعدادية.

---
**الخلاصة:** الواجهات الحالية تقتصر على معالجة مدفوعات المرضى الفردية طبياً، وهناك حاجة لتصميم محول فوترة مستقل وخاص بالاشتراكات (SaaS Billing Adapter).
