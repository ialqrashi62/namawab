# الدفعة 2 — تقرير المراجعة الأمنية (GATE 9)

**التاريخ:** 2026-06-30 · الفرع: `feature/jumanasoft-auth-rbac-hardening`.
**النطاق المُراجَع:** `rbac_guards.js` (جديد)، `server.js` (+27/-24 سطراً)، اختباران مُحدَّثان، `rbac_guards_test.js` (جديد).

## تحليل التغييرات الحسّاسة
1. **توحيد حارس الأدمن:** نُقل `role !== 'Admin'` من inline (3 مواضع) إلى middleware `requireTenantAdmin` يعمل **قبل** المعالج. نفس 403، نفس أسماء أحداث التدقيق (`BLOCKED_USER_CREATE`/`BLOCKED_USER_DELETE`/`BLOCKED_MFA_ADMIN_RESET`) عبر معاملات. المنطق العميق (آخر أدمن، حذف الذات، منع تصعيد الذات في PUT) **بقي دون مساس**.
2. **إصلاح `username` بالجلسة:** additive بحت. أصلح عطلاً كان يجعل حارس Super Admin يرفض **الجميع**. `/api/auth/me` صار يُرجع `username` الخاص بالمستخدم نفسه (غير حسّاس).
3. **حارس Super Admin خارجي موحّد:** طبقة دفاع إضافية بنفس هوية `super_admin.isSuperAdmin` (مصدر واحد) — لا تكرار منطق، لا كسر لاختبارات الدفعة 1 (28/28 سليمة).

## مخاطر متبقية (موثّقة، مقبولة)
- `requireCatalogAccess` يُبقي مطابقة فضفاضة (`manager`/`administrator`) — تُرك عمداً (القاعدة 7: لا تغيير بلا حاجة مُثبتة)؛ لا علاقة له بمسارات إدارة المستخدمين/المستأجرين.
- جلسات قائمة قبل النشر لن تحوي `username` حتى إعادة تسجيل الدخول — لا أثر إنتاجي (غير منشور، وSuper Admin غير مُفعّل). يُذكر في خطة التفعيل.
- صفحة Super Admin الساكنة (`/super-admin/*.html`) تُخدَم بلا حارس صفحة (الحماية على طبقة الـ API بـ 403؛ لا أسرار في HTML) — تحسين اختياري لدفعة لاحقة.
