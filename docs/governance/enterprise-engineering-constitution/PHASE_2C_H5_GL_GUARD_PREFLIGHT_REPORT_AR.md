## 1. الهدف

تحليل فجوة القيد المحاسبي العام (General Ledger) المنفصل عن دورة الفوترة والتحصيل والاسترداد الحالية، وتحديد مخاطر عدم وجود ربط تلقائي بين عمليات الفواتير/الدفع/الاسترداد وبين دفتر اليومية المحاسبي، وتصميم حل مقترح دون تنفيذه.

## 2. الوضع الحالي — مسارات مالية مكتشفة

### 2.1 مسار إنشاء الفاتورة (Invoice Creation)

| المسار | الملف | السطر |
|--------|-------|-------|
| `POST /api/invoices` | server.js | ~1005 |
| `POST /api/invoices/generate` | server.js | ~3391 |

**آلية العمل:**
- يتم حساب المبلغ والخصم وضريبة القيمة المضافة (15%) على الخادم (C-2/C-3).
- يتم إنشاء رقم فاتورة تسلسلي (`INV-YYYY-NNNNN`).
- يتم إدراج سجل في جدول `invoices` مع `tenant_id` و `facility_id`.
- يتم تسجيل عملية التدقيق عبر `logAudit`.
- **لا يوجد أي قيد محاسبي (journal entry) يُنشأ تلقائياً عند إصدار الفاتورة.**

### 2.2 مسار الدفع الكامل (Full Payment)

| المسار | الملف | السطر |
|--------|-------|-------|
| `PUT /api/invoices/:id/pay` | server.js | ~3426 |

**آلية العمل:**
- يتم التحقق من ملكية الفاتورة للمستأجر (IDOR prevention).
- يتم وضع علامة `paid=1` وتحديث `payment_method`.
- **لا يوجد أي قيد محاسبي يُنشأ عند تسجيل الدفع.**

### 2.3 مسار الدفع الجزئي (Partial Payment)

| المسار | الملف | السطر |
|--------|-------|-------|
| `PUT /api/invoices/:id/partial-pay` | server.js | ~11724 |

**آلية العمل:**
- المبلغ يُحسب بوحدات صغرى (هللات) لتفادي انحراف الأعداد العشرية.
- التحقق من أن المبلغ لا يتجاوز المستحق (`assertAmountWithinCap`).
- قفل الصف بالمعاملة (`FOR UPDATE`) لمنع سباق الدفع المزدوج.
- تحديث `amount_paid`, `balance_due`, `paid`.
- **لا يوجد أي قيد محاسبي يُنشأ.**

### 2.4 مسار الاسترداد (Refund)

| المسار | الملف | السطر |
|--------|-------|-------|
| `POST /api/invoices/:id/refund` | server.js | ~11762 |

**آلية العمل:**
- المبلغ القابل للاسترداد يُحسب على الخادم: `amount_paid - already_refunded`.
- يُنشأ سجل فاتورة جديد بمبلغ سالب (`service_type='Refund'`).
- رقم الاسترداد: `REF-YYYY-NNNNNN`.
- **لا يوجد أي قيد محاسبي يُنشأ.**
- التعليق الصريح في الكود: `No GL/journal/ZATCA/NPHIES (out of scope)`.

### 2.5 مسار إلغاء الفاتورة (Invoice Cancel)

| المسار | الملف | السطر |
|--------|-------|-------|
| `POST /api/invoices/cancel/:id` | server.js | ~10650 |

**آلية العمل:**
- وضع علامة `cancelled=1` مع سبب الإلغاء.
- **لا يوجد أي قيد محاسبي أو إشعار دائن (credit note) محاسبي.**

## 3. البنية التحتية المحاسبية الموجودة

### 3.1 محرك المالية (`finance_engine.js`)

وحدة نقية (pure module) بدون DB أو I/O تحتوي على:
- **التحقق من توازن القيد:** `validateBalancedEntry()` — يرفض القيد إذا مجموع المدين ≠ مجموع الدائن.
- **بناء قيود العكس:** `buildReversalLines()` — يقلب المدين/الدائن.
- **حساب ضريبة القيمة المضافة:** 15% KSA (من/إلى شامل الضريبة).
- **تقادم الذمم المدينة:** `ageInvoices()` — أربع شرائح (0-30, 31-60, 61-90, 90+).
- **ZATCA UBL + QR:** توليد XML و TLV/Base64 QR (بدون ختم حقيقي — placeholder).
- **حساب العملة بالوحدات الصغرى (هللات)** لتفادي انحراف الأعداد العشرية.

### 3.2 مسارات دفتر اليومية (Journal Routes) — موجودة لكن غير مفعّلة

| المسار | الوظيفة | الحالة |
|--------|---------|--------|
| `POST /api/finance/journal` | إنشاء قيد متوازن (DRAFT) | موجود ✓ |
| `POST /api/finance/journal/:id/post` | ترحيل القيد (DRAFT→POSTED) | **معطّل بالعلم** |
| `POST /api/finance/journal/:id/reverse` | عكس قيد مرحّل | **معطّل بالعلم** |
| `GET /api/finance/journal` | عرض القيود | موجود ✓ |
| `GET /api/finance/journal/:id` | عرض قيد + بنوده | موجود ✓ |
| `GET /api/finance/accounts` | دليل الحسابات | موجود ✓ |
| `POST /api/finance/accounts` | إنشاء حساب | موجود ✓ |
| `GET /api/finance/aging` | تقادم الذمم المدينة | موجود ✓ |
| `GET /api/finance/posting-status` | حالة التفعيل | موجود ✓ |
| `GET /api/finance/vouchers` | السندات | موجود ✓ |

### 3.3 علم التفعيل (Posting Gate)

```javascript
function e10PostingEnabled() {
    return /^(1|true|on|yes)$/i.test(
        String(process.env.ACCOUNTING_POSTING_ENABLED || '').trim()
    );
}
```

- **الحالة الافتراضية: OFF** — لا يمكن ترحيل أي قيد ما لم يُفعّل `ACCOUNTING_POSTING_ENABLED=1` في `.env`.
- **حالياً: OFF** — الحالة الإنتاجية لا تحتوي على هذا العلم مفعّلاً.

## 4. فجوات H-5 — التحليل

### 4.1 فجوة الربط بين الفوترة والقيد المحاسبي (Critical Gap)

| العملية المالية | قيد محاسبي تلقائي | الحالة |
|----------------|-------------------|--------|
| إنشاء فاتورة | ❌ لا يوجد | **فجوة** |
| دفع كامل | ❌ لا يوجد | **فجوة** |
| دفع جزئي | ❌ لا يوجد | **فجوة** |
| استرداد | ❌ لا يوجد | **فجوة** |
| إلغاء فاتورة | ❌ لا يوجد | **فجوة** |
| إغلاق يومي | ❌ لا يوجد | **فجوة** |
| قيد يدوي (DRAFT) | ✅ موجود | يعمل |
| ترحيل قيد | ✅ موجود (معطّل) | بوابة OFF |
| عكس قيد | ✅ موجود (معطّل) | بوابة OFF |

### 4.2 فجوة مفتاح التكرار (Idempotency Gap)

- **لا يوجد `idempotency_key`** على مسارات إنشاء الفاتورة أو الدفع أو الاسترداد.
- **خطر:** طلب مكرر (retry/double-click) قد يُنشئ فاتورة مزدوجة أو دفع مزدوج.
- **تخفيف جزئي:** الاسترداد يتحقق من المبلغ القابل للاسترداد، والدفع الجزئي يقفل الصف (`FOR UPDATE`).
- **تخفيف غير كافٍ:** لا يوجد `ON CONFLICT` أو `unique constraint` على مفتاح عملية.

### 4.3 فجوة التسوية (Reconciliation Gap)

- **يوجد:** تقرير تقادم ذمم مدينة (`/api/finance/aging`).
- **يوجد:** ملخص مالي (`/api/finance/summary`) — إجمالي الإيرادات والمدفوع وغير المدفوع.
- **لا يوجد:** تسوية بين إجمالي الفواتير وإجمالي القيود المحاسبية.
- **لا يوجد:** تسوية بين المدفوعات والقيود النقدية.
- **لا يوجد:** تسوية بين الاستردادات والقيود العكسية.
- **السبب:** لا توجد قيود محاسبية تُنشأ أصلاً عند حدوث العمليات.

## 5. نموذج المخاطر

### 5.1 مخاطر دورة الفاتورة

| الحالة | الحماية الحالية | الخطر المتبقي |
|--------|-----------------|---------------|
| فاتورة مسودة | لا يوجد مفهوم مسودة — كل فاتورة تُنشأ نهائية | متوسط |
| فاتورة صادرة بلا قيد | ❌ لا قيد محاسبي | **عالٍ** — إيراد غير مسجل في الدفتر |
| فاتورة ملغاة بلا إشعار دائن | ❌ لا قيد عكسي | **عالٍ** — إلغاء بلا أثر محاسبي |
| فاتورة معدّلة | لا يوجد مسار تعديل | منخفض (بالتصميم) |

### 5.2 مخاطر دورة الدفع

| الحالة | الحماية الحالية | الخطر المتبقي |
|--------|-----------------|---------------|
| دفع كامل | علامة `paid=1` فقط | **عالٍ** — لا قيد نقدي/بنكي |
| دفع جزئي | `amount_paid` + `FOR UPDATE` | **عالٍ** — لا قيد نقدي |
| دفع زائد | `assertAmountWithinCap` يرفض | ✅ محمي |
| عكس دفع | لا يوجد مسار | **متوسط** — لا يمكن عكس دفع خاطئ |

### 5.3 مخاطر دورة الاسترداد

| الحالة | الحماية الحالية | الخطر المتبقي |
|--------|-----------------|---------------|
| استرداد جزئي | حساب server-side + cap | ✅ محمي |
| استرداد كامل | حساب server-side | ✅ محمي |
| استرداد مكرر | فحص مبلغ متبقي | **متوسط** — لا idempotency key |
| استرداد عبر مستأجر | `tenant_id` check + `FOR UPDATE` | ✅ محمي |
| استرداد بلا قيد عكسي | ❌ لا قيد | **عالٍ** — خروج نقد بلا أثر محاسبي |

### 5.4 مخاطر دورة القيد المحاسبي (GL)

| الحالة | الحماية الحالية | الخطر المتبقي |
|--------|-----------------|---------------|
| مدين ≠ دائن | `validateBalancedEntry` يرفض | ✅ محمي |
| قيد مزدوج | لا `idempotency_key` | **متوسط** |
| ترحيل بدون مستند مصدر | `source_type` اختياري | **متوسط** |
| ترحيل والمحاسبة OFF | `e10PostingEnabled()` يرفض 403 | ✅ محمي |
| تعديل قيد مرحّل | مرفوض (immutable + reversal only) | ✅ محمي |
| قيد بلا نطاق مستأجر | `e10RequireTenant` يرفض 403 | ✅ محمي |

## 6. التصميم المقترح (لم يُنفّذ)

### 6.1 نموذج المستند المصدري

```
source_type  │  source_id       │  event_type
─────────────┼──────────────────┼─────────────────
INVOICE      │  invoices.id     │  ISSUED
INVOICE      │  invoices.id     │  CANCELLED
PAYMENT      │  invoices.id     │  FULL_PAYMENT
PAYMENT      │  invoices.id     │  PARTIAL_PAYMENT
REFUND       │  invoices.id     │  REFUND
```

### 6.2 سياسة الترحيل المحاسبي

1. **المحاسبة معطّلة افتراضياً** — لا يُنشأ أي قيد تلقائي ما لم يُفعّل `ACCOUNTING_POSTING_ENABLED=1` **و** يوافق المالك.
2. **لا إنشاء قيد بدون علم تفعيل صريح وموافقة المالك.**
3. **مفتاح التكرار:** `source_type + source_id + event_type` — يمنع القيد المزدوج.
4. **توازن مدين/دائن إلزامي** — `validateBalancedEntry()` موجود ويعمل.
5. **نطاق مستأجر إلزامي** — كل قيد مرتبط بـ `tenant_id`.
6. **القيد بعد الترحيل غير قابل للتعديل** — العكس فقط عبر قيد عكسي.
7. **قيد العكس بدلاً من الحذف** — `buildReversalLines()` موجود ويعمل.

### 6.3 القيود المحاسبية المقترحة (عند التفعيل)

| العملية | مدين | دائن |
|---------|------|------|
| إصدار فاتورة | ذمم مدينة (AR) | إيرادات + ض.ق.م مستحقة |
| دفع كامل | نقد/بنك | ذمم مدينة (AR) |
| دفع جزئي | نقد/بنك | ذمم مدينة (AR) |
| استرداد | إيرادات مرتجعة | نقد/بنك |
| إلغاء فاتورة | إيرادات (عكسي) | ذمم مدينة (AR) (عكسي) |

### 6.4 التسوية المقترحة

- إجمالي الفواتير الصادرة = إجمالي قيود الإيرادات.
- إجمالي المدفوعات = إجمالي قيود النقد/البنك.
- رصيد الذمم المدينة = الفواتير غير المسددة.
- إجمالي الاستردادات = إجمالي قيود الإيرادات المرتجعة.
- تغطية المصدر: كل قيد مرتبط بمستند مصدري (لا قيد يتيم).

### 6.5 سلوك الفشل

- **إغلاق عند الفشل (fail-closed):** إذا كان الترحيل مطلوباً لكن القيد غير صالح → رفض العملية بالكامل.
- **لا قيد جزئي صامت:** إما قيد كامل متوازن أو لا قيد.
- **لا اتصالات خارجية:** كل المنطق محلي وحتمي.

### 6.6 الاختبارات المطلوبة قبل التنفيذ

1. اختبار إنشاء قيد تلقائي عند إصدار فاتورة (عندما يكون التفعيل ON).
2. اختبار عدم إنشاء قيد عندما يكون التفعيل OFF.
3. اختبار مفتاح التكرار (idempotency).
4. اختبار توازن المدين/الدائن.
5. اختبار نطاق المستأجر.
6. اختبار تسوية الفواتير مقابل القيود.
7. اختبار قيد الاسترداد العكسي.
8. اختبار قيد الإلغاء.

## 7. قرار الجاهزية

### **H5_READY_FOR_CODE_IMPLEMENTATION_PLAN_WITH_ACCOUNTING_OFF**

**المبررات:**

1. **البنية التحتية موجودة:** دفتر اليومية، دليل الحسابات، التحقق من التوازن، العكس — كلها مبنية ومختبرة (`finance_engine.js`).
2. **بوابة التفعيل موجودة:** `e10PostingEnabled()` تمنع الترحيل ما لم يُفعّل صراحة.
3. **لا حاجة لجداول جديدة:** الجداول `finance_journal_entries` و `finance_journal_lines` و `finance_chart_of_accounts` موجودة.
4. **ما يحتاجه التنفيذ:** ربط تلقائي (hook) بين عمليات الفوترة/الدفع/الاسترداد وإنشاء قيد DRAFT — فقط عندما يكون `ACCOUNTING_POSTING_ENABLED=1`.
5. **المحاسبة ستبقى OFF** حتى يقرر المالك تفعيلها بعد إعداد دليل الحسابات.

**ما لا يمكن تنفيذه بدون قرار المالك:**
- تحديد هيكل دليل الحسابات (أرقام الحسابات).
- تحديد سياسة الترحيل التلقائي (هل يترحّل فوراً أم يبقى DRAFT).
- تحديد هل يُفعّل `ACCOUNTING_POSTING_ENABLED` في الإنتاج.

- ❌ لا push ولا deploy.
