# مهارة الأوتو بايلوت لتصميم هيكل وعزل التقييمات التمريضية (Nursing Assessments Schema Design Skill)
## نظام نما الطبي (NamaMedical)

توفر هذه المهارة الإرشادات والضوابط الصارمة اللازمة لإجراء تصاميم هيكلية وتخطيط هجرات البيانات وتعبئتها وتفعيل Row-Level Security (RLS) للجداول الطبية التي تفتقر لأعمدة المستأجر بشكل مباشر.

---

### 1. ضوابط ومبادئ تصميم نموذج الملكية (Ownership Design Principles)

* **ربط الكائنات الطبية (Clinical Object Linkage)**:
  - عند غياب أعمدة المستأجر (`tenant_id`, `facility_id`)، يجب تتبع سلسلة العلاقات الكلينيكالية للوصول إلى الكائن الرئيسي المملوك للمستأجر (مثل: المريض أو سجل التنويم).
  - تحديد دائم لمصدر الحقيقة:
    `nursing_assessments.patient_id -> patients.tenant_id`
* **فرض معايير الأداء لـ RLS**:
  - يمنع استخدام الـ JOINs في شروط USING لسياسات RLS بقاعدة البيانات لتفادي مشاكل الأداء.
  - القرار الفني القياسي هو تصميم إضافة الأعمدة الحيوية مباشرة كـ `nullable` أولاً، ثم إجراء التعبئة، ثم فرض قيد `NOT NULL`.

---

### 2. خطة تعبئة وتحديث البيانات التراكمية (Backfill Guidelines)

عند تخطيط هجرة البيانات، يجب إعداد جمل التحديث بدقة لتفادي إغلاق أو تشويه السجلات:
1. **ربط الجداول المتقاطعة (Cross-Table JOIN UPDATE)**:
   استخدام دائم لصيغة `UPDATE ... FROM ... WHERE` لربط السجل بمعرّف المريض وسحب المستأجر منه:
   ```sql
   UPDATE target_table t
   SET tenant_id = p.tenant_id
   FROM patients p
   WHERE t.patient_id = p.id;
   ```
2. **التحقق من السجلات اليتيمة (Orphan Records Verification)**:
   - يجب تشغيل استعلام كشف القيم `NULL` بعد الهجرة وقبل تفعيل سياسات الـ `NOT NULL` للتأكد من معالجة كافة الصفوف التاريخية.
   - النسبة المقبولة للسجلات اليتيمة: **0%** (يجب ربطها يدوياً أو تصفيتها).

---

### 3. تدقيق أمن الـ API ومنع IDOR

* **التحقق المسبق في الكود**:
  - يجب أن يتأكد الخادم برمجياً من أن المورد المراد الربط به (مثل المريض) يخص نفس المستأجر للجلسة قبل الشروع بالإدخال.
  - تجاهل أي قيم مستأجر ممررة من جسم الطلب للمستعرض والاعتماد المطلق على سياق الجلسة الآمنة.
