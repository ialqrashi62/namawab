# وثيقة سيناريوهات سير العمل السريري الشاملة (GATE 6)
## NamaMedical / Jumanasoft — 18 سيناريو End-to-End

> **الحالة:** وثيقة تخطيط فقط — لا DDL ولا لمس إنتاج.
> **المُعِدّ:** Clinical Workflow Analyst (وكيل ضمن نظام Multi-Agent).
> **التاريخ:** 2026-07-06.
> **المرجعية:** الكتالوج النهائي المعتمد (Gate 2) + الفجوات العليا (Gate 3-5) + الكود المبني فعلاً (محطة الطبيب v3 CPOE، محطة التمريض v1 بعشرة تبويبات NEWS2/eMAR/SBAR/فرز، محرك الدرجات GCS/APGAR/NIHSS/SOFA، محرك EWS/MEWS/PEWS + `/api/ews/assess`، فرز ESI بالطوارئ، ADT، بنك الدم، LIS/RIS، الصيدلية، المالية + Idempotency، NPHIES FHIR scaffolding، ZATCA Phase-2 مقيد بـCSID، RLS متعدد المستأجرين 150 سياسة FORCE، ملفات PHI محمية عبر `/api/phi-files/:id`).

### اصطلاحات الوثيقة

| الرمز | المعنى |
|---|---|
| ✅ مبني | القدرة موجودة ومكتملة في الكود الحالي |
| 🟡 جزئي | موجود بالكود لكنه ناقص أو هيكلي (placeholder) |
| 🔴 مفقود | غير موجود — مطلوب بناؤه وفق الكتالوج |
| 🔀 دمج | يُنفَّذ كتبويب داخل قسم قائم |
| SG | Safety Gate — بوابة سلامة إلزامية توقف التدفق حتى استيفائها |
| AC | Acceptance Criteria — اختبار قبول قابل للتحقق |
| RLS | كل جدول مذكور يخضع لعزل المستأجر `app.tenant_id` (سياسات FORCE) |
| Audit | كل حدث يُكتب في سجل التدقيق مع (المستخدم، الدور، المستأجر، الطابع الزمني، الكيان، الفعل، القيمة قبل/بعد) |

> **قاعدة عرضية لكل السيناريوهات:** كل API يمر عبر جلسة موثّقة (الجلسة تتغلب على ترويسة `x-tenant-id` — Gate 4)، وكل عملية مالية تمر عبر مفتاح Idempotency (Gate 7)، وكل نتيجة حرجة تتطلب Physician Acknowledgement (حلقة إغلاق الطلب-النتيجة — Gate 3).

## السيناريو 1: مريض جديد (تسجيل → أهلية تأمين → موعد → عيادة خارجية)

### 1.1 التعريف

| البند | القيمة |
|---|---|
| **Trigger** | وصول مريض لأول مرة إلى مكتب الاستقبال (أو تسجيل ذاتي عبر بوابة المرضى) |
| **Actor الرئيسي** | موظف الاستقبال والتسجيل (MPI) |
| **فاعلون مساندون** | منسق التأمين، موظف المواعيد، ممرض العيادات، الطبيب |
| **الأقسام** | A-الاستقبال والتسجيل ✅ ← أهلية NPHIES 🔴 ← المواعيد ✅ ← قائمة الانتظار ✅ ← OPD 🔴 (مغطاة جزئياً بمحطة الطبيب ✅) |
| **Safety Gate** | منع التسجيل المكرر (بحث MPI إلزامي قبل إنشاء ملف جديد) + تحقق الهوية الوطنية/الإقامة |

### 1.2 الخطوات

| # | الخطوة | الفاعل | الشاشة / الزر | البيانات الداخلة → الخارجة | API (مقترح/موجود) | الجداول | Audit |
|---|---|---|---|---|---|---|---|
| 1 | البحث في MPI عن تطابق | استقبال | شاشة الاستقبال ← زر «بحث عن مريض» | هوية/جوال/اسم → قائمة مطابقات مرجحة | `GET /api/patients/search` ✅ | `patients` | PATIENT_SEARCH |
| 2 | إنشاء ملف مريض جديد (عند عدم التطابق) | استقبال | نموذج «مريض جديد» ← زر «حفظ» | ديموغرافيا + هوية + جهة اتصال طوارئ → MRN | `POST /api/patients` ✅ | `patients` | PATIENT_CREATE |
| 3 | فحص أهلية التأمين لحظياً | منسق تأمين | شاشة «أهلية NPHIES» 🔴 ← زر «تحقق من الأهلية» | رقم الهوية + جهة التأمين → حالة الأهلية/الشبكة/التحمل | `POST /api/nphies/eligibility` 🔴 (على scaffolding FHIR الموجود) | `insurance_eligibility_checks` 🔴 | ELIGIBILITY_CHECK |
| 4 | ربط بوليصة التأمين أو تحديد «نقدي» | منسق تأمين | تبويب التأمين في ملف المريض ← «ربط بوليصة» | بوليصة/فئة/نسبة تحمل → ملف تغطية | `POST /api/patients/:id/coverage` 🟡 | `patient_insurance` | COVERAGE_LINK |
| 5 | حجز موعد | مواعيد | شاشة المواعيد ← «حجز» | عيادة/طبيب/وقت → رقم موعد + رسالة SMS | `POST /api/appointments` ✅ | `appointments` | APPT_CREATE |
| 6 | تفعيل الزيارة ووضعه في قائمة الانتظار | استقبال | قائمة الانتظار ← «تسجيل حضور» | رقم الموعد → تذكرة انتظار + رقم دور | `POST /api/queue/checkin` ✅ | `waiting_queue`, `encounters` | ENCOUNTER_OPEN |
| 7 | القياسات الحيوية قبل الطبيب | ممرض عيادات | محطة التمريض ← تبويب التقييم ✅ | ضغط/حرارة/نبض/وزن → علامات حيوية + NEWS2 تلقائي | `POST /api/vitals` ✅ + `POST /api/ews/assess` ✅ | `vital_signs`, `ews_assessments` | VITALS_RECORD |
| 8 | الكشف والتوثيق والأوامر | طبيب | محطة الطبيب v3 ✅ ← SOAP + CPOE | شكوى/تشخيص ICD-10-AM → أوامر/وصفة/إحالة | `POST /api/doctor-station/orders` ✅ | `clinical_orders`, `patient_clinical_records` | CPOE_ORDER |
| 9 | إغلاق الزيارة والفوترة | استقبال/كاشير | حسابات المرضى ← «إصدار فاتورة» | خدمات الزيارة → فاتورة + مطالبة أولية | `POST /api/billing/invoices` ✅ (Idempotency) | `invoices`, `invoice_items` | INVOICE_CREATE |

### 1.3 الحوكمة

| البند | التفصيل |
|---|---|
| **الصلاحيات** | استقبال: إنشاء/تعديل ديموغرافيا فقط. منسق تأمين: أهلية وتغطية. ممرض: قياسات. طبيب: توثيق سريري وأوامر. لا يرى أي دور بيانات مستأجر آخر (RLS) |
| **التنبيهات** | تطابق MPI محتمل (تحذير ازدواج) — أهلية مرفوضة (منع متابعة المسار التأميني) — SMS تأكيد موعد — NEWS2 ≥ العتبة يستدعي تصعيداً قبل دخول الطبيب |
| **Billing/Insurance** | تحديد المسار (نقدي/تأميني) من الخطوة 3-4 يحكم التسعير؛ رفض الأهلية من المنبع يمنع رفض المطالبة لاحقاً (أعلى فجوات Gate 5) |
| **Safety Gate** | SG-1: لا إنشاء ملف جديد دون بحث MPI موثّق. SG-2: لا زيارة تأمينية دون أهلية سارية أو تجاوز موثّق بموافقة مشرف |

### 1.4 حالات الفشل

| الحالة | سلوك النظام |
|---|---|
| انقطاع NPHIES أثناء فحص الأهلية | وضع «أهلية معلّقة» + متابعة نقدي-مؤقت بموافقة مشرف + إعادة محاولة تلقائية بطابور |
| اكتشاف ملف مكرر بعد الإنشاء | طلب «دمج ملفات» بموافقة مدير السجلات (HIM) مع Audit كامل، لا حذف فيزيائي |
| عدم حضور المريض (No-show) | إغلاق تلقائي للموعد بعد مهلة + تسجيل No-show في تقارير المواعيد |
| فشل SMS | إعادة إرسال + تسجيل فشل القناة دون تعطيل الحجز |

### 1.5 اختبارات القبول

- **AC-1.1:** البحث برقم هوية موجود يعيد الملف نفسه ولا يسمح بإنشاء MRN ثانٍ دون تجاوز مبرر.
- **AC-1.2:** فحص أهلية مرفوض يمنع فتح زيارة تأمينية ويعرض سبب الرفض بالعربية.
- **AC-1.3:** تسجيل الحضور يُظهر المريض في قائمة انتظار العيادة الصحيحة خلال ≤ 2 ثانية.
- **AC-1.4:** قياسات حيوية بقيم حرجة تولّد درجة NEWS2 وتنبيه تصعيد قبل شاشة الطبيب.
- **AC-1.5:** الفاتورة النقدية لا تُنشأ مرتين عند تكرار الطلب بنفس مفتاح Idempotency.
- **AC-1.6:** مستخدم من مستأجر آخر لا يرى المريض إطلاقاً (اختبار RLS: ctx مختلف → 0 نتائج).

## السيناريو 2: حالة طوارئ (وصول → فرز ESI → معالجة → قرار تصريف)

### 2.1 التعريف

| البند | القيمة |
|---|---|
| **Trigger** | وصول مريض إلى بوابة الطوارئ (سيراً/إسعاف/تحويل) |
| **Actor الرئيسي** | ممرض الفرز (Triage Nurse) |
| **فاعلون مساندون** | موظف تسجيل الطوارئ، طبيب الطوارئ، تمريض الطوارئ 🔴، إدارة الأسرّة 🔴 |
| **الأقسام** | الطوارئ ER (فرز ESI) ✅ ← محطة التمريض (تبويب الفرز ✅) ← محطة الطبيب ✅ ← ADT ✅ / إدارة الأسرّة 🔴 |
| **Safety Gate** | الفرز قبل التسجيل الكامل (Triage-first)؛ ESI 1-2 يتجاوز كل الطوابير |

### 2.2 الخطوات

| # | الخطوة | الفاعل | الشاشة / الزر | البيانات الداخلة → الخارجة | API | الجداول | Audit |
|---|---|---|---|---|---|---|---|
| 1 | تسجيل سريع (Quick Reg) | استقبال طوارئ | شاشة الطوارئ ← «تسجيل سريع» | اسم/عمر تقريبي أو «مجهول الهوية» → ملف مؤقت | `POST /api/er/quick-register` 🟡 | `patients`, `er_visits` | ER_QUICK_REG |
| 2 | الفرز ESI | ممرض فرز | تبويب الفرز ✅ ← «بدء فرز» | شكوى + علامات حيوية + وعي (GCS من محرك الدرجات ✅) → درجة ESI 1-5 | `POST /api/er/triage` ✅ + `POST /api/scores/gcs` ✅ | `er_triage`, `ews_assessments` | TRIAGE_COMPLETE |
| 3 | تخصيص سرير/منطقة معالجة | ممرض مسؤول | خريطة أسرّة الطوارئ 🔴 (حالياً قائمة) ← «تخصيص» | ESI → منطقة (إنعاش/عاجل/سريع) | `POST /api/er/assign-bed` 🔴 | `er_beds` 🔴 | BED_ASSIGN |
| 4 | تقييم الطبيب وأوامر عاجلة | طبيب طوارئ | محطة الطبيب v3 ✅ ← CPOE (مختبر/أشعة/أدوية/وريدي) | تقييم → أوامر STAT | `POST /api/doctor-station/orders` ✅ | `clinical_orders` | CPOE_STAT |
| 5 | تنفيذ تمريضي + مراقبة | تمريض طوارئ 🔴 (حالياً المحطة العامة ✅) | eMAR ✅ + تبويب السوائل ✅ | أدوية/سوائل → توثيق إعطاء + MEWS دوري | `POST /api/emar/administer` ✅، `POST /api/ews/assess` ✅ | `emar_administrations`, `ews_assessments` | MED_ADMIN |
| 6 | مراجعة النتائج والإقرار | طبيب طوارئ | محطة الطبيب ← «النتائج» ✅ ← زر «إقرار» | نتائج مختبر/أشعة → Physician Ack (Gate 3 ✅) | `POST /api/results/:id/ack` ✅ | `order_results`, `result_acknowledgements` | RESULT_ACK |
| 7 | قرار التصريف | طبيب طوارئ | شاشة القرار ← «خروج / تنويم / تحويل / وفاة» | القرار + تعليمات → مسار تابع | `POST /api/er/disposition` 🟡 | `er_visits`, `admissions` | ER_DISPOSITION |
| 8 | استكمال بيانات التسجيل والفوترة | استقبال | ملف المريض ← «استكمال بيانات» | هوية/تأمين → دمج الملف المؤقت | `PUT /api/patients/:id` ✅ | `patients`, `invoices` | PATIENT_COMPLETE |

### 2.3 الحوكمة

| البند | التفصيل |
|---|---|
| **الصلاحيات** | ممرض الفرز: فرز فقط لا يعدّل بعد الاعتماد. طبيب الطوارئ: أوامر وقرار تصريف. لا يغلق ملف طوارئ إلا الطبيب |
| **التنبيهات** | ESI-1: إنذار إنعاش فوري لكل شاشات الطوارئ. ESI-2: عدّاد زمن حتى رؤية الطبيب. تجاوز زمن الانتظار المستهدف لكل درجة ESI. نتيجة حرجة غير مُقَرَّة > 30 دقيقة → تصعيد |
| **Billing/Insurance** | رسوم الطوارئ حسب درجة ESI ومستوى الخدمة؛ حالات الحوادث تُعلَّم لمسار المطالبات الحكومي؛ العلاج المنقذ للحياة لا يُحجب لأسباب مالية (SG) |
| **Safety Gate** | SG-1: لا يُصرف مريض ESI 1-2 قبل إقرار الطبيب لكل النتائج الحرجة. SG-2: الفرز لا يُعتمد دون علامات حيوية كاملة. SG-3: العلاج العاجل يسبق استكمال التسجيل والدفع |

### 2.4 حالات الفشل

| الحالة | سلوك النظام |
|---|---|
| مريض مجهول الهوية | ملف «مجهول-تسلسلي» + سوار مؤقت، الدمج لاحقاً عبر HIM |
| امتلاء أسرّة الطوارئ | حالة «تكدس» تُشعِر إدارة الأسرّة المركزية 🔴 وتفعّل بروتوكول تحويل داخلي |
| مغادرة دون إذن (LAMA/DAMA) | إقرار مغادرة موقّع (قسم الإقرارات ✅) + إغلاق بحالة DAMA |
| تعطل محرك EWS | إدخال يدوي للدرجة مع علامة «حساب يدوي» — لا يُحجب الفرز |

### 2.5 اختبارات القبول

- **AC-2.1:** حالة ESI-1 تظهر بإنذار مرئي أعلى قائمة الطوارئ فوراً وتتجاوز الترتيب الزمني.
- **AC-2.2:** لا يمكن اعتماد فرز دون علامات حيوية إلزامية (رفض بالنموذج مع رسالة عربية).
- **AC-2.3:** أمر STAT يظهر في المختبر/الأشعة بعلامة عاجل خلال ≤ 5 ثوانٍ.
- **AC-2.4:** محاولة تصريف مع نتيجة حرجة غير مُقَرَّة تُحظر مع ذكر النتيجة المعلّقة.
- **AC-2.5:** ملف «مجهول» يُدمج بملف حقيقي دون فقدان أي أمر أو نتيجة (تتبع Audit كامل).

## السيناريو 3: تنويم مريض (قرار تنويم → سرير → رعاية يومية → خروج)

### 3.1 التعريف

| البند | القيمة |
|---|---|
| **Trigger** | قرار تنويم من طبيب (طوارئ/عيادة) أو تنويم مجدول |
| **Actor الرئيسي** | منسق التنويم ADT |
| **فاعلون مساندون** | إدارة الأسرّة 🔴، تمريض التنويم 🟡، الطبيب المعالج، التغذية 🟡، حسابات المرضى |
| **الأقسام** | ADT ✅ ← إدارة الأسرّة المركزية 🔴 (أعلى فجوات Gate 5) ← محطة التمريض ✅ ← محطة الطبيب ✅ |
| **Safety Gate** | تسوية دوائية عند الدخول (Medication Reconciliation) + تقييم مخاطر السقوط/القرح (تبويب المخاطر ✅) |

### 3.2 الخطوات

| # | الخطوة | الفاعل | الشاشة / الزر | البيانات الداخلة → الخارجة | API | الجداول | Audit |
|---|---|---|---|---|---|---|---|
| 1 | أمر تنويم | طبيب | محطة الطبيب ← «أمر تنويم» | تشخيص دخول + قسم + مستوى رعاية → طلب سرير | `POST /api/adt/admission-orders` ✅ | `admission_orders` | ADMIT_ORDER |
| 2 | تخصيص سرير من الخريطة الحية | إدارة أسرّة | خريطة الأسرّة 🔴 ← «تخصيص سرير» | جناح/جنس/عزل → سرير محجوز | `POST /api/beds/assign` 🔴 | `beds`, `bed_assignments` 🔴 | BED_ASSIGN |
| 3 | فتح حلقة التنويم | ADT | شاشة ADT ✅ ← «تنويم» | موافقات + كفيل مالي → رقم تنويم | `POST /api/adt/admit` ✅ | `admissions`, `encounters` | ADMIT |
| 4 | تقييم تمريضي شامل خلال 24 ساعة | تمريض تنويم | محطة التمريض ← التقييم + المخاطر ✅ | تاريخ + سقوط (Morse) + قرح (Braden) → خطة رعاية ✅ | `POST /api/nursing/assessments` ✅ | `nursing_assessments`, `care_plans` | NURSE_ASSESS |
| 5 | تسوية دوائية | طبيب + صيدلي سريري 🟡 | محطة الطبيب ← «تسوية دوائية» 🔴 | أدوية المنزل → قائمة موحدة معتمدة | `POST /api/med-reconciliation` 🔴 | `med_reconciliations` 🔴 | MED_RECON |
| 6 | الرعاية اليومية (جولات) | تمريض + طبيب | eMAR ✅ + NEWS2 ✅ + SBAR ✅ + أوامر تغذية/وريدية ✅ | جرعات/علامات/ملاحظات → سجل يومي | `POST /api/emar/administer` ✅، `POST /api/ews/assess` ✅ | `emar_administrations`, `vital_signs`, `nursing_notes` | يومي |
| 7 | تدهور → تصعيد | تمريض | تنبيه EWS ✅ ← SBAR ✅ | NEWS2 مرتفع → استدعاء فريق استجابة | محرك التصعيد ✅ | `ews_escalations` | EWS_ESCALATE |
| 8 | أمر خروج + تعليمات | طبيب | محطة الطبيب ← «أمر خروج» | ملخص خروج + وصفة خروج + مواعيد متابعة | `POST /api/adt/discharge-orders` ✅ | `discharge_orders` | DISCHARGE_ORDER |
| 9 | خروج مالي وإداري | حسابات + ADT | حسابات المرضى ← «تسوية نهائية» ثم ADT ← «خروج» | فاتورة إقامة → إخلاء سرير → حالة «تنظيف» | `POST /api/adt/discharge` ✅ | `admissions`, `invoices`, `beds` | DISCHARGE |

### 3.3 الحوكمة

| البند | التفصيل |
|---|---|
| **الصلاحيات** | أمر التنويم والخروج: طبيب فقط. تخصيص السرير: إدارة الأسرّة. الخروج المالي لا يُقفل الملف السريري (فصل الأدوار) |
| **التنبيهات** | سرير جاهز → إشعار الطوارئ/العيادة. NEWS2 تصعيد تلقائي ✅. تقييم الـ24 ساعة متأخر. دواء متأخر عن جدول eMAR. سرير بحالة «تنظيف» > مهلة CSSD/النظافة |
| **Billing/Insurance** | موافقة تأمينية مسبقة (Pre-authorization) لأيام الإقامة؛ تجديد الموافقة عند تمديد الإقامة؛ الفاتورة تجمع الإقامة + الأوامر + الأدوية آلياً |
| **Safety Gate** | SG-1: لا خروج دون ملخص خروج معتمد ووصفة خروج مُسوّاة. SG-2: لا تنويم بلا تقييم مخاطر خلال 24 ساعة (مؤشر جودة CBAHI). SG-3: تسوية دوائية موثّقة عند الدخول والخروج |

### 3.4 حالات الفشل

| الحالة | سلوك النظام |
|---|---|
| لا يوجد سرير مناسب | قائمة انتظار أسرّة + خيار تنويم مؤقت بالطوارئ (Boarding) مع مؤقّت ظاهر |
| رفض الموافقة التأمينية أثناء الإقامة | تحويل تلقائي للمسار النقدي مع إشعار المريض وتوقيع إقرار مالي |
| تحويل داخلي بين أجناح | حركة Transfer في ADT تحافظ على استمرارية eMAR وخطة الرعاية دون إعادة إدخال |
| خروج ضد المشورة الطبية | إقرار DAMA موقّع + إغلاق بحالة خاصة + إشعار الطبيب المعالج |

### 3.5 اختبارات القبول

- **AC-3.1:** لا يمكن تنويم مريضين على السرير نفسه (قيد تفرّد على السرير النشط).
- **AC-3.2:** جرعة eMAR متأخرة > 30 دقيقة تظهر بلون تحذيري وتُسجَّل كمؤشر جودة.
- **AC-3.3:** NEWS2 ≥ 7 يولّد تصعيداً تلقائياً وسجل SBAR مرتبطاً بالحدث.
- **AC-3.4:** محاولة خروج دون ملخص معتمد تُرفض برسالة تبين المتطلبات الناقصة.
- **AC-3.5:** بعد الخروج يتحول السرير إلى «تنظيف» ولا يقبل تخصيصاً جديداً قبل «جاهز».

| تدهور بالـPACU | تفعيل تصعيد EWS ✅ + استدعاء تخدير + خيار إعادة لغرفة العمليات |

### 4.5 اختبارات القبول

- **AC-4.1:** لا يقبل النظام «بدء عملية» وحقل Time-out فارغ (اختبار حجب واجهة + API).
- **AC-4.2:** طقم CSSD بدفعة فاشلة المؤشر البيولوجي يُرفض إصداره ويظهر إنذار.
- **AC-4.3:** سجل التخدير يفرض إدخال علامات بفواصل ≤ 5 دقائق أثناء العملية وإلا ظهر إنذار فجوة.
- **AC-4.4:** إدخال عدّ نهائي غير مطابق ينشئ OVR تلقائياً ويمنع Sign-out.
- **AC-4.5:** إخلاء PACU بدرجة Aldrete 7 يُرفض إلا بتجاوز طبيب تخدير موثّق السبب.

### 6.5 اختبارات القبول

- **AC-6.1:** وصفة بنسلين لمريض حساسيته موثّقة تُحجب Hard-stop مع اسم مصدر التوثيق.
- **AC-6.2:** لا يمكن للصرف أن يسبق التحقق (اختبار ترتيب الحالات على مستوى API).
- **AC-6.3:** صرف صنف يخصم من الدفعة الأقرب انتهاءً (FEFO) ويطبع رقم الدفعة على الملصق.
- **AC-6.4:** إعطاء جرعة على eMAR يستلزم تحقق هوية المريض وإلا رُفض التوثيق.
- **AC-6.5:** Refill يستهلك من QtyTotal ولا يتجاوز عدد التكرارات المصرح (ميزة v3 ✅).

| 4 | بناء حزمة FHIR وإرسالها | أخصائي مطالبات | «إرسال إلى NPHIES» | مطالبة → Bundle (message+MessageHeader ✅ Gate 8) → إيصال استلام | `POST /api/nphies/claims` 🟡 (Idempotency ✅) | `claims`, `nphies_messages` | CLAIM_SUBMIT |
| 5 | استقبال الرد | النظام | «صندوق الردود» | رد NPHIES → مقبول/مرفوض جزئياً/مرفوض | `GET /api/nphies/responses` 🟡 | `claim_responses` | CLAIM_RESPONSE |
| 6 | إدارة الرفض والاستئناف | أخصائي مطالبات | «إدارة الرفض» 🔴 | سبب رفض → تصحيح وإعادة إرسال أو استئناف | `POST /api/claims/:id/resubmit` 🔴 | `claim_appeals` 🔴 | CLAIM_APPEAL |
| 7 | تسوية الحوالة (Remittance) | مالية | المالية ✅ ← «تسوية حوالة» | حوالة دفع → مطابقة مطالبات وقيد GL (Idempotency ✅) | `POST /api/remittance/reconcile` ✅ | `remittances`, `gl_entries` | REMIT_RECONCILE |
| 8 | تحميل التحمل على المريض | كاشير | حسابات المرضى ✅ | نسبة التحمل/المرفوض النهائي → فاتورة مريض | `POST /api/billing/invoices` ✅ | `invoices` | PATIENT_SHARE |

### 10.3 الحوكمة

| البند | التفصيل |
|---|---|
| **الصلاحيات** | الترميز: مرمّز معتمد. الإرسال: أخصائي مطالبات. التسوية المالية: محاسب. لا يعدّل أحد مطالبة مرسلة — التعديل بنسخة إعادة إرسال |
| **التنبيهات** | مطالبة على وشك تجاوز مهلة التقديم النظامية. معدل رفض جهة تأمين يتجاوز العتبة. مطالبات معلّقة بلا رد > المهلة. حوالة غير مطابقة للمبالغ |
| **Billing/Insurance** | هذا هو سيناريو الإيراد الأساسي؛ Idempotency يمنع ازدواج الإرسال والقيود ✅؛ رفض الأهلية من المنبع (السيناريو 1) هو خط الدفاع الأول ضد الرفض |
| **Safety Gate** | SG-1: لا إرسال مطالبة بفحص Scrubbing فاشل. SG-2: قناة NPHIES الفعلية مقيدة باعتماد رسمي (scaffolding غير معتمد — لا يُفعَّل إنتاجياً دون شهادات) |

### 10.4 حالات الفشل

| الحالة | سلوك النظام |
|---|---|
| انقطاع قناة NPHIES | طابور إرسال بإعادة محاولة تصاعدية + لوحة مطالبات معلّقة |
| رفض لنقص توثيق سريري | إرجاع للطبيب عبر مهمة توثيق تكميلي ثم إعادة إرسال |
| ازدواج إرسال المطالبة | مفتاح Idempotency يعيد نفس النتيجة دون تكرار قيد ✅ |
| حوالة أقل من المطالَب | فرق يسجَّل كخصم مصنّف أو يفتح استئنافاً — لا يُشطب صامتاً |

### 10.5 اختبارات القبول

- **AC-10.1:** مطالبة بلا ترميز ICD-10-AM كامل لا تجتاز Scrubbing وتعرض الحقول الناقصة.
- **AC-10.2:** إعادة POST لنفس المطالبة بنفس مفتاح Idempotency لا تنشئ سجلاً ثانياً (انحدار Gate 7).
- **AC-10.3:** Bundle الناتج يطابق بنية KSA (message + MessageHeader) في اختبار البنية (انحدار Gate 8).
- **AC-10.4:** تسوية حوالة تنشئ قيد GL متوازناً (مدين=دائن) وتربط كل مطالبة بمبلغها.
- **AC-10.5:** المطالبة المرسلة للقراءة فقط؛ أي تعديل ينشئ نسخة إعادة إرسال بمرجع للأصل.

## السيناريو 11: مكافحة عدوى (اشتباه HAI → ترصد → عزل → تقصّي → إغلاق)

| **Trigger** | نتيجة زرع إيجابية بممرض مقاوم (MDRO) أو اشتباه عدوى مرتبطة بالرعاية (HAI) بعد 48 ساعة من التنويم |
| **Actor الرئيسي** | ممارس مكافحة العدوى (IPC Practitioner) |
| **الأقسام** | المختبر ✅ ← مكافحة العدوى (ترصد HAI) 🟡 (**فجوة عليا — شرط CBAHI جوهري**) ← التمريض ✅ ← إدارة الأسرّة 🔴 (غرف عزل) |
| **Safety Gate** | أمر العزل خلال ساعة من التأكيد + تبليغ «حصن» للأمراض الواجب الإبلاغ عنها |

### 11.3 الحوكمة

| البند | التفصيل |
|---|---|
| **الصلاحيات** | تصنيف HAI وإغلاقه: ممارس IPC. أمر العزل ورفعه: طبيب. بيانات الترصد تظهر للجودة بصيغة مجمّعة دون كشف هوية الطاقم المتسبب |
| **التنبيهات** | MDRO جديد → إنذار IPC فوري. مريض عزل نُقل بلا علامة عزل → إنذار حرج. تفشٍّ (≥ حالتين مرتبطتين) → إنذار تفشٍّ للإدارة. انخفاض التزام غسل اليدين عن العتبة |
| **Billing/Insurance** | أيام العزل تُرمَّز بدقة؛ الـHAI المؤكد قد يخضع لقواعد عدم تحميل المؤمِّن تكاليف الضرر — يُعلَّم للمراجعة المالية |
| **Safety Gate** | SG-1: نتيجة MDRO لا تبقى بلا تقييم IPC > 24 ساعة. SG-2: لا إلغاء علامة العزل إلا بصلاحية IPC. SG-3: التبليغ الوزاري للأمراض المعدية خلال المهلة النظامية |

### 11.4 حالات الفشل

| الحالة | سلوك النظام |
|---|---|
| لا تتوفر غرفة عزل | عزل مكاني بالجناح (Cohorting) موثّق + أولوية قصوى بقائمة الأسرّة |
| مريض عزل يحتاج أشعة/عمليات | علامة العزل ترافق كل طلب وتظهر للقسم المستقبل قبل الاستلام |
| تفشٍّ مؤكد | فتح «حادثة تفشٍّ» بلجنة + خط زمني للحالات + تقرير للجودة (يرتبط بالسيناريو 12) |
| نقص مستلزمات PPE | طلب مخزون عاجل (السيناريو 13) بعلامة أولوية عدوى |

### 11.5 اختبارات القبول

- **AC-11.1:** نتيجة زرع MRSA تنشئ حالة ترصد تلقائياً خلال ≤ دقيقة من اعتماد النتيجة.
- **AC-11.2:** علامة العزل تظهر في محطة الطبيب والتمريض وقوائم الأشعة/المختبر لنفس المريض.
- **AC-11.3:** محاولة نقل مريض معزول لسرير عادي تُحذّر وتتطلب موافقة IPC.
- **AC-11.4:** لوحة مؤشرات HAI تحسب المعدل لكل 1000 يوم قسطرة/تنفس صناعي بشكل صحيح على بيانات اختبار.
- **AC-11.5:** إغلاق حالة دون زرع سلبي موثّق (حيث يُشترط) يُرفض برسالة المعيار الناقص.

| **التنبيهات** | Sentinel Event → إشعار فوري للمدير الطبي ومدير الجودة. بلاغ بلا تصنيف > 48 ساعة. RCA يتجاوز المهلة. CAPA متأخر عن موعده |

| **Safety Gate** | SG-1: أحداث محددة (عدّ أدوات ناقص، تفاعل نقل، خطأ دوائي وصل للمريض) تنشئ OVR تلقائياً لا اختيارياً. SG-2: لا إغلاق Sentinel بلا RCA مكتمل معتمد |

### 12.4 حالات الفشل

| الحالة | سلوك النظام |
|---|---|
| مبلّغ يخشى الانتقام | وضع «بلاغ مجهول» متاح — يفقد فقط إمكانية طلب إيضاحات منه |
| بلاغ كيدي | مسار مراجعة عدالة داخل الجودة، دون كشف الهوية للمشكو ضده |
| حادثة على مريض غادر | البلاغ يُنشأ بمرجع الزيارة المغلقة؛ الملف السريري يبقى مقفلاً (HIM ✅) والتوثيق بالـOVR |
| تراكم بلاغات بلا معالجة | لوحة أعمار البلاغات + تصعيد تلقائي للإدارة العليا |

### 12.5 اختبارات القبول

- **AC-12.1:** مستخدم عادي يستعلم عن بلاغ فلا يرى هوية المبلّغ حتى لو كان مديره المباشر.
- **AC-12.2:** «عدّ أدوات غير مطابق» في السيناريو 4 ينشئ OVR تلقائياً بربط بالعملية.
- **AC-12.3:** تصنيف Sentinel يرسل إشعاراً فورياً للمدير الطبي (قناة الرسائل ✅) ويفتح عدّاد 45 يوماً.
- **AC-12.4:** لا يُغلق بلاغ Sentinel وحالة RCA «غير مكتمل» (حجب API).
- **AC-12.5:** تقرير الاتجاهات يجمع دون أسماء مبلّغين ولا معرّفات مرضى (إخفاء هوية).

| **التنبيهات** | حد إعادة الطلب ✅. صلاحية دفعة ≤ 90 يوماً. صنف راكد. فرق جرد يتجاوز نسبة السماح. طلب معلّق بلا اعتماد > 48 ساعة. سحب صنف من السوق (Recall) → تتبع الدفعات بكل الأقسام |
| **Billing/Insurance** | حركة المخزون تغذي تكلفة الخدمة (COGS) في المالية ✅؛ المستهلكات على المريض تُحمَّل من عهدة القسم للفاتورة عند الاستخدام |
| **Safety Gate** | SG-1: المخدرات بمسار توقيع مزدوج وسجل رقابي مستقل. SG-2: Recall يجمّد الدفعة بكل المواقع فوراً ويمنع صرفها. SG-3: لا صرف صنف منتهي الصلاحية (حجب نظامي) |

### 13.4 حالات الفشل

| الحالة | سلوك النظام |
|---|---|
| صنف غير متوفر بالمخزن الرئيسي | صرف جزئي + Backorder آلي + اقتراح بديل من الكتالوج |
| طلب عاجل خارج الدوام | مسار «صرف طوارئ» بصلاحية مناوب المخزن + تسوية ورقية لاحقة موثّقة |
| فرق استلام بين المصروف والمستلم | فتح «فرق نقص» يعلّق على مسؤولية الناقل حتى التسوية |
| انتهاء صلاحية بعهدة القسم | مسار إتلاف موثّق بمحضر (يرتبط بالنفايات الطبية 🔴 للأدوية) |

### 13.5 اختبارات القبول

- **AC-13.1:** طلب يتخطى الاعتماد يُرفض على API حتى لمستخدم بصلاحيتين (فصل مهام).
- **AC-13.2:** الصرف يتبع FEFO ويسجّل رقم الدفعة بكل حركة.
- **AC-13.3:** بلوغ حد إعادة الطلب ينشئ اقتراح شراء خلال دورة الفحص التالية ويظهر باللوحة.
- **AC-13.4:** تفعيل Recall على دفعة يمنع صرفها من أي موقع ويعرض تقرير أماكن تواجدها.
- **AC-13.5:** فرق جرد يُقيَّد محاسبياً بقيد متوازن ولا يُعدَّل الرصيد مباشرة.

## السيناريو 14: دورة تعقيم CSSD (استلام ملوث → غسيل → تعقيم → تخزين → إصدار → تتبع)

### 14.1 التعريف

| **Trigger** | وصول أدوات ملوثة من العمليات/الأقسام بعد الاستخدام |

| **Safety Gate** | مؤشرات التعقيم (كيميائي كل حمولة + بيولوجي دوري) — فشل المؤشر = حجر الحمولة كاملة |

### 14.2 الخطوات

### 14.3 الحوكمة

| البند | التفصيل |
|---|---|
| **الصلاحيات** | تسجيل المؤشرات: مشرف CSSD. الاستدعاء: مدير CSSD + إخطار مكافحة العدوى والجودة إلزامياً. لا يعدّل فني نتيجة مؤشر مسجلة |
| **التنبيهات** | فشل مؤشر بيولوجي → إنذار حرج + حجر آلي للدفعة. طقم معقم قارب انتهاء صلاحية التعقيم. طقم صادر لم يعد خلال المدة. جهاز تعقيم متأخر عن الصيانة الوقائية (يرتبط بالسيناريو 15) |
| **Billing/Insurance** | تكلفة التعقيم تُحمَّل ضمن تكلفة العملية؛ تتبّع الطقم-للمريض يدعم التحقيق القانوني والتأميني عند عدوى موضع الجراحة (SSI) |
| **Safety Gate** | SG-1: لا إصدار طقم من دفعة بلا مؤشر كيميائي صالح. SG-2: فشل بيولوجي = استدعاء كل ما لم يُستخدم + إخطار IPC عن المستخدم فعلاً. SG-3: طقم منتهي صلاحية التعقيم يُعاد للدورة إلزامياً |

### 14.4 حالات الفشل

| الحالة | سلوك النظام |
|---|---|
| أداة ناقصة عند التغليف | فتح «نقص أداة» يخطر القسم المُعيد + طقم معلّق حتى الاكتمال أو الاستبدال |
| تعطل جهاز التعقيم | بلاغ صيانة (السيناريو 15) + تحويل الحمل لجهاز بديل + إعادة حساب طاقة اليوم الجراحي |
| طقم فُتح بالعمليات ولم يُستخدم | يُعاد كامل الدورة (يُعد ملوثاً) — لا اختصار |
| استخدام طقم من دفعة فشلت لاحقاً | قائمة المرضى المعرّضين تُرسل لـIPC (السيناريو 11) + OVR (السيناريو 12) |

### 14.5 اختبارات القبول

- **AC-14.1:** إصدار طقم من دفعة بمؤشر فاشل يُحجب على API وواجهة الإصدار معاً.
- **AC-14.2:** كل طقم صادر يحمل رابط (دفعة تعقيم ← عملية ← مريض) قابلاً للاستعلام العكسي.
- **AC-14.3:** «استدعاء دفعة» يعيد قائمة دقيقة: أطقم بالمخزن (تُحجر) وأطقم استُخدمت (مرضاها).
- **AC-14.4:** طقم تجاوز تاريخ انتهاء التعقيم يختفي من شاشة الإصدار تلقائياً.
- **AC-14.5:** دورة الحالات مقفلة التسلسل: لا «تعقيم» لطقم لم يمر بحالة «مغلّف».

## السيناريو 15: صيانة جهاز طبي (بلاغ عطل → أمر عمل → إصلاح → معايرة → إعادة تشغيل)

| البند | التفصيل |
|---|---|
| **الصلاحيات** | بلاغ العطل: الجميع. إعادة جهاز حرج للخدمة: مهندس طبي حيوي + رئيس القسم المستخدم (توقيعان). لا يُحذف سجل معايرة (امتثال) |
| **التنبيهات** | جهاز حرج خارج الخدمة → إشعار فوري لإدارة التشغيل والقسم البديل. معايرة مستحقة خلال 30 يوماً. جهاز تجاوز معايرته → وسم «غير معاير» وحجب افتراضي. تنبيه استدعاء مصنّع (FSN) على طراز |
| **Billing/Insurance** | تكلفة الصيانة تُحمَّل على مركز تكلفة القسم بالمالية ✅؛ توثيق المعايرة شرط تغطية التأمين المهني عند حوادث الأجهزة |
| **Safety Gate** | SG-1: لا استخدام جهاز موسوم «خارج الخدمة» — الوسم يظهر بواجهات الأقسام المرتبطة. SG-2: جهاز حرج بلا شهادة معايرة سارية لا يعود للخدمة. SG-3: عطل جهاز أثناء استخدامه على مريض → OVR تلقائي (السيناريو 12) |

### 15.4 حالات الفشل

| الحالة | سلوك النظام |
|---|---|
| عطل جهاز أثناء عملية جراحية | بروتوكول جهاز بديل فوري + OVR تلقائي + حجر الجهاز للفحص الفني |
| قطعة غيار غير متوفرة محلياً | أمر شراء عاجل (السيناريو 13) + جهاز إعارة من المورد يوثّق بالسجل |
| تجاوز تكلفة الإصلاح قيمة الاستبدال | توصية «إخراج من الخدمة نهائياً» بمسار موافقة مالية وإدارية |
| استدعاء مصنّع لطراز كامل | حصر آلي لكل الأجهزة من الطراز + خطة فحص/سحب موثّقة |

### 15.5 اختبارات القبول

- **AC-15.1:** جهاز «خارج الخدمة» يظهر بوسم تحذيري في شاشات القسم المالك (مثلاً جهاز تخدير بشاشة OR).
- **AC-15.2:** إعادة جهاز حرج للخدمة بتوقيع واحد تُرفض (إلزام توقيعين بدورين مختلفين).
- **AC-15.3:** انقضاء تاريخ المعايرة يقلب حالة الجهاز آلياً إلى «غير معاير».
- **AC-15.4:** الصيانة الوقائية تولّد أمر عمل قبل الاستحقاق بالمدة المضبوطة دون تدخل يدوي.
- **AC-15.5:** سجل تاريخ الجهاز يعرض كل أوامر العمل والمعايرات بترتيب زمني غير قابل للتعديل.

## السيناريو 16: جلسة طب عن بعد (حجز → تحقق → جلسة → وصفة → متابعة)

| البند | التفصيل |

| **التنبيهات** | تذكير المريض قبل الموعد (SMS/بوابة). طبيب متأخر > 10 دقائق → إشعار المريض وخيار إعادة جدولة. أعراض حمراء أثناء الفرز الذاتي → توجيه فوري للطوارئ |

### 16.4 حالات الفشل

| الحالة | سلوك النظام |
|---|---|
| انقطاع الاتصال أثناء الجلسة | إعادة اتصال خلال مهلة؛ الفشل النهائي = جلسة «منقطعة» بردّ مالي وإعادة جدولة مجانية |
| اتضاح أن الحالة تستوجب فحصاً حضورياً | إنهاء بتحويل لموعد حضوري بنفس الملف دون رسوم إضافية للكشف |
| فشل تحقق الهوية | إلغاء الجلسة وتوثيق المحاولة — لا خدمة سريرية لهوية غير محققة |
| مريض قاصر بلا ولي أمر حاضر | حجب الجلسة حتى حضور ولي الأمر الموثّق بالملف |

### 16.5 اختبارات القبول

- **AC-16.1:** حجز افتراضي غير مدفوع/غير مؤهل تأمينياً يبقى «غير مؤكد» ولا يفتح غرفة جلسة.
- **AC-16.2:** وصفة دواء مخدر من سياق جلسة عن بعد تُحجب مع رسالة القاعدة التنظيمية.
- **AC-16.3:** ملاحظة الجلسة تُعلَّم «عن بعد» وتظهر كذلك في السجل الطبي وHIM.
- **AC-16.4:** جلسة منقطعة تقنياً تولّد ردّاً مالياً واحداً فقط مهما تكرر طلب الرد (Idempotency).
- **AC-16.5:** زر تحويل الطوارئ ينشئ سجل توجيه بوقته ويُخطر مركز الاتصال.

## السيناريو 17: بوابة المرضى (تسجيل → عرض نتائج → حجز → دفع → تقرير طبي)

### 17.1 التعريف

| البند | القيمة |
|---|---|
| **Trigger** | مريض يفعّل حسابه على بوابة المرضى ذاتياً |
| **Actor الرئيسي** | المريض (Self-service) |
| **الأقسام** | بوابة المرضى 🟡 (موجود-ناقص) ← الرسائل والتنبيهات 🟡 ← المواعيد ✅ ← حسابات المرضى 🟡 ← HIM 🟡 |
| **Safety Gate** | ربط الحساب بالهوية الوطنية عبر OTP + حجب النتائج الحساسة حتى مناقشة الطبيب |

### 17.2 الخطوات

| # | الخطوة | الفاعل | الشاشة / الزر | البيانات الداخلة → الخارجة | API | الجداول | Audit |
|---|---|---|---|---|---|---|---|
| 1 | تسجيل حساب وربط بالملف | مريض | البوابة ← «حساب جديد» | هوية + جوال مسجل → OTP → حساب مربوط بـMRN | `POST /api/portal/register` 🟡 | `portal_accounts` 🟡 | PORTAL_REG |
| 2 | عرض الملف الشخصي والزيارات | مريض | «ملفي» | جلسة → ديموغرافيا + زيارات (قراءة فقط) | `GET /api/portal/profile` 🟡 | Views مقيدة | PORTAL_VIEW |

| 4 | حجز/إلغاء موعد | مريض | «مواعيدي» ← «حجز» | عيادة/وقت متاح → موعد + تذكير | `POST /api/appointments` ✅ | `appointments` | PORTAL_BOOK |

| 6 | طلب تقرير طبي | مريض | «طلباتي» ← «تقرير طبي» | نوع تقرير → طلب لـHIM بموافقة طبيب | `POST /api/portal/report-requests` 🔴 | `report_requests` 🔴 | REPORT_REQUEST |

| 8 | رسائل وتذكيرات | النظام | الرسائل 🟡 | مواعيد/نتائج جاهزة/تعليمات → إشعارات | `POST /api/notifications` 🟡 | `notifications` | NOTIFY_SEND |

### 17.3 الحوكمة

| البند | التفصيل |
|---|---|
| **الصلاحيات** | حساب البوابة يرى بيانات صاحبه فقط (RLS + قيد MRN على الجلسة). حسابات الأوصياء للقصّر بربط موثّق ينتهي ببلوغ السن. لا كتابة سريرية من البوابة إطلاقاً — قراءة وطلبات فقط |
| **التنبيهات** | نتيجة جديدة متاحة. موعد غداً. فاتورة مستحقة. محاولات دخول فاشلة متكررة → قفل مؤقت وإشعار. تسجيل دخول من جهاز جديد |
| **Billing/Insurance** | الدفع الإلكتروني يسوّي الفاتورة فوراً بقيد مالي ✅ وإشعار ZATCA حسب التفعيل (مقيد CSID)؛ كشف حساب المريض متاح ذاتياً يخفف ضغط الكاشير |
| **Safety Gate** | SG-1: النتائج الحساسة (أورام/HIV/وراثة) لا تُنشر للبوابة إلا بعد Release من الطبيب. SG-2: كل وصول للبوابة يسجَّل Audit كوصول PHI. SG-3: OTP إلزامي للربط ولإعادة تعيين كلمة المرور |

### 17.4 حالات الفشل

| الحالة | سلوك النظام |
|---|---|
| جوال المريض غير محدث بالملف | مسار تحقق بديل حضوري بالاستقبال — لا ربط ذاتي بلا OTP |
| نزاع على فاتورة | زر «اعتراض» يفتح تذكرة لحسابات المرضى بحالة تتبع |
| محاولة وصول لحساب الغير | قفل + تسجيل الحادثة الأمنية + إشعار صاحب الحساب |
| فشل بوابة الدفع بعد الخصم | تسوية آلية بالمطابقة مع مزود الدفع + عدم ازدواج بالقيد (Idempotency ✅) |

### 17.5 اختبارات القبول

- **AC-17.1:** حساب بوابة لا يستطيع جلب بيانات MRN آخر حتى بتلاعب بالمعرّف في الطلب (403 + Audit).
- **AC-17.2:** نتيجة معلّمة «حساسة» لا تظهر بالبوابة قبل Release موثّق من الطبيب.
- **AC-17.3:** دفع إلكتروني ناجح يغيّر حالة الفاتورة ويولّد قيداً واحداً فقط عند التكرار.
- **AC-17.4:** إلغاء موعد من البوابة يحرر الخانة فوراً بجدول العيادة.
- **AC-17.5:** التقرير الطبي يُسلَّم كملف عبر المسار المحمي `/api/phi-files/:id` لا برابط عام.

## السيناريو 18: وفاة (إعلان → توثيق → شهادة → ثلاجة الموتى → تسليم → إقفال)

### 18.1 التعريف

|---|---|
| **Trigger** | وفاة مريض داخل المنشأة (تنويم/طوارئ/عمليات) أو وصول متوفى |
| **Actor الرئيسي** | الطبيب المعلن للوفاة ثم موظف خدمة الوفيات 🟡 |
| **الأقسام** | خدمة الوفيات 🟡 (موجود-ناقص) ← HIM (قفل EMR ✅) ← الخدمة الاجتماعية 🟡 ← ADT ✅ ← علم الأمراض 🟡 (تشريح عند الطلب) |
| **Safety Gate** | تحقق هوية المتوفى بسوارين + سلسلة عهدة الجثمان + قفل الملف بعد الاعتماد |

### 18.2 الخطوات

### 18.3 الحوكمة

| البند | التفصيل |
|---|---|
| **الصلاحيات** | إعلان الوفاة وسبب الوفاة: طبيب فقط. إصدار الشهادة الرسمية: HIM بصلاحية خاصة. تسليم الجثمان: موظف وفيات بتحقق هوية موثّق. فتح ملف مقفل: تعديل تصحيحي عبر `emr_amendments` ✅ (لا تحرير مباشر) |
| **التنبيهات** | وفاة خلال 24 ساعة من الدخول أو أثناء/بعد جراحة → مراجعة لجنة الوفيات إلزامية + مؤشر جودة. جثمان بالثلاجة > المدة النظامية دون تسليم → تصعيد إداري. حالة جنائية → منع أي إجراء على الجثمان |
| **Billing/Insurance** | إيقاف كل الرسوم بعد وقت الوفاة المعلن؛ الفاتورة النهائية حتى لحظة الوفاة؛ مطالبة التأمين تُعلَّم Deceased وتُغلق وفق العقد؛ لا تُرسل تذكيرات دفع آلية للأسرة قبل مهلة لائقة |
| **Safety Gate** | SG-1: لا تسليم جثمان بحالة جنائية معلّقة. SG-2: لا إصدار شهادة بسلسلة أسباب ناقصة. SG-3: قفل EMR بعد الاعتماد — أي تعديل عبر مسار Amendments الموثّق ✅. SG-4: مطابقة سوارين عند كل حركة للجثمان |

### 18.4 حالات الفشل

| الحالة | سلوك النظام |
|---|---|
| نزاع أسري على الاستلام | تجميد التسليم + إحالة للخدمة الاجتماعية/الشؤون القانونية بسجل قرارات |
| وفاة مجهول الهوية | مسار تعريف رسمي عبر الجهات المختصة قبل أي إصدار شهادة |
| اكتشاف خطأ بالشهادة بعد الإصدار | شهادة بدل فاقد/مصححة بمسار رسمي — الأصل يبقى بعلامة ملغى |
| وفاة بالطوارئ قبل استكمال التسجيل | استكمال الملف المؤقت (السيناريو 2) ثم مسار الوفاة الكامل — لا اختصارات |

### 18.5 اختبارات القبول

- **AC-18.1:** بعد إعلان الوفاة تتوقف جداول eMAR والأوامر النشطة آلياً بحالة «أوقفت-وفاة».
- **AC-18.2:** شهادة بسلسلة أسباب ناقصة (بلا سبب أساسي) تُرفض عند الإصدار.
- **AC-18.3:** حالة جنائية معلّمة تحجب زر «تسليم الجثمان» وأي إجراء تحضيري.
- **AC-18.4:** الملف المقفل يرفض أي PUT سريري ويقبل فقط مسار `emr_amendments` (انحدار قفل EMR ✅).
- **AC-18.5:** الرسوم بعد وقت الوفاة لا تُحتسب (اختبار حدّي: خدمة بعد الوقت المعلن تُرفض بالفوترة).

## 20. القواعد العرضية الموحدة (تنطبق على السيناريوهات الـ18 كلها)

| المحور | القاعدة الموحدة |
|---|---|
| **العزل متعدد المستأجرين** | كل جدول في هذه الوثيقة خاضع لسياسات RLS FORCE مع `app.tenant_id` من الجلسة (لا من الترويسة — Gate 4)؛ أي جدول جديد مقترح 🔴 يُنشأ بسياسة RLS منذ اليوم الأول |
| **Audit** | كل حدث معلّم بالأعمدة القياسية (مستخدم/دور/مستأجر/زمن/كيان/فعل/قبل-بعد)؛ أحداث PHI وOVR بسرية معززة؛ يتطلب «عارض سجل التدقيق» 🔴 من الكتالوج لإغلاق حلقة الحوكمة |
| **Idempotency** | كل نقطة مال (فاتورة/دفع/مطالبة/حوالة/رد) بمفتاح Idempotency إلزامي — مطبّق ✅ (Gate 7) ويُعمَّم على نقاط الدفع الجديدة (بوابة/طب عن بعد) |
| **حلقة الطلب-النتيجة** | كل نتيجة تشخيصية (مختبر/أشعة/باثولوجي/وظيفي) تمر بحالة «بانتظار إقرار الطبيب» ولا تُغلق دونه — مطبّق ✅ (Gate 3) ويُعمَّم على الوظيفية 🔴 |
| **التصعيد السريري** | محرك EWS/MEWS/PEWS ✅ هو العمود الفقري للتصعيد في السيناريوهات 2/3/4(PACU)/5(NICU)/9؛ كل تصعيد يولّد SBAR ✅ مرتبطاً |
| **الموافقات** | قسم الإقرارات ✅ هو المصدر الموحد للموافقات (جراحة/تخدير/دم/صبغة/اتصالي/تشريح) — لا نماذج موافقة متناثرة |
| **ملفات PHI** | كل ملف ثنائي (صور/تقارير/تسجيلات) عبر النمط المحمي `/api/phi-files/:id` ✅ (auth+RLS+traversal-deny+audit) — لا روابط عامة إطلاقاً |
