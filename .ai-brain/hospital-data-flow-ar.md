# GATE 7 — مخطط تدفق البيانات الشامل (Data Flow) لمنصة NamaMedical / Jumanasoft

> وثيقة تخطيطية فقط — لا تتضمن أي DDL ولا تمس بيئة الإنتاج. جميع المسارات مقيدة بعزل المستأجرين (RLS متعدد المستأجرين، 150 سياسة FORCE) وبمبدأ Idempotency على كل عملية مالية، وبتسجيل تدقيق (Audit) على كل حدث سريري أو مالي حساس.

**تاريخ الوثيقة:** 2026-07-06
**البوابة:** GATE 7 — Data Flow
**المرجعية:** الكتالوج النهائي المعتمد (GATE 2) + الحقائق المثبتة من الكود (Express monolith + PostgreSQL RLS + NPHIES FHIR scaffolding + ZATCA Phase-2).

---

## 0. اصطلاحات الوثيقة

| العنصر | الاصطلاح |
|---|---|
| السهم `→` | انتقال بيانات/حدث من كيان مصدر إلى كيان هدف |
| السهم `⇢` | حدث تكامل خارجي (NPHIES / ZATCA / FHIR / HL7) |
| السهم `↺` | مسار فشل/إعادة محاولة (Retry / Compensating action) |
| `[RLS]` | كل استعلام مقيد بـ `app.tenant_id` (سياسة FORCE) |
| `[IDEMP]` | العملية محمية بمفتاح Idempotency (المطالبات/ZATCA/التحويلات) |
| `[AUDIT]` | يُكتب سجل في `audit_log` (من، متى، ماذا، على أي مريض/كيان، بأي مستأجر) |
| `[GATE]` | بوابة سلامة (SafetyGate) لا يمر التدفق دونها |
| كيان | جدول/تجمّع منطقي في PostgreSQL أو شاشة/محطة في الواجهة |

**قاعدة عامة لمعالجة الفشل (تسري على كل الفلوهات ما لم يُذكر خلافها):**

1. فشل تحقق (Validation) ⇒ رفض فوري 422 + رسالة عربية للمستخدم + لا كتابة جزئية (معاملة DB واحدة).
2. فشل صلاحية (Permission/RLS) ⇒ رفض 403 + `[AUDIT: access_denied]` — لا يُكشف وجود السجل.
3. فشل تكامل خارجي (NPHIES/ZATCA) ⇒ الحدث يُخزَّن محلياً بحالة `pending_integration` + طابور إعادة إرسال بمهلة تصاعدية (Exponential backoff) + تنبيه للمشغل — **العملية السريرية لا تتوقف أبداً على التكامل المالي**.
4. فشل مزدوج/تكرار ⇒ مفتاح Idempotency يعيد نفس النتيجة السابقة دون تكرار الأثر المالي.

## 1. المسار العام End-to-End (رحلة المريض من التسجيل إلى البوابة)

### 1.1 المخطط النصي

```
[المريض/الهوية]                                                        [الجهات الخارجية]
      │                                                                        ▲
      ▼                                                                        │
(1) الاستقبال والتسجيل MPI ──⇢ NPHIES: التحقق من الأهلية (Eligibility) ────────┤
      │  إنشاء/مطابقة patient_id [RLS][AUDIT]                                  │
      ▼                                                                        │
(2) الموعد/قائمة الانتظار/الطوارئ ESI ── فتح Encounter (زيارة) [GATE: هوية] ──┤
      │  encounter_id + نوع الزيارة (OPD/ER/IPD)                               │
      ▼                                                                        │
(3) التمريض: علامات حيوية + فرز + NEWS2/MEWS ──► تنبيه تصعيد إن تجاوز العتبة  │
      │  vitals, triage_score [GATE: EWS]                                      │
      ▼                                                                        │
(4) محطة الطبيب CPOE v3: تقييم + تشخيص ICD-10-AM + أوامر                       │
      │  orders (مختبر/أشعة/دواء/دم/تغذية/وريدي/تمريضي) [GATE: تداخلات]        │
      ├────────────► (5أ) المختبر LIS ── عينة → تحليل → نتيجة → Critical Flag  │
      ├────────────► (5ب) الأشعة RIS ── جدولة → تصوير → تقرير → PHI Vault      │
      ├────────────► (5ج) الصيدلية ── مراجعة سريرية → صرف → eMAR               │
      └────────────► (5د) بنك الدم ── فصيلة/توافق → صرف وحدة → إعطاء موثق      │
      ▼                                                                        │
(6) النتائج ترجع للطبيب ── إقرار الاستلام (Physician Ack) [GATE: إغلاق الحلقة] │
      │  order_result_loop مغلق                                                │
      ▼                                                                        │
(7) القرار: صرف/تنويم ADT/عمليات OR/إحالة ── تحديث الخطة العلاجية              │
      ▼                                                                        │
(8) الفوترة: حساب المريض → مطالبة تأمين ⇢ NPHIES Claim [IDEMP] ────────────────┤
      │                        └─⇢ ZATCA فاتورة إلكترونية Phase-2 [IDEMP] ─────┘
      ▼
(9) الخروج Discharge ── ملخص خروج + تعليمات + وصفة خروج ── قفل EMR (HIM)
      ▼
(10) بوابة المرضى: نتائج/مواعيد/فواتير + سجل التدقيق الكامل [AUDIT viewer]
```

### 1.2 جدول المسار العام

| # | المرحلة | كيان المصدر | كيان الهدف | البيانات المنشأة | بوابة السلامة | حدث التكامل |
|---|---|---|---|---|---|---|
| 1 | التسجيل | شاشة الاستقبال | `patients` (MPI) | سجل مريض + رقم موحّد | منع تكرار الهوية | NPHIES Eligibility |
| 2 | فتح الزيارة | المواعيد/الطوارئ | `encounters` | زيارة بنوعها ومسارها | ربط إلزامي بمريض مُتحقق | — |
| 3 | التمريض | محطة التمريض | `vitals`, `triage` | علامات حيوية + NEWS2 | تصعيد EWS تلقائي | — |
| 4 | الأوامر | محطة الطبيب CPOE | `orders` | أوامر بأنواعها | تداخلات دوائية + حساسية | — |
| 5 | التشخيصات | LIS/RIS/صيدلية/بنك دم | `results`, `dispenses` | نتائج ومصروفات | قيم حرجة + توافق دم | FHIR DiagnosticReport (داخلي) |
| 6 | إغلاق الحلقة | النتائج | `order_acknowledgements` | إقرار الطبيب | لا خروج بنتيجة غير مُقرّة | — |
| 7 | القرار | محطة الطبيب | `admissions`/`or_bookings` | خطة/تنويم/عملية | خريطة أسرّة (فجوة معروفة) | — |
| 8 | الفوترة | حسابات المرضى | `invoices`, `claims` | فاتورة + مطالبة | Idempotency مالي | NPHIES Claim + ZATCA |
| 9 | الخروج | ADT/HIM | `discharges` | ملخص خروج + قفل EMR | اكتمال التوثيق قبل القفل | — |
| 10 | ما بعد الخروج | بوابة المرضى | عرض للقراءة فقط | لا إنشاء — عرض فقط | RLS + مصادقة المريض | — |

## 2. فلو 1 — الوصول للمريض (Patient Access: تسجيل ← موعد ← انتظار ← زيارة)

### 2.1 المخطط

```
طلب تسجيل ──► شاشة الاستقبال ──► بحث MPI (اسم/هوية/جوال)
                                      │
                     ┌── تطابق موجود ─┴─ لا تطابق ──┐
                     ▼                              ▼
              استرجاع patient_id            إنشاء سجل جديد [AUDIT: patient_created]
                     │                              │
                     └──────────┬───────────────────┘
                                ▼
                 ⇢ NPHIES Eligibility (أهلية التأمين) ── فشل ↺ متابعة كنقدي + علم pending
                                ▼
              حجز موعد ──► قائمة الانتظار (Queue) ──► نداء المريض
                                ▼
              فتح Encounter [GATE: مريض متحقق + أهلية معروفة أو نقدي صريح]
```

### 2.2 الجدول التفصيلي

| البند | التفصيل |
|---|---|
| كيان المصدر | شاشة الاستقبال / بوابة المرضى (حجز ذاتي) / الطوارئ (تسجيل سريع Unknown) |
| كيان الهدف | `patients` (MPI)، `appointments`، `waiting_queue`، `encounters` |
| الحدث | `patient.registered`، `appointment.booked`، `queue.enqueued`، `encounter.opened` |
| البيانات المنشأة/المحدثة | بيانات ديموغرافية، رقم هوية/إقامة، جهة تأمين وبوليصة، نوع زيارة، أولوية طابور |
| التحقق (Validation) | صيغة رقم الهوية السعودية/الإقامة؛ منع سجل مكرر (مطابقة اسم+هوية+ميلاد)؛ تاريخ ميلاد منطقي؛ جوال سعودي؛ الموعد داخل جدول الطبيب المتاح |
| الصلاحية (Permission) | موظف استقبال: إنشاء/تعديل ديموغرافي فقط؛ لا يرى السجل السريري؛ `[RLS]` على المستأجر؛ التعديل على الهوية بعد الإنشاء يتطلب صلاحية مشرف |
| حدث التدقيق | `patient_created`، `patient_demographics_updated` (بالقيم القديمة/الجديدة)، `eligibility_checked`، `encounter_opened` |
| حدث التكامل | ⇢ NPHIES `CoverageEligibilityRequest/Response` (FHIR) عند التسجيل وقبل كل زيارة مؤمَّنة |
| معالجة الفشل | فشل الأهلية ⇒ الزيارة تُفتح بعلم `eligibility_pending` + تحويل تلقائي لمسار نقدي مع موافقة المريض الموثقة؛ تعطل NPHIES ⇒ طابور إعادة استعلام؛ اشتباه سجل مكرر ⇒ شاشة دمج MPI بصلاحية مشرف سجلات طبية `[AUDIT: mpi_merge]` |

## 3. فلو 2 — السريري (Clinical: محطة الطبيب CPOE ← تشخيص ← أوامر ← قرار)

### 3.1 المخطط

```
Encounter مفتوح ──► محطة الطبيب v3
      │
      ├─ استعراض: تاريخ مرضي + حساسيات + نتائج سابقة + EWS الحالي
      ▼
   توثيق SOAP + تشخيص ICD-10-AM
      ▼
   CPOE: إنشاء أوامر ──► [GATE: فحص حساسية + تداخلات + جرعة/وزن للأطفال]
      ├── أمر مختبر ────────► فلو المختبر (5)
      ├── أمر أشعة ─────────► فلو الأشعة (6)
      ├── وصفة (Rx + Refill) ► فلو الصيدلية (7)
      ├── أمر دم ───────────► فلو بنك الدم (8)
      ├── أمر تغذية/وريدي/تمريضي ► محطة التمريض
      ▼
   النتائج تعود ──► Physician Acknowledgement [GATE: order-result loop]
      ▼
   القرار: خروج / تنويم ADT / تحويل OR / إحالة ── فشل توفر سرير ↺ قائمة انتظار تنويم
```

### 3.2 الجدول التفصيلي

| البند | التفصيل |
|---|---|
| كيان المصدر | محطة الطبيب CPOE v3 (طبيب مُصادق بجلسة نشطة) |
| كيان الهدف | `clinical_notes`، `diagnoses`، `orders` (بأنواعها)، `prescriptions`، `acknowledgements`، `admissions` |
| الحدث | `note.signed`، `diagnosis.added`، `order.placed`، `order.cancelled`، `result.acknowledged`، `decision.recorded` |
| البيانات المنشأة/المحدثة | ملاحظة سريرية موقعة، رمز ICD-10-AM، أمر بحالة (placed→in-progress→resulted→acknowledged)، وصفة بكمية إجمالية وإعادة صرف |
| التحقق | الأمر مرتبط بزيارة نشطة؛ الوصفة تمر بفحص حساسية المريض المسجلة + تداخلات؛ جرعات الأطفال مقيدة بالوزن؛ لا أمر مكرر نشط لنفس الفحص خلال نافذة زمنية؛ الإلغاء يتطلب سبباً |
| الصلاحية | طبيب فقط يضع أوامر ويوقّع؛ طبيب مقيم قد يتطلب توقيعاً مزدوجاً (Co-sign) حسب إعداد المنشأة؛ التعديل بعد التوقيع = إضافة تصحيح (Amendment) لا استبدال (`emr_amendments`) |
| حدث التدقيق | `order_placed`، `order_cancelled(reason)`، `note_signed`، `note_amended`، `result_acknowledged`، `critical_result_notified` |
| حدث التكامل | داخلي: تمثيل الأوامر بـ FHIR `ServiceRequest`/`MedicationRequest` تمهيداً للتبادل؛ التشخيصات جاهزة كـ FHIR `Condition` لحزم NPHIES |
| معالجة الفشل | فشل فحص التداخلات (الخدمة غير متاحة) ⇒ منع الحفظ الصامت: يظهر تحذير "تعذر الفحص" ويتطلب تجاوزاً موثقاً بسبب `[AUDIT: interaction_check_override]`؛ نتيجة حرجة غير مُقرّة خلال المهلة ⇒ تصعيد لرئيس القسم؛ انقطاع الجلسة أثناء التوثيق ⇒ مسودة محلية تُستأنف |

## 4. فلو 3 — التمريض (Nursing: علامات حيوية ← EWS ← eMAR ← SBAR)

### 4.1 المخطط

```
محطة التمريض (10 تبويبات)
      │
      ├─ (أ) علامات حيوية ──► محرك NEWS2/MEWS/PEWS ──► درجة
      │        │                        │
      │        │            درجة ≥ عتبة التصعيد؟
      │        │                ├─ نعم ──► تنبيه طبيب + توثيق SBAR [GATE]
      │        │                └─ لا ───► جدولة القياس التالي
      │        ▼
      ├─ (ب) eMAR: أمر دوائي معتمد من الصيدلية ──► [GATE: الحقوق الخمسة 5R]
      │        (مريض/دواء/جرعة/طريق/وقت) ──► توثيق الإعطاء أو الامتناع بسبب
      ├─ (ج) تقييم + خطة رعاية + سوائل (مدخول/مخرج) ──► رصيد السوائل
      ├─ (د) تقييم مخاطر (سقوط/قرح ضغط) ──► تدخلات وقائية
      └─ (هـ) تنفيذ الأوامر التمريضية القادمة من CPOE ──► إغلاق كل أمر بتوثيق
```

### 4.2 الجدول التفصيلي

| البند | التفصيل |
|---|---|
| كيان المصدر | محطة التمريض العامة (وامتداداتها التخصصية المخططة: طوارئ/ICU/عمليات/PACU/ولادة) |
| كيان الهدف | `vitals`، `ews_assessments`، `emar_administrations`، `care_plans`، `fluid_balance`، `risk_assessments`، `sbar_handoffs` |
| الحدث | `vitals.recorded`، `ews.calculated`، `ews.escalated`، `medication.administered`، `medication.withheld`، `handoff.completed` |
| البيانات المنشأة/المحدثة | قياسات حيوية بطابع زمني، درجة EWS محسوبة آلياً (لا تُدخل يدوياً — محرك مضاد للتلاعب)، سجل إعطاء دواء بتوقيع الممرضة، رصيد سوائل تراكمي |
| التحقق | القيم الحيوية ضمن مدى فسيولوجي ممكن (رفض قيم مستحيلة)؛ درجة EWS تُحسب في الخادم لا في المتصفح؛ الإعطاء لا يتم إلا لأمر بحالة `verified` من الصيدلية؛ لا إعطاء قبل وقته المجدول إلا بتجاوز موثق |
| الصلاحية | ممرضة مسجلة: توثيق وإعطاء؛ الأدوية عالية الخطورة تتطلب توقيعاً مزدوجاً (Witness)؛ لا صلاحية إلغاء أوامر الطبيب — فقط "امتناع بسبب" |
| حدث التدقيق | `vitals_recorded`، `ews_escalation_triggered(score, notified_to)`، `med_administered(witness?)`، `med_withheld(reason)`، `handoff_signed` |
| حدث التكامل | — (داخلي)؛ درجات EWS متاحة عبر `/api/ews/assess` للوحات التشغيل |
| معالجة الفشل | تعذر إشعار الطبيب بالتصعيد ⇒ سلسلة تصعيد بديلة (طبيب مناوب ← رئيس قسم) مع مؤقتات؛ ماسح/إدخال دواء لمريض خاطئ ⇒ منع بمطابقة رقم الزيارة + `[AUDIT: 5r_mismatch_blocked]`؛ انقطاع الشبكة أثناء جولة الأدوية ⇒ التوثيق البعدي يتطلب سبب تأخير |

## 5. فلو 4 — المختبر (LIS: أمر ← عينة ← تحليل ← نتيجة ← قيمة حرجة)

### 5.1 المخطط

```
CPOE أمر مختبر ──► LIS: قائمة عمل (Worklist)
      ▼
سحب العينة ──► ملصق باركود (مريض+زيارة+فحص) [GATE: تطابق هوية العينة]
      ▼
استلام العينة بالمختبر ── رفض؟ (تحلل/كمية/ملصق) ─ نعم ↺ إعادة سحب + إشعار الطبيب
      ▼ لا
التحليل ──► إدخال/استيراد النتيجة ──► تحقق فني (Tech Verify)
      ▼
اعتماد نهائي (Pathologist/Senior Verify) [GATE: توقيع مزدوج للنتائج الحرجة]
      ▼
النتيجة ضمن المدى الحرج؟
      ├─ نعم ──► إشعار فوري للطبيب + توثيق التبليغ (من/متى/لمن) [GATE: Critical Value]
      └─ لا ───► نشر النتيجة ──► محطة الطبيب (Ack) + بوابة المريض (بعد الاعتماد)
```

### 5.2 الجدول التفصيلي

| البند | التفصيل |
|---|---|
| كيان المصدر | أمر CPOE / أمر طوارئ / سحب خارجي (بوابة لاحقاً) |
| كيان الهدف | `lab_orders`، `lab_samples`، `lab_results`، `critical_notifications` |
| الحدث | `sample.collected`، `sample.received`، `sample.rejected`، `result.entered`، `result.verified`، `result.critical_flagged`، `result.published` |
| البيانات المنشأة/المحدثة | حالة الأمر عبر دورة الحياة، بيانات العينة (نوع/وقت السحب/الساحب)، النتيجة بقيمة ومدى مرجعي وعلم (H/L/Critical) |
| التحقق | تطابق باركود العينة مع الزيارة؛ فحص Delta Check مقابل آخر نتيجة للمريض؛ المدى المرجعي حسب العمر/الجنس؛ لا نشر لنتيجة غير معتمدة |
| الصلاحية | فني مختبر: إدخال وتحقق أولي؛ اعتماد نهائي لأخصائي/استشاري فقط؛ لا يرى الفني إلا عينات مستأجره `[RLS]` |
| حدث التدقيق | `sample_rejected(reason)`، `result_verified(by)`، `critical_value_notified(to, at, read_back?)`، `result_corrected(old→new)` — تصحيح النتيجة بعد النشر يبقي النسخة القديمة مرئية كـ "مُصحَّح" |
| حدث التكامل | داخلي FHIR `Observation`/`DiagnosticReport`؛ رموز الفحوصات جاهزة للتوحيد على LOINC لاحقاً (تمهيد NPHIES) |
| معالجة الفشل | رفض العينة ⇒ إعادة الأمر لحالة `recollect` وإشعار الجهة الطالبة تلقائياً (لا يسقط الأمر صامتاً — إغلاق الحلقة)؛ تعطل جهاز التحليل ⇒ تحويل يدوي مع علم `manual_entry`؛ نتيجة حرجة بلا إقرار خلال المهلة ⇒ تصعيد هرمي موثق |

## 6. فلو 5 — الأشعة (RIS: أمر ← جدولة ← تصوير ← تقرير ← PHI Vault)

### 6.1 المخطط

```
CPOE أمر أشعة ──► RIS: فحص مبررات + [GATE: حمل؟ سؤال إلزامي قبل التصوير الإشعاعي]
      ▼
جدولة ──► تحضير المريض ──► تنفيذ التصوير (فني أشعة)
      ▼
رفع الصور ──► PHI Vault (خارج webroot) ── وصول فقط عبر
              GET /api/phi-files/:id [مصادقة + RLS + منع Traversal + AUDIT]
      ▼
قراءة وتقرير (طبيب أشعة) ──► اعتماد التقرير
      ▼
نتيجة حرجة (Critical Finding)؟ ── نعم ──► إشعار فوري موثق للطبيب المعالج [GATE]
      ▼ لا
نشر التقرير ──► محطة الطبيب (Ack) ──► بوابة المريض (بعد الاعتماد)
```

## 7. فلو 6 — الصيدلية (وصفة ← مراجعة سريرية ← صرف ← eMAR ← مخزون)

### 7.1 المخطط

```
وصفة CPOE (Rx + QtyTotal + Refill) ──► طابور الصيدلية
      ▼
مراجعة صيدلي [GATE: حساسية + تداخل دوائي + ازدواج علاجي + جرعة]

التحقق (Verify) ──► الصرف (Dispense) ──► خصم المخزون (دفعة/صلاحية FEFO)
      │                                        │
```

## 8. فلو 7 — بنك الدم (طلب ← فصيلة وتوافق ← صرف وحدة ← نقل موثق)

### 8.1 المخطط

```
أمر دم CPOE ──► بنك الدم: طلب تحضير
      ▼
عينة Type & Screen [GATE: عينتان مستقلتان للفصيلة عند أول تحديد]
      ▼
فحص التوافق (Crossmatch) ── غير متوافق ↺ بحث وحدات بديلة / تنسيق مع مركز التبرع
      ▼ متوافق
حجز الوحدة ──► صرف الوحدة (سلسلة تبريد موثقة)
      ▼
عند السرير: تحقق مزدوج ممرضتان [GATE: مريض+وحدة+فصيلة+رقم]
      ▼
بدء النقل ──► مراقبة علامات حيوية (0/15/30 دقيقة...)
      ├─ تفاعل نقل؟ ── نعم ──► إيقاف فوري + بروتوكول تفاعل + بلاغ OVR (فلو 11) [GATE]
      └─ لا ──► إتمام النقل + توثيق + إعادة/إتلاف الكيس حسب السياسة
```

### 8.2 الجدول التفصيلي

| البند | التفصيل |
|---|---|
| كيان المصدر | أمر دم من CPOE (طبيب) بمؤشر سريري إلزامي |
| كيان الهدف | `blood_requests`، `blood_units`، `crossmatches`، `transfusions`، `transfusion_reactions` |
| الحدث | `blood.requested`، `type_screen.completed`، `crossmatch.compatible`، `unit.issued`، `transfusion.started`، `transfusion.completed`، `reaction.reported` |
| البيانات المنشأة/المحدثة | فصيلة المريض (لا تُعدَّل إلا بعينتين متطابقتين)، حالة الوحدة (متاحة→محجوزة→مصروفة→منقولة/مرتجعة)، سجل مراقبة النقل |
| التحقق | تطابق الفصيلة والـ Rh؛ صلاحية الوحدة؛ نافذة صلاحية الـ Crossmatch (72 ساعة)؛ التحقق المزدوج عند السرير لا يقبل توقيعاً واحداً؛ زمن خروج الوحدة من التبريد ≤ 30 دقيقة وإلا إرجاع مشروط |

## 9. فلو 8 — العمليات (OR: حجز ← ما قبل ← تخدير ← عملية ← PACU)

> ملاحظة فجوة: توثيق التخدير وPACU مفقودان في النظام الحالي (أخطر فجوة سلامة جراحية) — هذا الفلو يخطط الدورة الكاملة المستهدفة.

### 9.1 المخطط

```
قرار جراحة (فلو 2) ──► حجز غرفة عمليات + فريق
      ▼
ما قبل العملية: فحوصات + موافقة مستنيرة موقعة [GATE: Consent] + صيام + تقييم تخدير (ASA)
      ▼
[GATE: Surgical Safety Checklist — Sign-In]
      ▼
التخدير: بدء توثيق (أدوية/عمق/علامات حيوية مستمرة) ── (مخطط — فجوة حالية)
      ▼
[GATE: Time-Out قبل الشق: مريض/موضع/إجراء/فريق]
      ▼
العملية: توثيق جراحي + عدّ الشاش والأدوات [GATE: Count صحيح قبل الإغلاق]
      │        └─ عينة مستأصلة؟ ──► علم الأمراض (باثولوجيا) بسلسلة عهدة
      ▼
[GATE: Sign-Out] ──► نقل إلى PACU (إفاقة) ── (مخطط — فجوة حالية)
      ▼
PACU: مراقبة + درجة Aldrete ── الدرجة ≥ عتبة الخروج؟
      ├─ نعم ──► عودة للجناح (ADT) أو خروج نهاري
      └─ لا ──► استمرار مراقبة ↺ / تصعيد ICU
      ▼
مستلزمات وأدوات مستهلكة ──► فلو المخازن (10) + أدوات ──► CSSD (تعقيم)
```

### 9.2 الجدول التفصيلي

| البند | التفصيل |
|---|---|
| كيان المصدر | قرار جراحي من محطة الطبيب / إحالة تخصصات |
| كيان الهدف | `or_bookings`، `preop_assessments`، `consents`، `anesthesia_records` (مخطط)، `op_notes`، `pacu_records` (مخطط)، `pathology_specimens` |
| الحدث | `or.booked`، `consent.signed`، `checklist.sign_in`، `anesthesia.started`، `checklist.time_out`، `surgery.completed`، `counts.reconciled`، `checklist.sign_out`، `pacu.admitted`، `pacu.discharged` |
| البيانات المنشأة/المحدثة | جدول العمليات، تقييم ASA، سجل تخدير زمني، مذكرة العملية، عدّ الأدوات (قبل/بعد)، درجة Aldrete |
| التحقق | لا دخول للغرفة بلا موافقة موقعة سارية؛ قائمة السلامة الجراحية ثلاثية المراحل إلزامية بترتيبها؛ عدم تطابق العدّ يمنع إغلاق التوثيق ويستدعي تصوير أشعة فورياً؛ لا خروج من PACU دون بلوغ عتبة Aldrete أو أمر طبيب موثق |
| الصلاحية | جرّاح: مذكرة العملية؛ طبيب تخدير: سجل التخدير حصراً؛ ممرضة عمليات: العدّ والتحضير؛ ممرضة إفاقة: توثيق PACU؛ الموافقة تُوثَّق بحضور شاهد |

| معالجة الفشل | إلغاء/تأجيل العملية ⇒ سبب مصنف (مريض/طبي/تشغيلي) + إعادة جدولة تلقائية + إشعار المريض؛ عدم تطابق العدّ ⇒ بروتوكول Retained Item: أشعة + بلاغ OVR إلزامي؛ حجز متعارض للغرفة ⇒ منع بقيد تفرد زمني في الجدولة |

## 10. فلو 9 — الفوترة والتأمين (Billing/Insurance: تجميع ← مطالبة NPHIES ← ZATCA ← تحصيل)

### 10.1 المخطط

```
مصادر التكلفة (زيارة/أوامر/صرف صيدلية/عملية/إقامة سرير)
      ▼
حساب المريض: تجميع البنود (Charge Capture) ──► تسعير حسب العقد/الخطة
      ▼
نقدي أم مؤمَّن؟
      ├─ نقدي ──► فاتورة ──⇢ ZATCA Phase-2 (فاتورة إلكترونية، مقيد CSID) [IDEMP]
      │                └─ فشل إرسال ↺ طابور إعادة + الفاتورة محلية بحالة pending_zatca
      └─ مؤمَّن ──► بناء حزمة FHIR (Claim + MessageHeader + ICD-10-AM + SBS)
                        ▼
                  [GATE: اكتمال الترميز + أهلية سارية + موافقات مسبقة إن لزمت]
                        ▼
                  ⇢ NPHIES: إرسال المطالبة [IDEMP]
                        ├─ قبول كلي ──► إشعار تحويل (Remittance) ──► ترحيل GL
                        ├─ قبول جزئي/رفض ──► طابور الرفوضات ↺ تصحيح + إعادة تقديم
                        └─ خطأ تقني ↺ إعادة إرسال بنفس مفتاح Idempotency
      ▼
التحصيل (نقد/شبكة/تحويل تأمين) ──► قيود GL آلية ──► تقارير الإيرادات
```

### 10.2 الجدول التفصيلي

|---|---|
| كيان المصدر | كل نقاط الخدمة المولّدة للتكلفة (أوامر، صرف، إقامة، إجراءات) |
| كيان الهدف | `patient_accounts`، `invoices`، `invoice_lines`، `claims`، `claim_responses`، `remittances`، `gl_entries`، `zatca_submissions` |
| الحدث | `charge.captured`، `invoice.issued`، `claim.submitted`، `claim.accepted/partially/denied`، `remittance.received`، `payment.posted`، `zatca.cleared/reported` |

## 11. فلو 10 — المخازن وسلسلة الإمداد (Inventory: طلب قسم ← صرف ← إعادة طلب ← استلام)

### 11.1 المخطط

```
كتالوج الأصناف (تبويب) ──► أرصدة لحظية لكل مخزن فرعي [RLS]
      ▲
قسم (صيدلية/عمليات/تمريض/مختبر) ──► طلب قسم (Requisition)
      ▼
اعتماد أمين المخزن [GATE: صلاحية اعتماد + سقف كمية]
      ▼
صرف داخلي ──► خصم رصيد المصدر + إضافة لمخزن القسم (حركة مزدوجة ذرّية)
      ▼
الرصيد ≤ نقطة إعادة الطلب؟
      ├─ نعم ──► طلب شراء ──► اعتماد ──► أمر شراء للمورد
      │              ▼
      │        استلام (GRN): فحص كمية/صلاحية/دفعة ── مخالفة؟ ↺ إرجاع للمورد موثق
      │              ▼
      │        إضافة للرصيد + تحديث تكلفة ──► قيد GL (فلو 9)
      └─ لا ──► استمرار المراقبة
      ▼
جرد دوري ──► فروقات ──► تسوية معتمدة [AUDIT: adjustment(reason)]
```

### 11.2 الجدول التفصيلي

| البند | التفصيل |
|---|---|
| كيان المصدر | طلبات الأقسام (تبويب في المخازن)، نقاط الصرف الآلي (صيدلية/عمليات)، أوامر الشراء |
| كيان الهدف | `items`، `stock_balances`، `requisitions`، `stock_transactions`، `purchase_orders`، `goods_receipts`، `stock_adjustments` |
| الحدث | `requisition.created/approved/issued`، `stock.transferred`، `reorder.triggered`، `po.issued`، `grn.received`، `stock.adjusted`، `batch.expiring_alert` |
| البيانات المنشأة/المحدثة | حركة مخزنية مزدوجة (من مخزن إلى مخزن)، دفعات بتواريخ صلاحية، متوسط تكلفة، أرصدة لحظية |
| التحقق | لا صرف برصيد سالب؛ FEFO للدفعات (الأقرب صلاحية أولاً)؛ الأصناف الطبية الحرجة لا تُصرف لغير الأقسام المصرح لها؛ استلام الشراء يطابق أمر الشراء كمية وصنفاً |
| الصلاحية | أمين مخزن: صرف واستلام؛ اعتماد الطلبات حسب سقف مالي متدرج؛ التسويات الجردية بصلاحية مدير مخازن + سبب إلزامي؛ الأصناف المخدرة بمسار صلاحيات الصيدلية المقيد |
| حدث التدقيق | كل حركة مخزنية بسجل (من/إلى/كمية/دفعة/مَن نفّذ)؛ `adjustment(reason, delta)`، `expired_batch_quarantined`، `po_approved(by, amount)` |
| حدث التكامل | داخلي مع GL (تكلفة المخزون وقيود الاستلام)؛ ربط موردين إلكتروني = مخطط مستقبلي |
| معالجة الفشل | فشل الحركة المزدوجة ⇒ معاملة ذرّية ترجع بالكامل (لا رصيد معلق بين مخزنين)؛ صنف حرج تحت الحد الآمن ⇒ تنبيه تصعيدي للمشتريات + بديل معتمد؛ فرق جرد متكرر لنفس الصنف ⇒ علم تحقيق يظهر في تقارير الجودة |

## 12. فلو 11 — الجودة وسلامة المرضى (Quality/Safety: OVR ← RCA ← مؤشرات ← CBAHI)

### 12.1 المخطط

```
مصادر البلاغ:
  تفاعل نقل دم (فلو 8) ─┐
  خطأ دوائي (فلو 4/7) ──┤
  سقوط مريض ────────────┼──► بلاغ حادثة OVR (سري — يجوز مجهول المصدر)
  عدّ أدوات ناقص (فلو 9)┤        │
  عدوى مكتسبة HAI ──────┘        ▼
                        تصنيف الخطورة (SAC / تصنيف مصفوفي)
                                 │
              ┌── حدث جسيم (Sentinel) ──► إشعار فوري للإدارة + فريق RCA [GATE: 45 يوماً]
              ▼
        تحقيق وتحليل جذري RCA ──► خطة تصحيحية CAPA ──► متابعة إغلاق
                                 ▼
        مؤشرات الجودة (KPIs) + ترصد مكافحة العدوى (HAI) ──► لوحات + تقارير CBAHI
                                 ▼
        تتبع معايير CBAHI (فصل/معيار/دليل/حالة امتثال) ──► خطة اعتماد
```

### 12.2 الجدول التفصيلي

| البند | التفصيل |
|---|---|
| كيان المصدر | أي موظف (بلاغ OVR — يجوز مجهولاً)، ترصد مكافحة العدوى، مخرجات آلية من الفلوهات السريرية (تفاعل دم/عدم تطابق عدّ) |
| كيان الهدف | `ovr_reports`، `ovr_classifications`، `rca_investigations`، `capa_actions`، `hai_surveillance`، `quality_kpis`، `cbahi_standards_tracker` |
| الحدث | `ovr.reported`، `ovr.classified(severity)`، `rca.opened/closed`، `capa.assigned/verified`، `hai.case_confirmed`، `kpi.threshold_breached` |
| البيانات المنشأة/المحدثة | بلاغ بحقول موحدة (ماذا/أين/متى/تصنيف)، درجة خطورة، توصيات RCA، إجراءات CAPA بمسؤول وموعد، حالات HAI بمعايير تعريف موحدة |
| التحقق | البلاغ الجسيم لا يُغلق بلا RCA مكتمل؛ CAPA بلا تحقق إغلاق تبقى مفتوحة وتصعد؛ حالة HAI تتطلب استيفاء معايير التعريف قبل الاحتساب |
| الصلاحية | الإبلاغ متاح للجميع (وسرّي)؛ هوية المبلّغ محجوبة عن غير مسؤول الجودة (No-blame)؛ التصنيف والتحقيق لفريق الجودة؛ تقارير CBAHI للإدارة العليا؛ `[RLS]` صارم — بلاغات كل مستأجر معزولة كلياً |
| حدث التدقيق | `ovr_created(anonymous?)`، `severity_assigned(by)`، `rca_report_finalized`، `capa_overdue_escalated` — مع حماية خاصة: سجل التدقيق لا يكشف هوية المبلّغ المجهول |
| حدث التكامل | داخلي؛ تصدير تقارير مؤشرات لهيئات الاعتماد (CBAHI) كملفات موقعة؛ بلاغات الأحداث الجسيمة للجهات الصحية = مسار يدوي موثق (مخطط أتمتته) |
| معالجة الفشل | بلاغ جسيم بلا تصنيف خلال 24 ساعة ⇒ تصعيد تلقائي لمدير الجودة ثم المدير الطبي؛ محاولة تعديل بلاغ بعد التصنيف ⇒ ممنوعة — الإضافة بملاحق فقط؛ تسرب هوية مبلّغ ⇒ يعامل كحادثة أمنية بذاتها |

## 13. المصفوفة العرضية — أحداث التدقيق والتكامل عبر كل الفلوهات

### 13.1 خريطة أحداث التكامل الخارجي

| التكامل | الفلو المصدر | الرسالة/الصيغة | التوقيت | الحماية |
|---|---|---|---|---|
| NPHIES Eligibility | Patient Access (2) | FHIR `CoverageEligibilityRequest` | عند التسجيل وقبل كل زيارة مؤمَّنة | فشل ⇒ مسار نقدي موثق، طابور إعادة |
| NPHIES Claim | Billing (10) | حزمة FHIR message + MessageHeader + ICD-10-AM/SBS | بعد اكتمال الترميز | `[IDEMP]` + طابور رفوضات |
| NPHIES Remittance | Billing (10) | `PaymentReconciliation` | عند ورود التحويل | `[IDEMP]` + مطابقة آلية |
| ZATCA Phase-2 | Billing (10) | فاتورة إلكترونية Clearance/Reporting | عند إصدار الفاتورة | `[IDEMP]`، مقيد CSID، طابور pending_zatca |
| FHIR داخلي (تمهيدي) | Clinical/Lab/Rad/Pharmacy | ServiceRequest/Observation/DiagnosticReport/MedicationDispense | لحظي داخلي | أساس التبادل المستقبلي (نفيس تبادل صحي) |

### 13.2 القالب الموحد لسجل التدقيق (كل الفلوهات)

| الحقل | الوصف |
|---|---|
| `event_type` | اسم الحدث المعياري (مثل `order_placed`, `phi_file_accessed`) |
| `actor` | المستخدم/الدور/الجلسة (أو "مجهول محمي" في OVR) |
| `tenant_id` | مستأجر الحدث — مستمد من الجلسة لا من الترويسة (حماية Gate 4) |
| `subject` | المريض/الكيان المتأثر (معرّف داخلي، لا PHI في نص السجل) |
| `before/after` | القيم قبل وبعد للتعديلات الحساسة |
| `timestamp` | طابع زمني خادمي (لا يُقبل من العميل) |
| `outcome` | نجاح/رفض/تجاوز موثق |

### 13.3 مبادئ معالجة الفشل المعيارية (ملخص)

| نمط الفشل | الاستجابة المعيارية |
|---|---|
| فشل تحقق مدخلات | 422 + رسالة عربية + لا كتابة جزئية |
| فشل صلاحية/RLS | 403/404 + `access_denied` مدقق، دون كشف وجود السجل |
| فشل تكامل خارجي | حالة `pending_*` + طابور backoff — السريري لا ينتظر المالي |
| ازدواج طلب مالي | Idempotency يعيد الاستجابة الأولى دون أثر مكرر |
| فشل معاملة مركبة | ذرّية كاملة (Transaction) — كل شيء أو لا شيء |
| نتيجة حرجة بلا إقرار | تصعيد هرمي بمؤقتات + توثيق سلسلة الإشعار |
| بوابة سلامة لم تُستوفَ | حجب صلب؛ التجاوز (إن جاز) بصلاحية عليا + سبب مدقق |

## 14. خلاصة الترابط بين الفلوهات

```
Patient Access ──► Clinical ──► Nursing ──► [Lab | Radiology | Pharmacy | Blood Bank | OR]
      │                │                          │
      │                └── قرارات ◄── نتائج ◄─────┘
      ▼                ▼
   NPHIES أهلية    Billing/Insurance ⇢ NPHIES + ZATCA ──► GL
                        ▲                                   ▲
   Inventory ───────────┴── تكلفة الصرف والاستلام ──────────┘
   Quality/Safety ◄── بلاغات آلية من (دم/دواء/عمليات/عدوى) — حلقة تحسين مستمرة
```

- كل سهم في هذه الوثيقة يمر إلزامياً عبر: `[RLS]` عزل مستأجر ← صلاحية دور ← تحقق ← `[AUDIT]`.
- الفجوات المعروفة المضمنة كمسارات مخططة (لا موجودة): توثيق التخدير، PACU، NICU، خريطة الأسرّة الحية، محطات التمريض التخصصية، عارض سجل التدقيق، DICOM/PACS.
- هذه الوثيقة مرجع GATE 7 وتُغذّي مباشرة بوابات التصميم التفصيلي (شاشات + عقود API) اللاحقة.
