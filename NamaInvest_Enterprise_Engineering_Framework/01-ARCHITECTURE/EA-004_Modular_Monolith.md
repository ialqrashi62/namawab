# استراتيجية Modular Monolith

**Document ID:** EA-004  
**Purpose:** تنظيم النظام كموديولات مستقلة داخل نشر موحد.

## 1. القاعدة الأساسية

يجب أن تُصمم المعمارية بحيث تفصل بين:

- منطق الأعمال.
- قواعد الدومين.
- التخزين.
- الواجهات.
- التكاملات الخارجية.
- المهام الخلفية.
- التقارير.
- الذكاء الاصطناعي.

أي اعتماد مباشر بين هذه الطبقات يجب أن يكون مبرراً وموثقاً.

## 2. سياسات معمارية إلزامية

### POLICY EA-004-001: فصل الدومين عن التفاصيل التقنية

لا يجوز أن يحتوي منطق الدومين على تفاصيل ORM أو HTTP أو UI أو مكتبات خارجية غير ضرورية.

### POLICY EA-004-002: الحدود واضحة بين الوحدات

كل وحدة ERP يجب أن تمتلك حدوداً واضحة، واجهات دخول وخروج، وأحداثاً أو خدمات معلنة، ولا يجوز لوحدة أن تعدل بيانات وحدة أخرى مباشرة إلا عبر عقد واضح.

### POLICY EA-004-003: العزل متعدد المستأجرين شرط معماري

كل طبقة يجب أن تسأل: أين tenantId؟ أين companyId؟ أين branchId عند الحاجة؟ وأين صلاحيات المستخدم؟

### POLICY EA-004-004: قابلية الاستبدال

يجب أن تكون الأنظمة الخارجية مثل بوابات الدفع، مزودي الرسائل، مزودي الفوترة، خدمات الذكاء الاصطناعي، ومحركات التقارير قابلة للاستبدال عبر واجهات داخلية.

## 3. قواعد الدومين

- لا يكتب منطق محاسبي داخل مكونات الواجهة.
- لا تكتب قواعد تسعير داخل مسار API دون خدمة دومين.
- لا تحدث المخزون مباشرة من شاشة بيع دون خدمة حركة مخزون.
- لا تولد قيود مالية دون محرك محاسبي أو خدمة مالية معتمدة.
- لا يتم الاعتماد على قيم واجهة المستخدم كحقيقة نهائية دون تحقق خلفي.

## 4. نمط الاعتمادات

الاتجاه المسموح:

```text
UI / API / Jobs
        ↓
Application Services
        ↓
Domain Services / Entities
        ↓
Repositories / Infrastructure Contracts
        ↓
Database / External Providers
```

الاتجاه الممنوع:

```text
Domain → UI
Domain → HTTP Framework
Domain → ORM Specific Details
Accounting Core → Random Feature Service
Security Core → Presentation Layer
```

## 5. متطلبات قابلية التوسع

- دعم التحميل الكسول للواجهات.
- دعم فهرسة قاعدة البيانات للاستعلامات الأساسية.
- منع الاستعلامات غير المحددة بنطاق المستأجر.
- منع عمليات قائمة ضخمة دون Pagination.
- استخدام Queue للعمليات الثقيلة.
- استخدام Caching فقط بعد ضمان صحة الإبطال Invalidation.

## 6. متطلبات المراجعة المعمارية

يجب إجراء مراجعة معمارية عند:

- إضافة وحدة جديدة.
- تعديل قاعدة البيانات في جداول حساسة.
- إضافة تكامل خارجي.
- تعديل منطق المحاسبة أو المخزون أو المصادقة.
- إدخال تبعية جوهرية.
- تغيير طريقة الصلاحيات.
- إنشاء وظيفة AI مؤثرة على القرار أو البيانات.

## 7. مخرجات المراجعة

كل مراجعة معمارية يجب أن تنتج:

- ملخص القرار.
- البدائل.
- المخاطر.
- الأثر على الدومينات.
- خطة الاختبارات.
- ADR عند الحاجة.
- Quality Gate مناسب.

## 8. قائمة تحقق مختصرة

- [ ] هل الدومين مفصول عن الواجهة؟
- [ ] هل يوجد عزل مستأجر؟
- [ ] هل يوجد تحقق صلاحيات؟
- [ ] هل التأثير المحاسبي واضح؟
- [ ] هل يوجد اختبار؟
- [ ] هل القرار موثق؟
- [ ] هل الأداء مقبول؟
- [ ] هل التغيير قابل للرجوع؟
